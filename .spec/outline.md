### 全书设计原则

#### 1. 第一二章：通用场景为主，编程场景为辅

第一二章（CRC、多轮对话）是通用的 AI 沟通技能，面向所有 AI 用户（不限于程序员）。

- **主案例用通用场景**：如写商业计划书、设计课程大纲、策划活动、分析市场报告等
- **每节末尾附编程场景对照**：简短展示同一技巧在编程中的应用，方便程序员迁移
- **第三章开头做过渡**：说明"前两章学的技巧，接下来我们把它们应用到软件开发中"

通用场景建议：

| 技巧 | 通用场景 |
|------|---------|
| CRC-Context | 看医生（提供病史背景） |
| CRC-Requirement | 点餐（具体描述想吃什么） |
| CRC-Constraint | 装修（预算限制、风格要求、不能动承重墙） |
| 苏格拉底式提问 | 找律师咨询（律师先问你一系列问题） |
| 少样本引导 | 教 AI 按你的风格写周报 |
| 角色扮演 | 模拟面试（让朋友扮演面试官） |
| 方案对比 | 买车（让销售列出三款车的优缺点） |
| 挑错与优化 | 让 AI 审查商业计划书找漏洞 |
| 元提示 | 让 AI 帮你设计更好的提问方式 |
| 对话管理 | 长对话保持方向、何时另起新话题 |

#### 2. 渐进式提示词设计（第 4-8 章）

后续章节的提示词不能让读者觉得"SDD 的提示词好复杂"。每个 SDD 阶段的提示词采用三层设计：

**第一层：一句话启动（读者必学）**
每个阶段只需一句简单提示词即可启动：
```
Constitution: "为这个项目建立项目宪章，包括架构原则、技术栈、编码规范和质量标准。"
Specify:      "我要做一个 Todo 应用，帮我写功能规范。"
Clarify:      "审查这份规范，找出不够明确的地方，逐条向我提问。"
Plan:         "基于 @spec.md 和 @constitution.md，做技术方案设计。"
Tasks:        "基于 @plan.md，拆解为可执行的任务列表。"
Implement:    "按 @tasks.md 的第一个任务，先写测试再实现。"
```

**第二层：对话补充（自然追加）**
AI 产出初版后，通过简短追问补充细节：
```
→ AI 产出了 Constitution 初版
你："技术栈我想用 FastAPI + PostgreSQL，补充进去。"
你："安全方面要用 JWT 认证，加上。"
```

**第三层：完整参考（可选）**
每个阶段末尾提供完整版提示词参考，明确标注"这不是必须的"——一句话启动 + 对话补充就能达到同样效果。

#### 3. 标准文档结构

SDD 各阶段的产出物按以下目录结构组织，在第 3 章引入，后续各章严格遵循：

```
project/
├── .spec/                              # SDD 规范文档根目录
│   ├── constitution.md                 # 项目宪章（项目级，唯一）
│   └── features/                       # 功能规范目录
│       ├── 001-todo-core/              # Feature 1
│       │   ├── spec.md                 #   Specify 阶段产出
│       │   ├── plan.md                 #   Plan 阶段产出
│       │   └── tasks.md               #   Tasks 阶段产出
│       └── 002-todo-tags/              # Feature 2
│           ├── spec.md                 #
│           ├── plan.md                 #
│           └── tasks.md               #
├── .cursor/rules/                      # AI 规则文件（从 constitution 生成）
├── src/                                # 功能代码
└── tests/                              # 测试代码
```

设计要点：
- `.spec/` 作为根目录，所有规范文档集中存放，与代码分离
- `constitution.md` 在顶层，强调项目级、唯一
- `features/` 按编号+名称组织，每个 Feature 一个目录
- 文件名严格对应 SDD 阶段：`spec.md`（Specify）→ `plan.md`（Plan）→ `tasks.md`（Tasks）
- 领域模型、数据模型、API 设计等内容统一放在 `plan.md` 中，不单独拆文件

### 统一讲解模式

第 4-7 章的每个 SDD 阶段统一采用 **"讲 → 做 → 审"** 三步模式：

| 步骤 | 内容 | 说明 |
|------|------|------|
| **讲** | 概念讲解 | 这个阶段做什么、为什么重要（简短，2-3 段） |
| **做** | 提示词 + AI 产出示例 | 一句话启动 → 对话补充 → 完整参考（可选） |
| **审** | 审查要点 | 你应该检查什么、常见问题、产出物保存路径 |

### 案例设计

- **Feature 1**（第 5-7 章）：Todo 核心功能（CRUD + 认证授权 + 筛选分页），完整走 SDD 全流程
- **Feature 2**（第 8 章）：一个小型优化需求（如"增加 Todo 标签功能"），压缩演示迭代循环

## 第二部分：规范驱动开发（SDD）

### 第 3 章：SDD 概述

**本章目标**：理解 SDD 的全貌，建立对规范驱动开发的整体认知。

#### 知识点

1. **从 Vibe Coding 说起**
   - 反面案例：直接让 AI"帮我写一个 Todo API"会怎样
   - 问题本质：跳过思考直接编码 → 需求不清、架构混乱、反复返工
   - AI 擅长执行，不擅长决策

2. **什么是 SDD（规范驱动开发）**
   - 核心理念：规范先行，分阶段推进，人决策 AI 执行
   - 规范是"单一真相源"，代码是规范的产物
   - 与 Vibe Coding 的对比

   | 维度 | Vibe Coding | SDD |
   |------|------------|-----|
   | 起点 | 模糊的提示词 | 结构化的规范文档 |
   | 过程 | 一次性生成 | 分阶段推进 |
   | 验证 | 跑起来就行 | 对照规范持续验证 |
   | 代码地位 | 唯一产物 | 规范的衍生物 |

3. **SDD 完整流程**
   - 项目级（一次性）：Constitution — 建立项目宪章
   - 功能级（每个 Feature）：Specify → Clarify → Plan → Tasks → Implement
   - 流程图展示

4. **项目级 vs 功能级**
   - Constitution 是"规矩"，做一次，所有 Feature 遵守
   - Specify → Implement 是"做事"，每个 Feature 循环一次
   - Constitution 包含：架构原则、技术栈、编码规范、安全策略、部署架构
   - 功能级包含：需求定义、领域建模、技术设计、任务拆解、编码实现

5. **CRC 和多轮对话在 SDD 中的应用**
   - CRC 是每次与 AI 对话的基本工具，贯穿 SDD 所有阶段
   - 多轮对话技巧的典型应用场景：
     - Constitution：方案对比（技术选型讨论）
     - Specify：苏格拉底式提问（需求完善）
     - Clarify：挑错与反驳（查漏补缺）
     - Plan：角色扮演（架构师审查）
     - Implement：少样本引导（代码风格统一）

6. **SDD 的文档结构**
   - 规范文档的标准目录结构（`.spec/` 目录树）
   - 项目级文件 vs 功能级文件的组织方式
   - 文件名与 SDD 阶段的对应关系
   - 为什么要有结构化的文档管理（给 AI 提供上下文、团队协作、版本追踪）

7. **本书案例预告**
   - Todo 应用简介
   - Feature 1（核心功能）+ Feature 2（迭代优化）的安排说明

#### 讲解形式

- 以反面案例开场，引出问题
- 概念讲解为主，配流程图和对比表格
- 展示完整的 `.spec/` 目录树，让读者建立全局认知
- 不涉及具体操作（为后续章节铺垫）
- 本章无提示词演示

#### 产出物

- 无文件产出（纯概念章节，但读者应理解后续的文档结构）

### 第 4 章：Constitution — 项目宪章

**本章目标**：学会为项目建立一份完整的项目宪章，作为所有后续开发的治理基础。

#### 知识点

1. **Constitution 的定位**
   - 项目级，做一次，对所有 Feature 生效
   - 类比：项目的"宪法"——长期稳定、普遍适用的规矩
   - Constitution 只放"规矩"，不放"设计"（领域模型、API 设计等属于 Plan）

2. **架构原则**
   - 分层架构（如 DDD 四层）、关注点分离、模块化
   - 为什么要在项目开始时确定架构原则
   - 讲 → 做 → 审

3. **技术栈选择**
   - 语言、框架、数据库的选择及理由
   - Todo 案例：选择 FastAPI + PostgreSQL + JWT 的决策过程
   - 讲 → 做 → 审

4. **开发方法论**
   - 行为测试驱动（BDD/TDD）
   - 为什么在 Constitution 阶段就要确定开发方法论
   - 讲 → 做 → 审

5. **编码规范与质量标准**
   - 命名约定、目录结构约定、代码风格
   - 测试覆盖率要求、性能基线
   - 讲 → 做 → 审

6. **安全策略**
   - 认证方式要求（如必须使用 JWT）
   - 数据保护原则（如密码必须加密存储）
   - 合规要求
   - 讲 → 做 → 审

7. **部署架构**
   - Docker 容器化
   - 环境管理（开发/测试/生产）
   - CI/CD 策略
   - 讲 → 做 → 审

8. **规则文件落地**
   - 把 Constitution 转化为 AI 能持续遵守的规则文件
   - 示例：`.cursor/rules/` 目录下的规则文件
   - Constitution 文档 vs 规则文件的关系

#### 讲解形式

每个知识点（2-7）统一采用 **"讲 → 做 → 审"**：
- **讲**：简要说明这个要素是什么、为什么重要（2-3 段）
- **做**：渐进式提示词
  - 先展示一句话启动提示词 + AI 初版产出
  - 再展示 2-3 轮追问 + AI 更新后的产出
  - 末尾给出完整版参考提示词（标注为可选）
- **审**：列出审查要点，说明常见问题

最后整合所有要素，给出一份完整的 Constitution 文档示例。

#### 产出物

- `.spec/constitution.md`（项目宪章文档）
- `.cursor/rules/` 相关规则文件

### 第 5 章：Specify & Clarify — 功能规范

**本章目标**：学会为一个 Feature 编写完整的功能规范，并通过 Clarify 查漏补缺。

#### 知识点

**Specify 部分：**

1. **功能规范的定位**
   - 每个 Feature 的起点
   - 只关注"做什么、为什么做"，不涉及技术实现
   - 与 Constitution 的关系：Constitution 定规矩，Specify 定需求

2. **规范的核心内容**
   - 用户故事：从用户视角描述需求（"作为…我希望…以便…"）
   - 功能需求：系统需要提供的具体能力
   - 非功能需求：性能、安全、可用性等要求
   - 验收标准：可验证的完成条件（每个需求对应明确的验收条件）
   - 边界场景与异常情况

3. **好规范 vs 差规范**
   - 对比示例：模糊的需求 vs 具体可验证的需求
   - 关键标准：具体、可验证、无歧义

4. **Todo Feature 1 的 Specify 实战**
   - 描述 Todo 核心功能：CRUD + 认证授权 + 筛选分页
   - 讲 → 做 → 审

**Clarify 部分：**

5. **为什么要 Clarify**
   - 规范的第一版一定有盲区
   - Clarify 的目标：在进入 Plan 之前消除歧义

6. **结构化澄清**
   - 让 AI 系统性地逐条提问，覆盖所有可能的盲区
   - 讲 → 做 → 审

7. **自由补充**
   - 针对特定模糊点追加说明
   - 讲 → 做 → 审

8. **验收清单审查**
   - 让 AI 逐条检查规范是否满足验收标准
   - 已满足的打勾，未满足的标记待补充
   - 讲 → 做 → 审

#### 讲解形式

- Specify 部分：先讲规范结构，再用 Todo Feature 1 完整演示
- Clarify 部分：演示两种澄清方式 + 验收清单审查
- 每个环节采用渐进式提示词（一句话启动 → 对话补充 → 完整参考）
- 展示 Clarify 前后的规范对比，直观看到改进

#### 产出物

- `.spec/features/001-todo-core/spec.md`（功能规范文档，含用户故事、需求、验收标准）

### 第 6 章：Plan — 架构设计

**本章目标**：学会基于功能规范进行领域建模和技术设计，产出完整的实现方案。

#### 知识点

**领域建模：**

1. **领域建模的目的**
   - 从需求中提取核心业务概念，建立结构化的业务模型
   - 领域建模是设计工作，属于 Plan 阶段（不是 Constitution）

2. **识别核心领域对象**
   - 对象及其属性
   - 对象之间的关系（用 Mermaid 图表达）
   - Todo 案例：用户、待办事项、分类等
   - 讲 → 做 → 审

3. **业务流程梳理**
   - 核心操作的流转过程（用 Mermaid 流程图）
   - Todo 案例：创建/修改/删除/查询的业务流程
   - 讲 → 做 → 审

4. **业务规则提炼**
   - 从需求中提取约束和规则
   - Todo 案例：权限规则、状态流转规则等
   - 讲 → 做 → 审

**技术设计：**

5. **数据模型设计**
   - 从领域对象映射到数据库表结构
   - 字段类型、约束、索引
   - 讲 → 做 → 审

6. **API 契约设计**
   - 接口列表、URL、HTTP 方法
   - 请求/响应格式（含示例）
   - 错误码定义
   - 讲 → 做 → 审

7. **目录结构设计**
   - 基于 Constitution 的架构原则（如 DDD 分层）落地为具体目录
   - 讲 → 做 → 审

**安全实现方案：**

8. **认证流程设计**
   - JWT 具体配置：签名算法、过期时间、刷新机制
   - 注册/登录/鉴权的完整流程
   - 讲 → 做 → 审

9. **授权规则实现**
   - 资源级别的权限控制方案
   - Todo 案例：用户只能操作自己的待办事项
   - 讲 → 做 → 审

**方案审查：**

10. **整体方案审查**
    - 让 AI 审查方案是否有过度设计
    - 让 AI 检查方案是否有遗漏
    - 与 Constitution 的一致性检查（技术选型是否符合、是否遵循架构原则）
    - 讲 → 做 → 审

#### 讲解形式

按 **领域建模 → 技术设计 → 安全方案 → 审查** 的顺序推进。

每个环节采用渐进式提示词（一句话启动 → 对话补充 → 完整参考），提示词中通过 `@` 引用前面产出的文件作为上下文。

#### 产出物

- `.spec/features/001-todo-core/plan.md`（实现方案文档，含领域模型、数据模型、API 设计、安全方案）

### 第 7 章：Tasks & Implement — 任务拆解与实现

**本章目标**：学会从 Plan 拆解出可执行的任务列表，并通过 Test → Implement → Review 循环逐个完成。

#### 知识点

**Tasks 部分：**

1. **从 Plan 到任务列表**
   - 如何把 Plan 中的设计拆解为具体可执行的任务
   - 讲 → 做 → 审

2. **拆解策略**
   - 自顶向下：适用于简单 CRUD（API 路由 → Service → 数据库操作）
   - 自底向上：适用于复杂业务逻辑（领域模型 → 领域服务 → 应用服务 → API）
   - 如何判断用哪种

3. **任务排序与依赖**
   - 任务之间的依赖关系

   - 拆解完成后的一致性检查：任务是否覆盖 spec 所有需求、有无遗漏或重复
   - 作为 Tasks 阶段的"审"环节自然完成
   - 讲 → 做 → 审

**Implement 部分：**

5. **实现循环概述**
   - 对每个任务走 Test → Implement → Review 三步
   - 为什么要测试先行：先定义"完成的标准"，再去实现

6. **演示任务 A：基础 CRUD（完整演示）**
   - **Test**：为该任务设计测试场景，生成测试代码
     - 讲 → 做 → 审（审查测试是否覆盖关键场景）
   - **Implement**：实现功能代码，使测试通过
     - 讲 → 做 → 审（审查代码质量、是否符合 Constitution 规范）
   - **Review**：代码审查与重构
     - 讲 → 做 → 审（审查 AI 的审查建议是否合理）

9. **验收对照**
