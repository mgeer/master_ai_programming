## 各章设计

### Ch3：Agent（让 AI 真正干活）

**核心问题**：AI 编程不只是让大模型生成代码——如何让它真正编译、运行、调试，自己把活干完？

**概念**
- 传统 AI 编程：人写提示词 → AI 输出文本 → 人复制代码 → 人手动运行
- Agent 模式：人描述目标 → AI 自主循环（读代码 → 写代码 → 运行 → 看结果 → 修复）→ 完成
- Agent = 大模型 + 工具 + 自主循环
- Claude Code 本身就是一个 Agent：它能读写文件、在终端运行命令、编译代码、执行测试、修复报错，全程自主
- 本书后续所有技巧（Token 管理、规范、SKILL、MCP）本质上都是在让这个 Agent 更好用

**案例**
交给 Agent："为 `calculate_discount()` 函数补全单元测试，并确保全部通过"

Agent 自主读代码、写测试、运行 `pytest`、定位 bug、修复、验证通过——全程无需人工干预。这是 AI 编程从"生成代码"到"完成任务"的质变。

**要点**
- 描述目标，而非步骤：目标清晰（"确保测试通过"）比步骤清晰（"先写测试，再运行"）更能激发 Agent 能力
- 设置合理的边界：给 Agent 授权前想清楚它可以操作哪些文件、能否执行破坏性命令
- Agent 能力上限取决于它拥有的工具：后续章节将介绍如何通过 SKILL 和 MCP 进一步扩展它的能力

### Ch4：Token 管理

**核心问题**：为什么 AI 对话越来越混乱、越来越贵？

**概念**
- Token 是什么：计量单位，≠"字"；代码/图片 token 消耗远高于文字
- Token 如何消耗：每轮对话携带完整历史，成本线性增长
- 上下文窗口限制：超限后 AI "失忆"、前后矛盾

**案例**
- 同一段代码：复制粘贴 vs `@` 引用的 token 差异对比
- 对话分段策略：何时结束当前对话、如何用 `@` 引用前序产出物开启新对话
- 提示词精简技巧：去掉礼貌性语言，只保留 3C 核心信息

**要点**
- 识别"高 token 陷阱"的检查清单
- 对话分段的判断依据：上下文是否已经完整？
- 把节省 token 的规则写入 CLAUDE.md，让 AI 自动遵守（详见 Ch5）
  示例规则："始终用 @ 引用文件，不要复制文件内容到对话中"

### Ch5：开发规范（AI Rules Files）

**核心问题**：AI 没有真正的记忆——如何让它始终记住你的规矩？

**概念**
- AI 助手的本质：每次对话从零开始，规则文件是"外置记忆"
- 规则文件生态：CLAUDE.md（全局/项目级）、.cursor/rules/、.github/copilot-instructions.md
- 两类内容：
  - **技术约定**：技术栈、架构原则、目录结构
  - **AI 行为约束**：禁止过度设计、必须写测试、禁止改动无关代码

**案例**
- 从零搭建项目级 CLAUDE.md：
  1. 一句话让 AI 生成初版
  2. 多轮追问完善：技术栈补充、安全要求、编码风格
- 对比展示：有/无 CLAUDE.md 时 AI 产出的差异

**要点**
- 好规范的标准：约束具体可验证（"使用 FastAPI" vs "用主流框架"）
- 定期维护：发现 AI 违反规范时立即更新文件
- 规范文件解决的是"AI 记住规则"的问题；如果面对的是系统级开发，需要更结构化的规范方法——这就是 SDD（详见 Ch6）

### Ch6：SDD 方法论（规范驱动开发）

**核心问题**：为什么"直接让 AI 写代码"总是翻车？系统开发该怎么做？

**概念**
- Vibe Coding 的问题：决策权甩给 AI → 需求不清、架构混乱、反复返工
- SDD 核心理念：规范先行、人决策 AI 执行、规范是"单一真相源"
- SDD 流程：定义规范 → 审查规范 → 实现代码 → 归档

**案例**
- 对比演示：Vibe Coding vs SDD 处理同一个需求的结果差异
- 展示规范文档的三层结构，以"添加用户登录功能"为例：
  - **需求层**（做什么）：支持邮箱+密码登录；不支持第三方 OAuth（超出本期范围）
  - **设计层**（怎么做）：使用 JWT，token 有效期 7 天；密码用 bcrypt hash 存储
  - **任务层**（分几步）：① 建 users 表 ② 实现注册接口 ③ 实现登录接口 ④ 添加鉴权中间件

**即时练习**（无需任何工具）
用任意文本编辑器，为一个你熟悉的功能手写三层文档：
- 需求层：这个功能做什么、不做什么（非目标同样重要）
- 设计层：至少写出两个关键技术决策及其理由
- 任务层：拆成可独立执行的 3-5 个步骤

目标：在接触任何 SDD 工具之前，先建立"写规范比写代码优先"的肌肉记忆。

**要点**
- 判断依据：何时该用 SDD，何时不必（生产项目 vs 一次性脚本）
- 规范审查清单：需求文档是否说明了"非目标"？设计文档是否有可验证的决策？
- SDD 与工具无关：规范文档可以是任意格式，工具只是辅助生成（详见 Ch9）

### Ch7：SKILL（可复用提示词）

**核心问题**：好的提示词每次都要重新写——如何固化为资产？

**概念**
- **SKILL 的本质是 prompt**：一个 Markdown 文件，存在 `.claude/commands/` 下
- 用户级（`~/.claude/commands/`）vs 项目级（`.claude/commands/`）
- 斜杠命令触发：`/skill-name`
- 两个关键机制：
  - **`$ARGUMENTS`**：让 Skill 接受参数，变成可复用的"函数"；例如 `/code-review src/auth.py` 中 `src/auth.py` 即为 `$ARGUMENTS`
  - **`!` 前缀**：在 Skill 内嵌入 bash 命令（`! git status`），让 Skill 可以读取文件内容、运行脚本，用于需要获取上下文信息的场景
- Anthropic 官方 skills 仓库：现成 Skill 可直接复用

**案例**
从零创建 `/code-review` Skill，并演示参数化改造：
1. 写静态 prompt → 保存为 `.claude/commands/code-review.md` → 测试：只能审查当前文件
2. 加入 `$ARGUMENTS` → 重新测试：`/code-review src/auth.py` 可指定任意文件
3. 展示前后对比：临时写提示词 vs `/code-review src/auth.py` 的效率差异

**要点**
- 好 Skill 的标准：单一职责、上下文充分、输出格式明确
- Skill 与 CLAUDE.md 的关系：规范（Ch5）约束 Skill 的行为
- Skill 是 MCP 之前的"能力扩展"手段：不需要连接外部系统，只靠提示词就能标准化复杂任务（MCP 详见 Ch8）

### Ch8：MCP（模型上下文协议）

**核心问题**：AI 只会"说话"——如何让它真正"动手"操作外部系统？

**概念**
- AI 的默认能力边界：生成文本，无法访问外部数据
- MCP 是什么：让 AI 连接外部工具的标准协议（2024.11 发布）
- 类比：插件系统；装了 MCP 的 AI vs 没装 MCP 的 AI

**案例**
主案例：安装 **fetch MCP**，让 AI 真正"上网"（无需额外环境，所有读者可跟做）
1. 没有 fetch MCP 时：问 AI "帮我总结 https://example.com 的内容" → AI 拒绝，说无法访问网络
2. 和 Agent 对话，让 Agent 自动配置 fetch MCP（Claude Code：`claude mcp add`；Claude Desktop：写入 `~/.claude/claude_desktop_config.json`）
3. 重启后演示：同一问题 → AI 实时抓取页面并返回摘要

进阶示例（供参考）：MySQL MCP 让 AI 直接查询数据库
- 适合已有本地 MySQL 的读者；其余读者跳过不影响理解
- 演示：直接问"users 表有多少条记录"，AI 返回真实数据

**要点**
- 安全边界：数据库类 MCP 只开读权限到开发库，不暴露生产环境
- 适用场景：调试、数据分析、信息检索；不适用：生产环境写操作
- MCP vs SKILL（Ch7）：SKILL 扩展 AI 的"思维方式"，MCP 扩展 AI 的"行动能力"
- MCP 是让 Agent（Ch3）能力边界扩展的关键机制：装了什么 MCP，Agent 就能操作什么系统

### Ch9：SDD 工具实战

**核心问题**：有了 SDD 方法论，如何用工具真正落地实践？

**概念**

SDD 工具生态科普：

| 工具 | 出品方 | 方式 | 特点 |
|------|--------|------|------|
| GitHub Spec Kit | GitHub 官方 | 斜杠命令（`/speckit.specify` 等） | 轻量，搭配现有 AI 助手使用 |
| OpenSpec | 开源社区 | 斜杠命令（`/opsx-propose/apply/archive`） | 工件驱动，结构清晰，基于 SKILL 实现 |
| Kiro | AWS | 图形界面 | 可视化工作流，IDE 集成；2025 年发布，目前为预览版 |

**案例：用 OpenSpec 完整走一遍 SDD 流程**

OpenSpec 是什么：开源社区打造的 SDD 工具，本质是三个 Skill（`.md` 文件）：
- `/opsx-propose`：定义变更，AI 生成需求、设计、任务三份文档
- `/opsx-apply`：按任务逐条实现代码，完成一条打勾一条
- `/opsx-archive`：归档完成的变更，清理工作目录
工件驱动：每个阶段有明确的文档产出，不依赖对话记忆

案例演示（以"为博客系统添加评论功能"为例）：
1. `/opsx-propose`：AI 生成需求文档（为什么）+ 设计文档（如何）+ 任务清单（步骤）
2. **人工审查设计文档**：确认关键设计决策（评论是否支持嵌套？是否需要审核机制？）
3. `/opsx-apply`：AI 逐条实现任务清单中的任务，完成打勾
4. `/opsx-archive`：归档，清理工作目录

重点展示第2步"人工审查"：这是 SDD 与 Vibe Coding 的核心区别。

**要点**
- 工具选择原则：小团队/个人用 OpenSpec 或 Spec Kit，偏好可视化用 Kiro
- 观察：`/opsx-propose` 等命令与 Ch7 创建的 `/code-review` 是同一种机制——都是 `.md` 文件驱动的 Skill
- 延伸：参考 OpenSpec 的结构，可以创建符合自己项目需求的 SDD 工作流 Skill
