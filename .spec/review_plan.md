# 全书 Review 计划

## 评审角色与关注维度

### 角色 A：AI 编程专家
**关注**：技术准确性、示例可用性、概念时效性

检查项：
- 技术术语使用是否准确（MCP、Token、Agent、SKILL 等）
- 代码示例是否实际可运行、无语法错误
- 工具版本信息是否过时（Claude Code、Pydantic v2、FastAPI 等）
- 最佳实践是否符合行业主流
- 跨章引用的内容是否**准确**（如"详见 Ch5"，Ch5 是否真的讲该内容）

### 角色 B：目标学员（有编程基础，AI 工具新手）
**关注**：可读性、可学性、练习可达性

检查项：
- 核心概念在首次出现时是否有清晰解释
- 类比和例子是否能快速建立直觉
- 每章的学习曲线是否平缓（是否突然出现未铺垫的概念）
- 练习题是否明确、可操作、不依赖外部条件
- 读完是否清楚"我学到了什么、我能用它做什么"
- 是否有明显遗漏的知识点（学员读完后仍会困惑的常见问题）

### 角色 C：培训讲师
**关注**：模块独立性、课堂可操作性

检查项：
- 每章是否可作为独立培训模块使用（不强依赖其他章节）
- 章末练习是否可作为课堂任务直接使用（无需额外备课）
- 引言目标与实际内容是否匹配
- 小结是否能帮学员快速复盘本章核心

### 角色 D：技术编辑
**关注**：一致性、格式规范、无冗余

检查项：
- 术语一致性（3C/Context/Command/Constraint，SKILL vs Skill，等）
- 没有遗留的旧术语（CRC、Requirement、Constitution 等）
- 章节编号与文件名是否对应
- 跨章引用**格式**统一（Ch3、Ch5 等，不混用"第三章"）
- 各章结构是否遵循模板（N.1 引言 → 核心概念 → 案例 → 要点 → 小结）
- 练习题格式一致

## 评审输出格式

每批次产出一份报告，格式如下（只记录有发现的角色，无问题则略去该角色）：

```
## 文件：[文件名]

### 角色 X 发现
- 🔴/🟡/🟢 [问题描述] → [修改建议]
```

严重级别：
- 🔴 必改：影响准确性或可学性
- 🟡 建议：影响流畅度或一致性
- 🟢 可选：细节优化

---

## 执行方式

逐批次执行，每批次：
1. 精读该批次所有文件
2. 按四个角色维度逐一分析
3. 输出评审报告到 `.spec/reviews/report_[报告文件名]`
4. 修复 🔴 问题，由用户确认 🟡 问题
