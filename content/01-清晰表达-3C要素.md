# 第一章：清晰表达 - 3C 要素

## 1.1 引言

**本章目标**：掌握向 AI 清晰表达的方法——3C 要素。

AI 的输出质量直接取决于你的输入质量。它就像一个能力极强但对你的项目一无所知的外部专家，你必须主动提供充足的背景和明确的指令。

3C 要素正是为此设计的通用结构化表达方法，适用于从日常沟通到复杂编程的任何对话场景。学完本章，你将能快速组织高质量的提示词，显著提升 AI 的输出准确率。本章案例将先从通用场景切入，并在各节末尾提供编程对照。

---

## 1.2 3C 要素

3C 是三个英文单词的缩写：

- **C - Context（背景）**：你是谁？在做什么？背景是什么？
- **C - Command（指令）**：你要 AI 做什么？
- **C - Constraint（约束）**：有什么限制条件？不能做什么？

---

### C - Context（背景）

背景是 AI 理解你指令所必需的上下文信息。提供清晰的背景，能帮助 AI 快速缩小搜索范围，提高答复的精准度。

想象你去看医生。如果没有背景直接说"我肚子疼"，医生只能盲目排查；如果补充了"右下腹疼、昨晚吃过火锅、有胃溃疡病史"，医生就能迅速精准诊断。和 AI 对话同理，你给的背景越清晰，AI 的回答越精准。

**背景应该包含哪些信息？**

| 信息类型 | 说明 | 示例 |
|---------|------|------|
| 身份角色 | 你是谁，在做什么 | "我是一名架构师" |
| 背景情况 | 事情的来龙去脉 | "公司正在进行微服务改造" |
| 已有条件 | 手头有什么资源或信息 | "已有数据库模型设计" |
| 目标受众 | 结果给谁看或谁用 | "供前端开发调用的接口" |

#### 编程场景对照

```text
我在开发一个基于 FastAPI 的待办事项 API，使用 PostgreSQL 16 存储数据。
用户认证采用 JWT Token，现在需要写一个用户验证函数。
```

---

### C - Command（指令）

指令描述了你要 AI 具体完成的任务。提示词失效的核心原因往往是指令过于模糊。

这就像去餐厅点餐。如果你只说"来一碗面"，服务员端来的未必合你口味；但如果说"牛肉面，少辣，加煎蛋，面偏硬"，你就能一次得到满意的结果。指令越具体，AI 的输出越符合预期。

**一个好指令应回答以下问题：**

| 要素 | 说明 | 示例 |
|------|------|------|
| 做什么 | 具体的任务描述 | "写一个用户注册接口" |
| 包含什么 | 需要涵盖的内容 | "包含参数校验和密码哈希逻辑" |
| 输出形式 | 用什么形式呈现 | "直接输出完整的 Python 代码" |
| 关键细节 | 不能遗漏的要点 | "校验邮箱格式的合法性" |

#### 编程场景对照

```text
写一个 FastAPI 的依赖注入函数，功能是：
- 从请求的 Authorization Header 中提取 JWT Token
- 解码并验证 Token 是否有效、是否过期
- 验证通过返回 UUID 类型的 user_id
- 验证失败抛出 HTTPException 异常
```

---

### C - Constraint（约束）

约束是限制条件，用来划定 AI 的执行边界。指令告诉 AI 目的地，约束则规定了路线和规则。

找装修公司时，如果只提"装修三居室"，结果可能是严重超支的豪华风。但加上"预算 10 万内、现代简约、承重墙不能动"这些约束后，方案才会切实可行。没有约束，AI 往往会采用它认为最通用的处理方式，而非你实际需要的。

**常见约束类型：**

| 约束类型 | 说明 | 示例 |
|---------|------|------|
| 资源约束 | 依赖库限制 | "仅使用 FastAPI 内置功能" |
| 风格约束 | 代码规范 | "严格遵循 PEP 8 规范" |
| 格式约束 | 异常处理要求 | "验证失败统一返回 422 Unprocessable Entity" |
| 排除约束 | 明确排除不想要的 | "不要使用正则表达式解析 JSON" |

#### 编程场景对照

```text
约束：
- 使用 python-jose 库处理 JWT
- 包含完整的 Python 类型注解
- 验证失败统一抛出带有 401 Unauthorized 状态码的异常
- 不要过度封装，保持函数简单独立
```

## 1.3 实战案例与常见错误

### 案例 1：完整 3C 表达示范

在编程场景中构建一个数据校验模型的提示词示范：

```text
## Context
我在开发一个 Todo API，使用 Python 3.11 和 Pydantic v2。
待办事项包含 title、description、priority 和 due_date 字段。

## Command
写一个 Pydantic 模型用于校验创建待办事项的请求数据：
- title 必填，长度 1-100 个字符
- description 可选，最大 500 个字符
- priority 必填，仅限 high、medium、low
- due_date 可选，必须为未来日期

## Constraint
- 校验失败时统一返回 422 Unprocessable Entity 状态码
- 必须包含完整的类型注解
```

### 案例 2：常见错误示范

很多初学者在编写提示词时容易犯以下错误：

**错误 1：完全没有背景与约束（模糊提问）**
> **你**：帮我写一个用户验证函数。

这类提问会导致 AI 盲目猜测，输出完全不符合你实际项目技术栈的代码。

**错误 2：提供无效的背景噪音**
> **你**：我是一个 35 岁的程序员，已婚，最近在学 Rust。帮我写一个 Python 用户验证函数。

与任务无关的背景信息会分散 AI 的注意力，背景必须紧扣当前目标任务。

**错误 3：指令和约束混合且自相矛盾**
> **你**：控制在 20 行代码内，同时必须包含数据库连接池、日志记录、错误重试和全部数据校验。

这会让 AI 陷入逻辑瘫痪。必须确保约束条件的合理性与一致性。

## 1.4 实操要点

日常使用时，可以直接套用以下 3C 模板：

```text
## Context
[你的背景、情况、已有条件]

## Command
[具体要做什么、包含什么内容、输出形式]

## Constraint
[限制条件、风格要求、格式要求]
```

**何时可以简化 3C？**
对于简单知识问答，可以直接提问。如果在多轮对话的上下文中追问，通常只需补充 Command。要素齐全比严格按顺序排列更重要，AI 对你的背景了解越少，3C 越需要完整。

## 1.5 练习题

### 练习 1：改写模糊指令

将以下模糊指令改写为结构化的 3C 格式：
> **你**：帮我写一个接口。

### 练习 2：为真实任务编写 3C

选择你当前项目的一个真实开发任务，用 3C 格式写一段提示词发给 AI。**将提示词和 AI 回复保存为文件**，培训时与同组对比效果差异。

### 参考思路

**练习 1 参考思路**：
Context 补充使用的框架、数据库等已有条件；Command 明确接口的具体功能（路由路径、请求/响应格式）；Constraint 设定限制（如状态码规范、是否需要认证）。参考答案不唯一，重点是每个要素都有实质内容。

**练习 2 参考思路**：
带有完整 3C 的提示词通常能让 AI 在首次输出就达到高度可用的状态，大幅减少后续反复修改的成本。

---

## 1.6 本章小结

**核心要点回顾：**

- **Context（背景）**：交代背景和已有条件。
- **Command（指令）**：明确具体任务和输出形式。
- **Constraint（约束）**：设定边界、风格与格式限制。
- 结构化表达是驾驭 AI 的基本功，AI 的输出质量直接取决于你的输入质量。
