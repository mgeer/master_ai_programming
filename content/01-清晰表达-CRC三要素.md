# 第一章：清晰表达 - CRC 三要素

## 1.1 引言

**本章目标**：掌握向 AI 清晰表达需求的方法——CRC 三要素。

很多人第一次用 AI 写代码，体验大概是这样的：

> "帮我写一个登录功能"
>
> AI 输出了一堆代码……但用的框架不对、数据库不对、连语言都不是你想要的。

然后得出结论："AI 不行，写的东西不能用。"

**真相是：AI 的输出质量，取决于你的输入质量。**

同样一个 AI 模型，有人能让它写出生产级代码，有人只能得到一段跑不起来的 demo。差别不在 AI，在于**你怎么说**。

这就像和一个**技术能力远超你、但对你的项目一无所知**的同事协作。他什么都能写，但需要你告诉他写什么。和普通新同事不同的是，他不会主动观察项目、翻阅文档、理解上下文——**你说了什么，他就知道什么；你没说的，他只能猜。**

CRC 三要素就是解决这个问题的方法：**用结构化的方式，把事情说清楚。**

学完本章，你可以：
- 在任何一次 AI 对话中，快速组织出高质量的提示词
- 明显减少"AI 输出不符合预期"的情况
- 养成结构化表达的习惯，这个能力不仅对 AI 有用，对日常沟通同样有效

**一点提醒**：本章的案例会展示"写到位"的 CRC，看起来内容不少。别担心——这是为了让你完整地看到好的需求表达该覆盖哪些信息。实际使用中，你不需要一次写到这个程度。先把想到的写出来，写不到位的地方可以通过对话来补（第二章会讲）。本章的目标是让你**具备判断力**——知道什么信息该给、什么时候给得不够——而不是背模板。

## 1.2 CRC 三要素

CRC 是三个英文单词的缩写：

- **C - Context（上下文）**：你是谁？在做什么？背景是什么？
- **R - Requirement（需求）**：你要 AI 做什么？
- **C - Constraint（约束）**：有什么限制条件？不能做什么？

一个好的提示词，就是把这三件事说清楚。

---

### C - Context（上下文）

**什么是上下文？**

上下文就是 AI 理解你需求所需要的**背景信息**。没有上下文，AI 只能猜，猜对是运气，猜错是常态。

**上下文应该包含哪些信息？**

不需要每次都面面俱到，但以下信息越明确，AI 输出越精准：

| 信息类型 | 说明 | 示例 |
|---------|------|------|
| 项目背景 | 你在做什么项目 | "一个待办事项管理系统" |
| 技术栈 | 用什么语言、框架 | "Python + FastAPI + PostgreSQL" |
| 你的角色 | 你在项目中的职责 | "后端开发" |
| 已有条件 | 现有代码、数据结构、接口 | "已有 User 模型，使用 SQLAlchemy" |
| 目标受众 | 代码给谁用 | "团队内部工具" |

**案例对比：无上下文 vs 有上下文**

❌ **无上下文**：
```
帮我写一个用户验证函数
```

AI 不知道：用什么语言？验证什么？密码？Token？邮箱格式？用什么框架？输出可能是任何语言、任何场景的代码。

✅ **有上下文**：
```
我在开发一个基于 FastAPI 的待办事项 API，使用 PostgreSQL 存储数据，
用户认证采用 JWT Token。现在需要写一个用户验证函数。
```

AI 立刻知道：Python、FastAPI、JWT、PostgreSQL——输出会精准得多。

---

### R - Requirement（需求）

**如何清晰描述"你要什么"？**

需求是提示词的核心。很多人的问题不是"没说需求"，而是**需求太模糊**。

一个好需求应该回答以下问题：

| 要素 | 说明 | 示例 |
|------|------|------|
| 做什么 | 具体的功能描述 | "验证 JWT Token 是否有效" |
| 输入 | 函数/接口接收什么 | "接收 HTTP Header 中的 Authorization 字段" |
| 输出 | 返回什么结果 | "返回 user_id；Token 无效时抛出 401 异常" |
| 行为 | 关键的业务逻辑 | "需要检查 Token 是否过期" |

**案例对比：模糊需求 vs 精确需求**

❌ **模糊需求**：
```
帮我写一个验证函数
```

"验证"什么？验证邮箱格式？验证密码强度？验证 Token？AI 只能猜。

✅ **精确需求**：
```
写一个 FastAPI 的依赖注入函数，功能是：
- 从请求的 Authorization Header 中提取 JWT Token
- 解码并验证 Token 是否有效、是否过期
- 验证通过返回 user_id
- 验证失败抛出 HTTPException（401）
```

需求越具体，AI 输出越接近你的预期。

---

### C - Constraint（约束）

**什么是约束？**

约束就是**限制条件**——告诉 AI "不能做什么"或"必须怎么做"。需求告诉 AI 目的地，约束告诉 AI 路线和规则。

**为什么约束很重要？**

没有约束，AI 会按照它认为"最通用"的方式输出。但"通用"往往不是你想要的。比如你要一个简单的工具函数，AI 可能给你一个过度设计的类层级结构。

**常见约束类型：**

| 约束类型 | 说明 | 示例 |
|---------|------|------|
| 技术约束 | 必须使用或不能使用的技术 | "使用 PyJWT 库，不要用 python-jose" |
| 质量约束 | 代码质量要求 | "包含完整的类型注解和 docstring" |
| 格式约束 | 输出格式要求 | "只返回代码，不需要解释" |
| 排除约束 | 明确排除不想要的东西 | "不要使用全局变量" |
| 性能约束 | 性能方面的要求 | "时间复杂度不超过 O(n)" |
| 风格约束 | 编码风格要求 | "遵循 PEP 8 规范" |

**案例对比：无约束 vs 有约束**

❌ **无约束**：
```
写一个 JWT 验证函数
```

AI 可能随便选一个 JWT 库，可能不写类型注解，可能不处理异常，可能过度封装。

✅ **有约束**：
```
约束：
- 使用 PyJWT 库
- 包含完整的类型注解
- 异常处理要明确区分：Token 过期、Token 无效、Token 缺失
- 遵循 PEP 8 规范
- 不要过度封装，保持简单
```

约束越明确，AI 越不会"自由发挥"。

## 1.3 实战案例

### 案例 1（Python）：数据校验函数

**场景**：你需要一个函数，校验用户提交的待办事项数据是否合法。

#### 反面：一句话需求

```
帮我写一个校验待办事项的函数
```

AI 的典型输出：

```javascript
// AI 用了 JavaScript（语言都不对）
function validateTodo(todo) {
  if (!todo.title) {
    return false;  // 只检查了标题，其他字段完全没管
  }
  return true;
}
```

问题很明显：语言错了、校验逻辑不完整、没有错误提示、没有类型信息。

#### 正面：CRC 结构化表达

```
## Context
我在开发一个待办事项 API，使用 Python + FastAPI + Pydantic。
待办事项的数据结构包含：title（标题）、description（描述）、
priority（优先级：high/medium/low）、due_date（截止日期）。

## Requirement
写一个 Pydantic 模型，用于校验创建待办事项的请求数据：
- title 必填，长度 1-100 个字符
- description 可选，最大 500 个字符
- priority 必填，只能是 high、medium、low 三个值之一
- due_date 可选，但如果提供，必须是未来的日期

## Constraint
- 使用 Pydantic v2 语法
- 校验失败时返回清晰的中文错误提示
- 包含完整的类型注解
```

AI 的输出：

```python
from datetime import date
from enum import Enum
from typing import Optional
from pydantic import BaseModel, Field, field_validator


class Priority(str, Enum):
    high = "high"
    medium = "medium"
    low = "low"


class CreateTodoRequest(BaseModel):
    title: str = Field(..., min_length=1, max_length=100, description="待办事项标题")
    description: Optional[str] = Field(None, max_length=500, description="详细描述")
    priority: Priority = Field(..., description="优先级")
    due_date: Optional[date] = Field(None, description="截止日期")

    @field_validator("due_date")
    @classmethod
    def due_date_must_be_future(cls, v: Optional[date]) -> Optional[date]:
        if v is not None and v <= date.today():
            raise ValueError("截止日期必须是未来的日期")
        return v
```

语言对、框架对、校验规则完整、有类型注解、有中文错误提示——**CRC 的效果一目了然。**

### 案例 2（Vue）：表单组件

**场景**：你需要一个创建待办事项的表单组件。

#### 反面：一句话需求

```
帮我写一个待办事项的表单
```

AI 可能给你一个原生 HTML 表单，没有校验、没有组件化、用 Options API 写的、样式也不对。你需要反复追问修改，浪费好几轮对话。

#### 正面：CRC 结构化表达

```
## Context
我在开发待办事项管理系统的前端，使用 Vue 3 + Composition API + TypeScript。
UI 框架使用 Element Plus。后端 API 接口为 POST /api/todos，
请求体为 { title, description, priority, due_date }。

## Requirement
创建一个"新建待办事项"的表单组件 CreateTodoForm.vue：
- 包含 title 输入框（必填）
- 包含 description 文本域（可选）
- 包含 priority 下拉选择器（high/medium/low）
- 包含 due_date 日期选择器（可选，只能选未来日期）
- 提交按钮，点击后调用后端 API
- 提交成功后清空表单并触发 created 事件

## Constraint
- 使用 <script setup> 语法
- 表单校验使用 Element Plus 的表单校验机制
- 不使用 any 类型
- 组件只负责表单逻辑，不包含页面布局
```

### 案例 3：常见错误示范

**错误 1：上下文过多（信息噪音）**

```
我们公司成立于 2015 年，是一家做高精定位的科技公司，
团队有 200 人，其中研发 100 人，我在基础架构组，
组里有 8 个人，我们最近在做技术升级，老系统用的是 Java，
新系统准备用 Python，我之前写了 5 年 Java……

帮我写一个 Hello World。
```

**问题**：大量无关信息干扰 AI 理解你的真实意图。上下文要**相关且精简**，不是写自传。

**错误 2：需求和约束混在一起**

```
帮我写一个函数，要用 Python，要有类型注解，
校验用户输入，要处理异常，用 PEP 8 风格。
```

**问题**：现在的 AI 模型其实能理解这段话。但混着写的坏处不在于 AI 看不懂，而在于**你自己容易遗漏**。"校验用户输入"是核心需求，其他都是约束——当你把它们分开写的时候，你会发现需求部分太模糊了：校验什么输入？哪些字段？什么规则？**CRC 是帮你理清思路的工具，不只是格式要求。**

**错误 3：约束相互矛盾**

```
## Constraint
- 代码要简洁，不超过 20 行
- 要包含完整的异常处理、日志记录、重试机制和详细注释
```

**问题**：20 行代码不可能同时包含这么多内容。自相矛盾的约束会让 AI 输出质量下降。

## 1.4 实操要点

### CRC 提示词模板

日常使用时，可以直接套用以下模板：

```
## Context
[项目背景、技术栈、已有条件]

## Requirement
[具体要做什么、输入输出、预期行为]

## Constraint
[技术限制、质量要求、格式要求]
```

### 什么时候可以简化 CRC？

**不是每次都要写完整的 CRC。** 根据任务复杂度灵活调整：

| 场景 | 建议 |
|------|------|
| 简单语法问题（如"Python 如何反转列表"） | 不需要 CRC，直接问 |
| 解释一段代码的含义 | 不需要 CRC，直接贴代码 |
| 在已有对话上下文中追问 | 只需要补充 R 和 C |
| 开始一个新的编码任务 | 先写粗略 CRC，对话中逐步补充 |
| 处理复杂业务逻辑 | 先写粗略 CRC，对话中逐步补充 |

**原则：AI 对你的情况了解越少，CRC 就越要写完整。**

**粗略 CRC 就够启动一次有效对话**

以案例 1 为例，实际使用中写成这样就够了：

```
Python + FastAPI 项目，写一个 Pydantic v2 模型校验创建待办事项的请求。
字段：title（必填，1-100字符）、description（可选）、priority（high/medium/low）、due_date（可选，须为未来日期）。
校验失败返回中文提示。
```

三行，CRC 三要素都有（Context：技术栈；Requirement：要做什么、字段规则；Constraint：Pydantic v2、中文提示）。和前面的完整版比，少了一些细节，但足以让 AI 产出 80 分的代码。剩下的 20 分，看到 AI 输出后再补充调整就行。

**写 CRC 的心态应该是：把想到的写出来，想不到的通过对话补。不是一次写完美，而是给对话一个好的起点。**

### CRC 的顺序可以灵活调整

CRC 是**内容要素**，不是固定的书写顺序。实际使用中，很多人是先想到"我要做什么"（Requirement），再补充背景（Context）和限制（Constraint）。这完全没问题——**重要的是三个要素都覆盖到，而不是按什么顺序写。**

### 注意事项

1. **上下文不是越多越好**：只提供和当前任务相关的信息，无关信息是噪音
2. **需求要可验证**：写完需求后问自己"我能根据这段描述判断 AI 的输出是否正确吗？"
3. **约束要合理**：不要提出矛盾的约束，也不要约束过多导致 AI 无法满足
4. **迭代优化**：第一次写的 CRC 不一定完美，根据 AI 的输出调整你的表达

## 1.5 练习题

### 练习 1：改写模糊需求

将以下模糊需求改写为 CRC 格式：

> "帮我写一个分页查询的接口"

提示：思考一下——什么项目？查询什么数据？分页参数有哪些？返回什么格式？有什么技术限制？

### 练习 2：诊断以下 CRC 的问题

阅读以下提示词，找出其中的问题并改进：

```
## Context
我们团队用 Python 开发后端服务。

## Requirement
写一个处理数据的函数。

## Constraint
- 代码要高质量
- 性能要好
- 要简洁，不超过 10 行
- 要包含完整的错误处理、重试机制、日志记录和详细注释
```

提示：从三个维度思考——Context 够不够？Requirement 够不够具体？Constraint 之间有没有矛盾？

### 练习 3：为实际开发任务编写 CRC

选择你最近工作中的一个真实开发任务（如修复一个 bug、添加一个小功能），用 CRC 格式写一段提示词，然后发给 AI，看看输出效果。

对比一下：和你平时随意提问相比，输出质量有什么差异？

## 1.6 本章小结

**核心要点回顾：**

- **C - Context**：告诉 AI 你的背景（项目、技术栈、已有条件）
- **R - Requirement**：告诉 AI 你要什么（功能、输入输出、行为）
- **C - Constraint**：告诉 AI 限制条件（技术、质量、格式、排除）
- CRC 不是教条，简单问题可以简化，复杂任务要写完整
- AI 输出质量 = 你的输入质量，结构化表达是基本功
