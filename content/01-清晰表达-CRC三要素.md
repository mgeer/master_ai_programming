# 第一章：清晰表达 - CRC 三要素

## 1.1 引言

**本章目标**：掌握向 AI 清晰表达需求的方法——CRC 三要素。

> CRC 是通用的 AI 沟通方法，适用于任何场景——无论你是用 AI 写文章、做分析、策划活动，还是写代码，背后的核心都是把上下文、需求、约束说清楚。本章用日常通用场景演示 CRC 的思路，每节末尾附编程场景对照，方便程序员读者迁移到编程实战中。

很多人第一次用 AI，体验大概是这样的：

> "帮我写一篇关于人工智能的文章"
>
> AI 洋洋洒洒写了两千字……但内容太浅、风格太学术、篇幅也不对，完全不是你想要的。

然后得出结论："AI 写的东西太泛了，不能用。"

**真相是：AI 的输出质量，取决于你的输入质量。**

同样一个 AI 模型，有人能让它产出让客户眼前一亮的方案，有人只能得到一篇泛泛而谈的废话。差别不在 AI，在于**你怎么说**。

这就像去找一个**能力很强、但对你的情况一无所知**的顾问。他什么都能做，但需要你告诉他做什么。和你身边的同事不同，他不了解你的背景、你的偏好、你的限制——**你说了什么，他就知道什么；你没说的，他只能猜。**

CRC 三要素就是解决这个问题的方法：**用结构化的方式，把事情说清楚。**

学完本章，你可以：
- 在任何一次 AI 对话中，快速组织出高质量的提示词
- 明显减少"AI 输出不符合预期"的情况
- 养成结构化表达的习惯，这个能力不仅对 AI 有用，对日常沟通同样有效

**一点提醒**：本章的案例会展示"写到位"的 CRC，看起来内容不少。别担心——这是为了让你完整地看到好的需求表达该覆盖哪些信息。实际使用中，你不需要一次写到这个程度。先把想到的写出来，写不到位的地方可以通过对话来补（第二章会讲）。本章的目标是让你**具备判断力**——知道什么信息该给、什么时候给得不够——而不是背模板。

> 本书后续章节会聚焦到编程场景，把 CRC 和多轮对话技巧应用到软件开发的完整流程中。但请记住，CRC 本身是通用的——你在任何 AI 对话中都用得上。

---

## 1.2 CRC 三要素

CRC 是三个英文单词的缩写：

- **C - Context（上下文）**：你是谁？在做什么？背景是什么？
- **R - Requirement（需求）**：你要 AI 做什么？
- **C - Constraint（约束）**：有什么限制条件？不能做什么？

一个好的提示词，就是把这三件事说清楚。

> 你可能注意到 CRC 有两个 C。为了避免混淆，后文在需要单独引用时会使用全称（Context / Constraint），而不是缩写字母。

---

### C - Context（上下文）

**什么是上下文？**

上下文就是 AI 理解你需求所需要的**背景信息**。没有上下文，AI 只能猜，猜对是运气，猜错是常态。

想象你去看医生。

❌ **没有上下文**：

> "医生，我肚子疼。"

医生一脸问号：疼了多久？哪个位置？之前吃了什么？有没有慢性病？他只能从最常见的情况开始排查，效率很低，甚至可能误判。

✅ **有上下文**：

> "医生，我肚子疼，右下腹，从昨晚开始的。我有胃溃疡病史，昨天吃了火锅，今早开始发低烧。"

医生立刻能缩小范围：有病史参考、有症状时间线、有伴随症状——诊断精准得多。

和 AI 对话也是一样。**你给的背景越清楚，AI 的回答越精准。**

**上下文应该包含哪些信息？**

不需要每次都面面俱到，但以下信息越明确，AI 输出越精准：

| 信息类型 | 说明 | 示例 |
|---------|------|------|
| 你的身份/角色 | 你是谁，在做什么 | "我是一名市场经理" |
| 背景情况 | 事情的来龙去脉 | "公司下个月要发布新产品" |
| 已有条件 | 手头有什么资源或信息 | "已有产品功能清单和竞品分析" |
| 目标受众 | 结果给谁看/谁用 | "给公司高管做汇报" |

**案例对比：无上下文 vs 有上下文**

❌ **无上下文**：
```
帮我写一封邀请邮件
```

AI 不知道：邀请谁？什么活动？什么语气？多正式？输出可能是婚礼请柬，也可能是会议通知——完全靠猜。

✅ **有上下文**：
```
我是一家科技创业公司的市场经理，下个月公司要举办产品发布会。
我需要写一封邮件邀请行业媒体记者参加。
```

AI 立刻知道：商务场景、科技行业、面向媒体、发布会邀请——输出会靠谱得多。

#### 编程场景对照

同样的道理应用到编程中：

❌ **无上下文**：
```
帮我写一个用户验证函数
```

AI 不知道：用什么语言？验证什么？密码？Token？邮箱格式？用什么框架？输出可能是任何语言、任何场景的代码。

✅ **有上下文**：
```
我在开发一个基于 FastAPI 的待办事项 API，使用 PostgreSQL 存储数据，
用户认证采用 JWT Token。现在需要写一个用户验证函数。
```

AI 立刻知道：Python、FastAPI、JWT、PostgreSQL——输出会精准得多。编程中的上下文通常包括项目背景、技术栈、已有代码结构等。

---

### R - Requirement（需求）

**如何清晰描述"你要什么"？**

需求是提示词的核心。很多人的问题不是"没说需求"，而是**需求太模糊**。

想象你去餐厅点餐。

❌ **模糊需求**：

> "来一碗面。"

服务员只能随便给你上一碗——可能是你不吃的牛肉面，可能辣得你怀疑人生，面还煮得稀烂。不是服务员不想做好，是你没说清楚。

✅ **精确需求**：

> "来一碗牛肉面，少辣，加一个煎蛋，面要硬一点。"

四个具体信息：品种、辣度、加料、面的软硬——服务员一次就能做对。

和 AI 对话一样，**需求越具体，输出越接近你的预期。**

一个好需求应该回答以下问题：

| 要素 | 说明 | 示例 |
|------|------|------|
| 做什么 | 具体的任务描述 | "写一份项目提案" |
| 包含什么 | 需要涵盖的内容 | "包含背景分析、目标、实施计划、预算" |
| 输出形式 | 用什么形式呈现 | "按 Word 文档的格式，分章节组织" |
| 关键细节 | 不能遗漏的要点 | "重点突出投资回报率分析" |

**案例对比：模糊需求 vs 精确需求**

❌ **模糊需求**：
```
帮我写一个活动方案
```

什么活动？什么目的？多少人？线上还是线下？AI 只能编一个泛泛的模板。

✅ **精确需求**：
```
帮我策划一场公司年会方案：
- 参与人数：约 200 人
- 形式：线下晚宴 + 表演 + 颁奖
- 需要包含：时间安排表、节目流程、场地布置建议、互动环节设计
- 年会主题要体现"科技创新"
```

需求越具体，AI 输出越接近你想要的效果。

#### 编程场景对照

同样的道理在编程中：

❌ **模糊需求**：
```
我需要一个验证功能，能验证用户的输入
```

"验证"什么？验证邮箱格式？验证密码强度？验证 Token？"用户的输入"是哪些字段？AI 只能猜。

✅ **精确需求**：
```
写一个 FastAPI 的依赖注入函数，功能是：
- 从请求的 Authorization Header 中提取 JWT Token
- 解码并验证 Token 是否有效、是否过期
- 验证通过返回 user_id
- 验证失败抛出 HTTPException（401）
```

编程中的需求通常需要明确：做什么功能、输入输出是什么、关键的业务逻辑有哪些。

---

### C - Constraint（约束）

**什么是约束？**

约束就是**限制条件**——告诉 AI "不能做什么"或"必须怎么做"。需求告诉 AI 目的地，约束告诉 AI 路线和规则。

想象你找装修公司装修新房。你说了需求（"帮我装修这套三居室"），但如果不给约束，装修公司可能花 50 万给你整一个欧式豪华风——这不是你想要的。

✅ **有约束的装修需求**：

> "帮我装修这套三居室。预算 10 万以内，现代简约风格，客厅要大面积留白。另外，厨房那面墙是承重墙，不能拆。"

三条关键约束：
- **预算约束**：10 万以内（不能超）
- **风格约束**：现代简约（不要欧式巴洛克）
- **物理约束**：承重墙不能动（硬性限制）

有了这些约束，装修公司才能在合理范围内给你靠谱的方案。AI 也是一样——**没有约束，AI 会按照它认为"最通用"的方式输出，而"通用"往往不是你想要的。**

**常见约束类型：**

| 约束类型 | 说明 | 示例 |
|---------|------|------|
| 资源约束 | 预算、时间等限制 | "预算不超过 5000 元" |
| 风格约束 | 调性、风格要求 | "语气正式但不死板" |
| 格式约束 | 输出格式要求 | "用表格形式呈现对比" |
| 排除约束 | 明确排除不想要的 | "不要用太专业的术语" |
| 篇幅约束 | 长度限制 | "控制在 500 字以内" |
| 受众约束 | 针对特定人群调整 | "面向非技术背景的管理层" |

**案例对比：无约束 vs 有约束**

❌ **无约束**：
```
帮我写一份市场分析报告
```

AI 可能写了一万字的学术论文，满是专业术语，老板看不懂。

✅ **有约束**：
```
约束：
- 控制在 2000 字以内
- 语言通俗易懂，面向非技术背景的管理层
- 用图表和数据说话，少写大段文字
- 重点分析国内市场，不需要覆盖海外
- 结论部分给出 3 条可执行的建议
```

约束越明确，AI 越不会"自由发挥"。

#### 编程场景对照

编程中的约束同样重要：

❌ **无约束**：
```
写一个 JWT 验证函数
```

AI 可能随便选一个 JWT 库，可能不写类型注解，可能不处理异常，可能过度封装。

✅ **有约束**：
```
约束：
- 使用 PyJWT 库
- 包含完整的类型注解
- 异常处理要明确区分：Token 过期、Token 无效、Token 缺失
- 遵循 PEP 8 规范
- 不要过度封装，保持简单
```

编程中常见的约束包括：技术约束（用什么库/框架）、质量约束（类型注解、测试覆盖）、性能约束（时间复杂度）、风格约束（代码规范）等。

## 1.3 实战案例

### 案例 1：让 AI 做一份旅行攻略

**场景**：你打算五一假期带家人去旅行，想让 AI 帮你做一份攻略。

#### 反面：一句话需求

```
帮我做一份旅行攻略
```

AI 的典型输出：一份泛泛的"十大热门旅游城市推荐"，或者一份不知道给谁看的通用行程模板——去哪、几天、几个人、预算多少，全是 AI 自己编的，大概率不是你想要的。

#### 正面：CRC 结构化表达

```
## Context
五一假期（5 天），我和妻子带 5 岁的孩子一起出行。
我们坐标北京，打算去云南（大理 + 丽江）。
之前没去过云南，孩子比较怕晒。

## Requirement
帮我做一份 5 天的旅行攻略：
- 每天的行程安排（景点、餐厅推荐、交通方式）
- 适合带小孩的景点优先
- 推荐当地必吃的美食
- 需要提前预订的项目列表

## Constraint
- 总预算控制在 1.5 万以内（含机票住宿）
- 每天步行不超过 1 万步（孩子走不了太远）
- 不安排高海拔徒步（孩子太小）
- 住宿选亲子友好型酒店
```

AI 的输出会完全不同：行程围绕亲子活动设计、预算合理分配、避开了不适合小孩的项目——**因为你把关键信息都告诉它了。**

#### 编程场景对照

同样的 CRC 结构用在编程任务上（以下是一个假设的 Todo 数据结构，用于演示 CRC 写法，和后续章节的正式规范可能不同）：

```
## Context
我在开发一个待办事项 API，使用 Python + FastAPI + Pydantic。
待办事项的数据结构包含：title（标题）、description（描述）、
priority（优先级：high/medium/low）、due_date（截止日期）。

## Requirement
写一个 Pydantic 模型，用于校验创建待办事项的请求数据：
- title 必填，长度 1-100 个字符
- description 可选，最大 500 个字符
- priority 必填，只能是 high、medium、low 三个值之一
- due_date 可选，但如果提供，必须是未来的日期

## Constraint
- 使用 Pydantic v2 语法
- 校验失败时返回清晰的中文错误提示
- 包含完整的类型注解
```

结构完全一样——Context 交代技术背景，Requirement 明确要做什么，Constraint 限定技术要求。CRC 在编程场景中同样好用。

### 案例 2：常见错误示范

**错误 1：上下文过多（信息噪音）**

```
我是一个 35 岁的程序员，已婚，有一个孩子，住在北京朝阳区，
平时喜欢跑步和看电影，最近在学钢琴，
去年去过日本觉得不错，前年去了泰国也挺好的，
我老婆是做设计的，孩子在上幼儿园中班……

帮我做一份五一旅行攻略。
```

**问题**：你的职业、爱好、去年的旅行、老婆的工作，这些信息和"做旅行攻略"基本无关。上下文要**和当前任务相关**——出行人数、孩子年龄、出发地有用，你的钢琴学习进度没用。

**错误 2：需求和约束混在一起**

```
帮我写一份报告，要正式一点，分析一下市场情况，
不要太长，最好有数据，面向管理层的。
```

**问题**：现在的 AI 模型其实能理解这段话。但混着写的坏处不在于 AI 看不懂，而在于**你自己容易遗漏**。"分析市场情况"是核心需求，其他都是约束——当你把它们分开写的时候，你会发现需求部分太模糊了：分析什么市场？什么行业？什么时间范围？和谁竞争？**CRC 是帮你理清思路的工具，不只是格式要求。**

**错误 3：约束相互矛盾**

```
## Constraint
- 内容要全面详尽，覆盖所有方面
- 篇幅控制在 300 字以内
```

**问题**：300 字不可能覆盖"所有方面"。自相矛盾的约束会让 AI 左右为难——要么超字数，要么内容太浅，怎么做都不对。

## 1.4 实操要点

### CRC 提示词模板

日常使用时，可以直接套用以下模板：

```
## Context
[你的背景、情况、已有条件]

## Requirement
[具体要做什么、包含什么内容、输出形式]

## Constraint
[限制条件、风格要求、格式要求]
```

### 什么时候可以简化 CRC？

**不是每次都要写完整的 CRC。** 根据任务复杂度灵活调整：

| 场景 | 建议 |
|------|------|
| 简单问题（如"什么是量子计算"） | 不需要 CRC，直接问 |
| 理解一段内容（如"帮我解释这段话"） | 不需要 CRC，直接贴内容 |
| 在已有对话上下文中追问 | 只需要补充 Requirement 和 Constraint |
| 开始一个新的复杂任务 | 先写粗略 CRC，对话中逐步补充 |

**原则：AI 对你的情况了解越少，CRC 就越要写完整。**

**粗略 CRC 就够启动一次有效对话**

以旅行攻略案例为例，实际使用中写成这样就够了：

```
五一 5 天假期，我和老婆带 5 岁孩子从北京去大理+丽江。
帮我做旅行攻略，要适合带小孩的行程，每天别走太多路。
总预算 1.5 万以内，不安排高海拔徒步。
```

三行，CRC 三要素都有（Context：谁去、从哪去、几天；Requirement：做攻略、适合小孩的行程；Constraint：预算、步行量、海拔限制）。和前面的完整版比，少了一些细节，但足以让 AI 产出 80 分的攻略。剩下的 20 分，看到 AI 输出后再补充调整就行。

**写 CRC 的心态应该是：把想到的写出来，想不到的通过对话补。不是一次写完美，而是给对话一个好的起点。**

### CRC 的顺序可以灵活调整

CRC 是**内容要素**，不是固定的书写顺序。实际使用中，很多人是先想到"我要做什么"（Requirement），再补充背景（Context）和限制（Constraint）。这完全没问题——**重要的是三个要素都覆盖到，而不是按什么顺序写。**

### 注意事项

1. **上下文不是越多越好**：只提供和当前任务相关的信息，无关信息是噪音
2. **需求要可验证**：写完需求后问自己"我能根据这段描述判断 AI 的输出是否符合预期吗？"
3. **约束要合理**：不要提出矛盾的约束，也不要约束过多导致 AI 无法满足
4. **迭代优化**：第一次写的 CRC 不一定完美，根据 AI 的输出调整你的表达

## 1.5 练习题

### 练习 1：改写模糊需求

将以下模糊需求改写为 CRC 格式：

> "帮我写一份简历"

提示：思考一下——你是什么岗位？几年经验？投什么公司？简历什么格式？有什么特别要强调或回避的？

### 练习 2：诊断以下 CRC 的问题

阅读以下提示词，找出其中的问题并改进：

```
## Context
我是一个上班族，最近比较忙。

## Requirement
帮我做一份工作计划。

## Constraint
- 要高质量
- 要全面
- 要简洁，控制在一页纸
- 要包含每日时间安排、周目标、月度复盘、年度规划和风险预案
```

提示：从三个维度思考——Context 够不够？Requirement 够不够具体？Constraint 之间有没有矛盾？

### 练习 3：为真实任务编写 CRC

选择你最近生活或工作中的一个真实任务（如写一封重要邮件、做一个方案、分析一份数据），用 CRC 格式写一段提示词，然后发给 AI，看看输出效果。

对比一下：和你平时随意提问相比，输出质量有什么差异？

### 参考思路

**练习 1 参考思路**：一份好的改写应该包含：你的岗位和经验年限（Context）、简历的具体用途和目标公司类型（Requirement）、格式要求和内容侧重（Constraint）。比如"我是 5 年经验的 Java 后端，要投互联网大厂的高级工程师岗，简历用一页 PDF，重点突出架构设计和性能优化经验"。

**练习 2 参考思路**：这段 CRC 有三个问题。(1) Context 太模糊——"上班族"不够，应该说明岗位和具体忙什么。(2) Requirement 太笼统——"工作计划"可以是日计划、周计划、项目计划，完全不同。(3) Constraint 自相矛盾——"要简洁，控制在一页纸"和"包含每日安排、周目标、月度复盘、年度规划和风险预案"不可能同时满足。

**练习 3 参考思路**：这道题没有标准答案，关键是对比有 CRC 和没有 CRC 时的输出差异。通常你会发现：有 CRC 时 AI 的第一次输出就接近你想要的，不需要反复修改。

## 1.6 本章小结

**核心要点回顾：**

- **C - Context**：告诉 AI 你的背景（你是谁、在做什么、已有什么条件）
- **R - Requirement**：告诉 AI 你要什么（具体任务、包含内容、输出形式）
- **C - Constraint**：告诉 AI 限制条件（资源、风格、格式、排除项）
- CRC 不是教条，简单问题可以简化，复杂任务要写完整
- AI 输出质量 = 你的输入质量，结构化表达是基本功
