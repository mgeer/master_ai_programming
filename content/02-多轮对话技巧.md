# 第二章：多轮对话技巧

## 2.1 引言

**本章目标**：掌握与 AI 进行多轮对话的五个核心技巧。

上一章我们学会了怎么把需求说清楚——用 CRC 三要素结构化表达。但实际开发中，一次表达往往不够。

一个复杂任务通常需要多轮对话：先描述需求，再讨论方案，再审查代码，再优化改进。**和 AI 协作不是"下单等菜"，而是"持续沟通"。**

多轮对话的关键不是"多说几句"，而是**掌握对话策略**——知道什么时候让 AI 问你、什么时候让 AI 扮演角色、什么时候让 AI 挑错、什么时候和 AI 一起设计方法。

学完本章，你可以：
- 让 AI 帮你发现自己没想到的问题
- 让 AI 从不同角度审查你的代码和方案
- 让 AI 帮你设计更专业的提示词
- 有效管理长对话，避免上下文丢失和方向跑偏

---

## 2.2 技巧一：让 AI 提问（苏格拉底式引导）

### 为什么要让 AI 反过来问你？

写代码时最危险的不是"你不会的"，而是"你以为自己想清楚了，但其实遗漏了"。

比如你打算写一个缓存模块，脑子里想的是"用 Redis 缓存查询结果"。但你可能没考虑过：
- 缓存过期策略是什么？
- 缓存穿透怎么处理？
- 缓存和数据库的一致性如何保证？
- 缓存 key 怎么设计？

这些问题你自己很难发现——因为**人很难意识到自己不知道什么**。

但 AI 可以。让 AI 反过来向你提问，它会从系统性的角度列出你可能遗漏的关键问题。

### 如何触发 AI 提问

核心提示词很简单：

```
在你开始做之前，先向我提问，确保你完全理解了我的需求。
每次最多问 5 个最关键的问题。
```

或者更直接：

```
不要直接给我代码。先分析我的需求，列出你认为需要澄清的问题。
```

### 进阶技巧：一次一问

一次列出 5 个问题效率高，但问题之间相互独立，无法层层深入。对于复杂任务，让 AI **一次只问一个问题**效果更好——前一个回答会影响后续的提问方向：

```
在你开始之前，先向我提问，确保你完全理解需求。
一次只问一个问题，等我回答后再问下一个。
当你认为信息足够时，告诉我并开始执行。
```

比如 AI 先问"缓存用 Redis 还是内存？"，你回答"Redis"后，AI 才会追问"Redis 是单机还是集群？"——如果你回答的是"内存"，追问方向就完全不同了。

**建议**：简单任务用一次多问（快），复杂任务用一次一问（深）。

### 案例（Python）：设计一个缓存模块

**你的提示词：**

```
## Context
我在开发一个待办事项 API，使用 Python + FastAPI，数据库是 PostgreSQL。
现在查询接口响应较慢，我想加一层缓存。

## Requirement
帮我设计一个缓存方案。

## Constraint
在你给出方案之前，先向我提问，确保你完全理解了需求和约束。
每次最多问 5 个最关键的问题。
```

**AI 的提问（示例）：**

> 在给出方案之前，我需要了解以下几点：
>
> 1. **缓存对象**：需要缓存哪些查询？全部查询还是特定接口（如列表查询、详情查询）？
> 2. **一致性要求**：当数据更新后，缓存可以容忍多长时间的延迟？（比如用户创建了新 Todo，列表缓存多久更新？）
> 3. **基础设施**：项目中是否已经引入 Redis？还是希望用内存缓存（如 Python 的 lru_cache）？
> 4. **并发量**：大概的 QPS 是多少？这会影响缓存策略的选择。
> 5. **部署方式**：服务是单实例还是多实例部署？多实例的话内存缓存会有一致性问题。

这 5 个问题中，至少有 2-3 个是你之前没想到的。回答完之后，AI 给出的方案会精准得多。

### 与 CRC 的配合

上一章讲了 CRC 三要素。苏格拉底式提问的一个重要用途，就是**帮你补全 CRC 中遗漏的信息**：
1. 先用 CRC 写出初步的需求描述
2. 让 AI 提问，看看 AI 能问出哪些你没覆盖到的问题
3. 根据 AI 的提问，补充完善你的 CRC

CRC 是"你主动说"，苏格拉底是"让 AI 帮你查漏"，两者配合效果最佳。

### 适用场景

| 场景 | 效果 |
|------|------|
| 需求不明确、只有模糊想法 | AI 帮你把模糊想法变成清晰需求 |
| 技术方案设计 | AI 帮你发现遗漏的技术考量 |
| 技术选型 | AI 帮你理清选型的关键维度 |
| 任务拆解 | AI 帮你找到遗漏的子任务 |
| 验证 CRC 完整性 | AI 帮你发现上下文、需求或约束的遗漏 |

## 2.3 技巧二：让 AI 扮演角色

### 为什么角色扮演有效？

同一段代码，不同角色看到的问题完全不同：
- **开发者**看到的是"功能实现了没有"
- **Code Reviewer** 看到的是"代码质量、可维护性"
- **QA 工程师**看到的是"边界条件、异常场景"
- **安全专家**看到的是"注入、越权、信息泄露"

一个人很难同时具备所有视角。但 AI 可以——你让它扮演谁，它就用谁的视角看问题。

### 常用角色

| 角色 | 关注维度 | 适用场景 |
|------|---------|---------|
| Code Reviewer | 代码可读性、设计模式、命名规范、重复代码 | 代码写完后的质量审查 |
| QA Engineer | 边界条件、异常输入、并发场景、错误处理 | 功能完成后的测试设计 |
| Security Expert | SQL 注入、XSS、权限校验、敏感数据 | 涉及用户输入和权限的代码 |
| Junior Developer | 代码是否容易理解、注释是否清晰 | 检验代码可读性 |
| DevOps Engineer | 部署配置、日志、监控、容错 | 上线前的检查 |

### 不指定维度 vs 指定维度

先看一个对比：

❌ **不指定维度**：
```
帮我审查一下这段代码
```
AI 的典型回答："这段代码整体不错，建议加一些注释，变量命名可以更清晰。"——正确但没用。

✅ **指定角色和维度**：
```
作为 Code Reviewer，从代码质量、错误处理、安全性三个维度审查。
```
AI 会逐个维度深入分析，给出具体的问题和修复建议。

**差别的本质**：不指定维度，AI 会给"安全的泛泛回答"；指定维度，AI 被"逼"着深入思考每个方向。

### 案例 1（Python）：Code Reviewer 审查代码

**场景**：你写了一个创建待办事项的接口，觉得写得还不错。

**你的代码：**

```python
@app.post("/todos")
async def create_todo(data: dict, db: Session = Depends(get_db)):
    todo = Todo(
        title=data["title"],
        description=data.get("description", ""),
        priority=data.get("priority", "medium"),
        user_id=data["user_id"]
    )
    db.add(todo)
    db.commit()
    return {"id": todo.id, "message": "created"}
```

**你的提示词：**

```
作为一名严格的 Code Reviewer，审查以上代码。
从以下维度给出具体的改进建议：
1. 代码质量和可读性
2. 错误处理
3. 安全性
4. 设计合理性
```

**AI 的审查意见（示例）：**

> **问题 1：参数类型不安全**
> 使用 `dict` 接收请求体，完全没有校验。应该使用 Pydantic 模型（如第一章的 `CreateTodoRequest`），让 FastAPI 自动校验参数。
>
> **问题 2：缺少错误处理**
> `data["title"]` 和 `data["user_id"]` 如果不存在会抛出 `KeyError`，但没有 try-except 或 Pydantic 校验来捕获。`db.commit()` 也没有处理数据库异常。
>
> **问题 3：权限问题**
> `user_id` 直接从请求体获取，用户可以伪造任意 `user_id`。应该从 JWT Token 中提取当前登录用户的 ID。
>
> **问题 4：返回值不规范**
> 返回的字典没有明确的响应模型，建议定义 Pydantic 响应模型，并返回完整的 Todo 对象而不是只返回 id。

这些问题你自己很可能看不出来——因为"写代码的人"和"审查代码的人"天然视角不同。

### 案例 2（Vue）：QA Engineer 审查组件

**你的提示词：**

```
作为 QA Engineer，审查以下 Vue 3 表单组件的边界条件和异常场景。
列出你会设计的测试用例，重点关注：
1. 用户可能的异常操作
2. 网络异常情况
3. 并发提交问题
```

```vue
<script setup lang="ts">
import { ref } from 'vue'
import { createTodo } from '@/api/todo'

const title = ref('')
const loading = ref(false)

async function handleSubmit() {
  loading.value = true
  await createTodo({ title: title.value })
  loading.value = false
  title.value = ''
}
</script>
```

**AI 的审查意见（示例）：**

> **测试用例 1：空标题提交**
> 用户不输入标题直接点提交，`title.value` 为空字符串，会创建一个无标题的 Todo。缺少前端校验。
>
> **测试用例 2：网络异常**
> `createTodo` 请求失败时没有 try-catch，`loading.value` 永远不会被重置为 `false`，提交按钮会一直处于加载状态。
>
> **测试用例 3：重复提交**
> 用户快速连续点击提交按钮，虽然有 `loading` 状态，但如果按钮没有绑定 `:disabled="loading"`，仍然可以触发多次请求。
>
> **测试用例 4：超长标题**
> 用户输入几千个字符的标题，前端没有限制，后端可能会报错或存储失败。

### 角色扮演的提示词模板

```
作为 [角色名称]，审查以下 [代码/方案/设计]。
从以下维度给出具体的改进建议：
1. [维度 1]
2. [维度 2]
3. [维度 3]
```

**关键点**：指定具体的审查维度，否则 AI 可能泛泛而谈。

## 2.4 技巧三：让 AI 挑错与优化

### 和角色扮演的区别

角色扮演是给 AI 一个**身份**（"你是 Code Reviewer"），AI 会从那个角色的视角全面审查。

挑错与优化是给 AI 一个**具体任务指令**（"找出这段代码的 bug"），目标更聚焦。

两者可以结合使用，也可以单独使用。

### 三种挑错模式

#### 模式 1：找 bug

```
仔细检查以下代码，找出所有潜在的 bug 和逻辑错误。
特别注意：边界条件、空值处理、类型错误、并发问题。
不要放过任何细节。
```

#### 模式 2：找改进空间

```
以下代码能正常工作，但我觉得还有改进空间。
请从以下方面给出优化建议：
1. 性能优化
2. 代码简化
3. 更好的设计模式
```

#### 模式 3：挑战方案

```
我计划用以下方案实现 [功能描述]。
请站在反对者的角度，挑战这个方案：
1. 这个方案最大的风险是什么？
2. 有没有更好的替代方案？
3. 在什么情况下这个方案会失败？
```

### 案例（Python）：找出隐藏 bug

**你的代码：**

```python
from datetime import datetime

def get_overdue_todos(todos: list[dict]) -> list[dict]:
    """返回所有已过期的待办事项"""
    overdue = []
    for todo in todos:
        if todo["due_date"] < datetime.now():
            overdue.append(todo)
    return sorted(overdue, key=lambda x: x["due_date"])
```

**你的提示词：**

```
仔细检查以下代码，找出所有潜在的 bug 和边界条件问题。
不要放过任何细节，即使看起来不太可能发生。
```

**AI 的回答（示例）：**

> **Bug 1：`due_date` 可能为 None**
> 如果某个 Todo 没有设置截止日期（`due_date` 为 None），`None < datetime.now()` 会抛出 `TypeError`。
>
> **Bug 2：时区问题**
> `datetime.now()` 返回的是本地时间。如果 `due_date` 存储的是 UTC 时间，比较结果会不正确。应该统一使用 `datetime.now(timezone.utc)`。
>
> **Bug 3：`due_date` 可能是字符串**
> 如果数据来自 JSON 反序列化，`due_date` 可能是字符串格式（如 `"2026-03-01"`），不能直接和 `datetime` 对象比较。

3 个 bug 都很典型：空值、时区、类型——这些问题在本地测试环境往往"恰好没问题"，上线后才暴露。自己 Review 很难发现，但 AI 能系统性地检查。

### 如何让 AI 深入思考而不是敷衍回答

**反面提示词：**

```
这段代码有问题吗？
```

AI 很可能回答："这段代码整体不错，只有一些小建议……"——这是敷衍。

**正面提示词：**

```
这段代码一定有 bug，仔细找出来。
不要说"整体不错"，我要的是具体的问题和修复方案。
```

**关键技巧：**
- 用肯定语气（"一定有 bug"而不是"有没有 bug"）
- 明确排除敷衍回答（"不要说整体不错"）
- 要求具体产出（"具体的问题和修复方案"）

## 2.5 技巧四：元提示（Meta-Prompting）

### 什么是元提示

前面三个技巧，都是你**自己设计提示词**，然后让 AI 执行。但有一个问题：你设计提示词的水平，决定了 AI 输出的上限。如果你不知道 code review 应该关注"幂等性"或"错误传播链路"，你就不会把这些维度写进提示词，AI 自然也不会去检查。

元提示的思路是：**不要自己闷头写提示词，而是先和 AI 一起讨论"应该怎么做"，共同设计出提示词，再执行。**

- 苏格拉底式提问：AI 帮你补全**你的需求**中遗漏的信息
- 元提示：AI 帮你补全**你的提示词**中遗漏的维度和标准

一个是补需求，一个是补方法。

### 案例：设计 Code Review 提示词

**场景**：你写完了一个功能，想让 AI 帮你做 code review。

如果用角色扮演（技巧二），你需要自己指定审查维度：

```
作为 Code Reviewer，从代码质量、错误处理、安全性三个维度审查。
```

这三个维度是你能想到的，但可能还有你想不到的。

**用元提示的方式**，你可以这样开始：

```
我现在要对以下代码进行 code review，帮我一起设计 review 的提示词，然后再执行。
```

```python
@router.post("", status_code=201)
async def create_todo(
    request: CreateTodoRequest,
    db: Session = Depends(get_db),
    current_user_id: int = Depends(get_current_user),
):
    todo = todo_service.create_todo(db, request, current_user_id)
    return TodoResponse.model_validate(todo, from_attributes=True)


@router.get("")
async def list_todos(
    status: Optional[str] = None,
    priority: Optional[str] = None,
    page: int = 1,
    page_size: int = 20,
    db: Session = Depends(get_db),
    current_user_id: int = Depends(get_current_user),
):
    todos, total = todo_service.list_todos(
        db, current_user_id, status, priority, page, page_size
    )
    return {"items": todos, "total": total, "page": page}
```

**AI 的回应（示例）：**

> 好的，我们先设计 review 维度。针对这段 API 路由代码，我建议从以下维度审查：
>
> 1. **输入校验**：参数类型和范围是否有校验（比如 page < 1、page_size 过大）
> 2. **错误处理**：异常是否被正确捕获和转换为 HTTP 响应
> 3. **安全性**：权限校验、数据隔离是否到位
> 4. **API 设计规范**：响应格式是否统一、状态码是否合理、是否符合 RESTful 规范
> 5. **可维护性**：分层是否清晰、是否存在隐式耦合
> 6. **幂等性**：POST 操作重复提交会怎样
>
> 你觉得这些维度够了吗？有没有你特别关注的方面要加上？

**你的回应：**

```
加一个"与项目规范的一致性"，我们的编码规范文档里有具体要求。其他可以了，生成 review 提示词吧。
```

**AI 生成的提示词：**

> 作为 Code Reviewer，审查以上代码，从以下 7 个维度逐一给出具体的问题和改进建议：
>
> 1. **输入校验**：所有参数是否有类型和范围校验？是否存在未校验的用户输入？
> 2. **错误处理**：service 层抛出的异常是否被正确转换为 HTTP 响应？是否有未捕获的异常？
> 3. **安全性**：是否存在越权风险？数据隔离是否严格？
> 4. **API 设计规范**：响应格式是否统一？状态码是否合理？是否符合 RESTful 规范？
> 5. **可维护性**：路由层是否只负责路由？是否存在和 service 层的隐式耦合？
> 6. **幂等性**：重复提交同一请求会产生什么后果？是否需要防重？
> 7. **项目规范一致性**：是否符合项目编码规范中的风格和分层要求？
>
> 每个维度给出：有没有问题 → 问题是什么 → 怎么修复。

这个提示词比你自己写的"三个维度"版本全面得多。其中"幂等性""隐式耦合""响应格式统一性"这些维度，很可能是你自己想不到的。

### 为什么元提示有效

核心原因：**你不需要在所有领域都是专家，AI 可以帮你补上专业知识的盲区。**

你知道"要做 code review"，但你可能不清楚 code review 的最佳实践包含哪些维度。AI 在这方面有大量的训练数据——它见过成千上万的 review 清单、审查标准、最佳实践。通过讨论，它把这些知识注入到你们共同设计的提示词中。

### 适用场景

元提示不是每次都需要的。当你对"怎么做"已经很清楚时，直接写提示词更高效。

| 场景 | 是否适合元提示 |
|------|--------------|
| 你很熟悉的任务（比如日常 CRUD） | 不需要，直接写提示词 |
| 你不太熟悉的专业领域（比如安全审计、性能优化） | 适合，让 AI 帮你补专业维度 |
| 高风险任务（比如上线前的最终检查） | 适合，确保不遗漏关键维度 |
| 第一次做某类任务（比如第一次写迁移脚本） | 适合，让 AI 帮你建立检查清单 |

## 2.6 技巧五：对话管理

> 前面四个技巧是"怎么和 AI 协作"，对话管理是"怎么让协作持续有效"。

### 何时开新对话 vs 继续当前对话

| 场景 | 建议 |
|------|------|
| 换了一个完全不同的任务 | 开新对话 |
| 当前对话已经很长（超过 20 轮） | 开新对话，带上关键上下文 |
| AI 开始"忘记"之前讨论的内容 | 开新对话，总结之前的结论 |
| 在当前任务上继续深入 | 继续当前对话 |
| 基于上一轮的输出做修改 | 继续当前对话 |

### 如何在长对话中保持上下文

AI 的上下文窗口是有限的。对话越长，早期的信息越可能被"挤出去"。

**策略 1：阶段性总结**

在长对话中，每隔几轮让 AI 总结一下当前进展：

```
请总结一下我们目前的讨论结论，包括：
1. 已经确定的方案
2. 还未决定的问题
3. 下一步要做什么
```

这段总结可以保存为文件，在开新对话时通过 `@` 引用（或直接粘贴）作为上下文。

**策略 2：重要信息重复提及**

如果某个约束很重要（比如"必须使用 Python 3.10+"），在关键节点重复一次，防止 AI "忘记"。

**策略 3：善用 AI IDE 的上下文能力**

如果你使用 AI IDE（如 Cursor、Windsurf）或 AI 编程工具（如 Claude Code），上下文管理比纯聊天窗口方便得多：
- 通过文件引用功能直接引用项目中的代码文件，AI 可以自动读取
- 通过规则文件（如 Cursor 的 `.cursor/rules/`、Claude Code 的 `CLAUDE.md`）预设项目规范，AI 每次对话都会自动遵循
- 不需要反复粘贴代码，工具会自动附加相关文件上下文

这意味着在 AI 编程工具中，**你的 Context 成本大幅降低**，可以把精力集中在 Requirement 和 Constraint 上。

### 如何纠正 AI 的方向偏差

AI 有时候会理解错你的意思，或者朝你不想要的方向发展。

**不好的纠正方式：**

```
不对
```

AI 不知道哪里不对，可能继续往错误方向走。

**好的纠正方式：**

```
你理解错了。我的意思不是 [AI 理解的]，而是 [你真正想要的]。
具体来说：[明确的描述]。
请基于这个理解重新来。
```

**核心原则**：**说清楚"哪里错了"和"正确的应该是什么"，而不是只说"不对"。**

### 案例：一次完整的多轮对话流程

以下展示一个完整的多轮对话过程，从需求到完成：

**第 1 轮：CRC + 苏格拉底式提问**
```
[用户]
## Context
我在开发 Todo API，使用 Python + FastAPI。

## Requirement
我需要一个"按优先级筛选待办事项"的接口。

## Constraint
在你动手之前，先问我几个关键问题。
```

**第 2 轮：回答 AI 的问题**
```
[AI] 我有以下问题：
1. 是否支持同时筛选多个优先级？
2. 是否需要分页？
3. 筛选结果的排序规则是什么？

[用户]
1. 支持多选
2. 需要分页，每页 20 条
3. 按创建时间倒序
```

**第 3 轮：让 AI 写代码**
```
[用户] 好，请基于以上讨论编写接口代码。
```

**第 4 轮：角色扮演审查**
```
[用户] 作为 Code Reviewer，审查这段代码的质量和安全性。
```

**第 5 轮：根据审查意见修改**
```
[用户] 你提到的第 2 和第 3 个问题，请帮我修复。
```

**第 6 轮：挑错**
```
[用户] 最终版本的代码，帮我找一下有没有遗漏的边界条件。
```

这个流程就是：**CRC → 苏格拉底 → 实现 → 角色审查 → 修改 → 挑错**。六轮对话，比一轮"帮我写一个筛选接口"的效果好得多。

## 2.7 实操要点

### 多轮对话提示词模板

**苏格拉底式提问：**
```
在你开始之前，先向我提问，确保你完全理解了需求。
每次最多问 [N] 个最关键的问题。
```

**角色扮演：**
```
作为 [角色名称]，审查以下 [代码/方案]。
从以下维度给出具体建议：
1. [维度 1]
2. [维度 2]
```

**找 bug：**
```
这段代码一定有 bug，仔细找出来。
不要说"整体不错"，我要的是具体的问题和修复方案。
```

**挑战方案：**
```
站在反对者的角度，挑战这个方案。
这个方案最大的风险是什么？在什么情况下会失败？
```

**元提示：**
```
我现在要 [做某件事]，帮我一起设计 [提示词/检查清单/评估标准]，然后再执行。
```

### 注意事项

1. **不要一次要求太多**：每轮对话聚焦一个目标，比如这轮只做审查，下轮再做修改
2. **给 AI 足够的信息**：角色扮演时，把相关代码完整贴出来，不要只给片段
3. **追问比重新问更好**：如果 AI 的回答有价值但不够深入，追问"能展开说说第 3 点吗？"比重新描述一遍更高效
4. **保存关键结论**：长对话中的重要决策，及时复制保存，避免后续丢失

## 2.9 本章小结

**五个核心技巧回顾：**

| 技巧 | 核心思路 | 一句话总结 |
|------|---------|-----------|
| 苏格拉底式提问 | 让 AI 问你 | 发现你不知道自己遗漏了什么 |
| 角色扮演 | 让 AI 换身份 | 用不同视角发现不同问题 |
| 挑错与优化 | 让 AI 找问题 | 肯定语气 + 具体要求 = 深入分析 |
| 元提示 | 和 AI 一起设计方法 | 不知道怎么做时，先和 AI 讨论怎么做 |
| 对话管理 | 管理对话过程 | 阶段性总结 + 明确纠正 |

**关键心法：**

- 一轮对话解决简单问题，多轮对话解决复杂问题
- AI 不是搜索引擎，而是协作伙伴——要"对话"，不是"搜索"
- 你引导得越好，AI 输出的质量越高
