# 第四章：Constitution — 项目宪章

## 4.1 引言

**本章目标**：学会为项目建立一份完整的项目宪章，作为所有后续开发的治理基础。

上一章我们了解了 SDD 的全貌：项目级的 Constitution 做一次，功能级的 Specify → Implement 每个 Feature 循环一次。

现在，我们要迈出 SDD 的第一步——写 Constitution。

Constitution 是什么？打个比方：**它是项目的"宪法"。**

一个国家的宪法不会规定"周三食堂吃什么"，但会规定"公民有受教育的权利"。同样，Constitution 不会规定"User 表有哪些字段"，但会规定"我们用 DDD 四层架构"、"密码必须哈希存储"、"测试覆盖率不低于 80%"。

**Constitution 只放规矩，不放设计。** 领域模型、API 设计、数据库表结构——这些是"设计"，属于后面 Plan 阶段的事。Constitution 关心的是：不管你做什么 Feature，都必须遵守的规矩。

再具体一点：

| 属于 Constitution（规矩） | 不属于 Constitution（设计） |
|---|---|
| 使用 DDD 四层架构 | User 实体有哪些属性 |
| 技术栈：FastAPI + PostgreSQL | users 表的字段定义 |
| 密码必须用 bcrypt 哈希 | 登录 API 的请求/响应格式 |
| 测试覆盖率 ≥ 80% | 具体的测试用例 |
| Docker 容器化部署 | docker-compose.yml 的具体配置 |

这个区分很重要。很多人第一次写 Constitution，恨不得把所有东西都塞进去。结果写了一份又长又细的文档，后面每次改需求都要回来改 Constitution——那就失去了"宪法"的意义。

**Constitution 做一次，对所有 Feature 生效。** 它应该足够稳定，不会因为某个功能的增删而需要修改。

接下来，我们会一个一个地把 Constitution 的各个要素讲清楚，每个要素都会走一遍"讲 → 做 → 审"。最后，我们把所有要素整合成一份完整的 Constitution 文档，并把它转化为 AI 能持续遵守的规则文件。

> **本章的贯穿案例**：我们要做一个 Todo 应用，后端用 FastAPI + PostgreSQL + JWT 认证。这个案例会从本章一直用到第 8 章。

## 4.2 架构原则

### 讲

架构原则回答的是一个根本问题：**代码怎么组织？**

你可能觉得"先做出来再说"，但经验会告诉你：代码组织方式在项目开始时不定好，后面改的成本极高。特别是用 AI 写代码的时候——AI 不会自己决定把代码放哪里。你不告诉它架构规则，它今天把业务逻辑写在路由层，明天写在数据库层，后天再来个混搭。

常见的架构原则包括：

- **分层架构**：比如 DDD 四层（API 层 → 应用层 → 领域层 → 基础设施层），每层有明确的职责边界
- **关注点分离**：路由不碰数据库，数据库不碰业务逻辑
- **模块化**：按业务域划分模块，而不是按技术类型（不要搞一个 `models/` 把所有模型堆一起）

对于我们的 Todo 应用，我们选择 DDD 四层架构。这不是因为 DDD 是银弹，而是因为它的分层逻辑清晰，AI 容易理解和遵守。

### 做

#### 第一层：一句话启动

我们先用最简单的提示词让 AI 开始：

> **提示词**：
> "我正在开始一个新的后端项目。帮我确定架构原则，要求采用 DDD 四层架构，强调关注点分离和模块化。"

AI 会给出一份初版的架构原则描述，大致包含四层的定义和各层的职责。但通常这个初版会比较泛——缺少你项目的具体约束。

#### 第二层：对话补充

看完 AI 的初版后，你可以通过 2-3 轮追问补充细节：

> **你**："每层之间的依赖方向是什么？哪些层可以互相调用，哪些不行？明确列出来。"

> **你**："我们按业务域划分模块，不按技术类型。比如不要一个全局的 models/ 目录，而是每个模块有自己的 models。给出具体的目录结构示例。"

> **你**："补充一条：API 层只做请求解析和响应封装，不包含任何业务逻辑。"

经过几轮补充，AI 的产出会更贴合你的项目实际。

#### 第三层：完整参考（可选）

> 下面这个完整版提示词**不是必须的**。上面的一句话启动 + 对话补充完全能达到同样效果。这里放出来只是作为参考，给喜欢一次性把事情说清楚的读者。

```
我正在建立一个后端项目的架构原则。请按以下要求输出：

1. 分层架构：采用 DDD 四层
   - API 层（接口适配）：只负责请求解析、参数校验、响应封装
   - 应用层（用例编排）：编排领域服务，处理事务，不含业务规则
   - 领域层（业务核心）：实体、值对象、领域服务，纯业务逻辑
   - 基础设施层（技术实现）：数据库、外部 API、消息队列等

2. 依赖规则：
   - 只能上层依赖下层，不能反向依赖
   - 领域层不依赖任何外部框架

3. 模块划分：
   - 按业务域划分模块，不按技术类型
   - 给出目录结构示例

4. 关注点分离的具体规则
```

AI 产出示例（节选）：

```markdown
## 架构原则

### 分层架构（DDD 四层）

| 层级 | 职责 | 允许依赖 |
|------|------|---------|
| API 层 | 请求解析、参数校验、响应封装 | 应用层 |
| 应用层 | 用例编排、事务管理 | 领域层、基础设施层 |
| 领域层 | 实体、值对象、业务规则 | 无外部依赖 |
| 基础设施层 | 数据库访问、外部服务集成 | 领域层（实现接口） |

### 依赖规则
- 只能上层调用下层，严禁反向依赖
- 领域层是纯净的：不导入 FastAPI、SQLAlchemy 等框架
- 基础设施层通过实现领域层定义的接口（Repository 模式）与领域层交互

### 模块化
- 按业务域组织代码，每个模块包含完整的四层结构
- 模块间通过应用层协调，不直接互调领域层
```

### 审

拿到 AI 的架构原则后，检查这几个点：

- **四层的职责边界是否清晰？** 特别注意"应用层"和"领域层"的边界——这是最容易混淆的地方。应用层编排流程，领域层包含业务规则。
- **依赖方向是否明确？** 必须是单向的，上层依赖下层。如果 AI 写了"领域层可以调用基础设施层"，这是错误的。
- **模块化规则是否具体？** 不能只说"按业务域划分"，要有目录结构示例。
- **有没有过度设计？** 如果 AI 在这里引入了事件驱动、CQRS 之类的模式，对于一个 Todo 应用来说太重了。Constitution 应该保持简洁。

## 4.3 技术栈选择

### 讲

技术栈选择是 Constitution 中最直接的部分：**这个项目用什么语言、什么框架、什么数据库？**

为什么要写在 Constitution 里？因为这些选择一旦做出，影响所有 Feature。如果你不在 Constitution 里明确写清楚，AI 今天给你用 SQLAlchemy，明天给你用 Tortoise ORM，后天改成 Peewee——每次对话都要重新纠正。

技术栈选择不只是列个清单，还要说明**为什么选它**。这个"为什么"不是给 AI 看的，是给未来的你（或者你的队友）看的。三个月后回头看，你得知道当初为什么选了 PostgreSQL 而不是 MySQL。

对于我们的 Todo 应用：
- **语言**：Python 3.11+（团队熟悉、生态丰富）
- **Web 框架**：FastAPI（异步、自动文档、类型提示友好）
- **数据库**：PostgreSQL（功能完备、JSON 支持好）
- **ORM**：SQLAlchemy 2.0（成熟稳定、DDD 友好）
- **认证**：JWT（无状态、适合 API）

### 做

#### 第一层：一句话启动

> **提示词**：
> "帮我确定这个项目的技术栈。要求：Python 后端，RESTful API，关系型数据库，JWT 认证。给出具体的库选择和版本要求。"

#### 第二层：对话补充

> **你**："Web 框架选 FastAPI，数据库选 PostgreSQL。ORM 用 SQLAlchemy 2.0 的新式写法。补充每个选择的理由。"

> **你**："再加上这些开发工具：pytest 做测试、Alembic 做数据库迁移、Pydantic 做数据校验。"

> **你**："密码哈希用 bcrypt，JWT 库用 python-jose。列一个完整的依赖清单。"

#### 第三层：完整参考（可选）

> 同样，这个完整版**不是必须的**。

```
帮我确定以下项目的技术栈，并说明选择理由：

项目类型：RESTful API 后端服务

要求：
- 语言：Python 3.11+
- Web 框架：FastAPI
- 数据库：PostgreSQL 16+
- ORM：SQLAlchemy 2.0（新式映射）
- 数据校验：Pydantic v2
- 认证：JWT（python-jose + passlib[bcrypt]）
- 测试：pytest + httpx（异步测试客户端）
- 数据库迁移：Alembic
- 代码质量：ruff（lint + format）

请按以下格式输出：
1. 核心依赖清单（名称 + 版本要求 + 用途）
2. 开发依赖清单
3. 每个选择的简短理由（1-2 句话）
```

AI 产出示例（节选）：

```markdown
## 技术栈

### 核心依赖

| 依赖 | 版本 | 用途 |
|------|------|------|
| Python | ≥ 3.11 | 运行环境 |
| FastAPI | ≥ 0.110 | Web 框架，异步支持、自动生成 OpenAPI 文档 |
| SQLAlchemy | ≥ 2.0 | ORM，支持新式声明映射，DDD 友好 |
| PostgreSQL | ≥ 16 | 主数据库 |
| Pydantic | ≥ 2.0 | 数据校验与序列化 |
| python-jose | ≥ 3.3 | JWT 令牌生成与验证 |
| passlib[bcrypt] | ≥ 1.7 | 密码哈希 |
| asyncpg | ≥ 0.29 | PostgreSQL 异步驱动 |

### 开发依赖

| 依赖 | 用途 |
|------|------|
| pytest | 测试框架 |
| pytest-asyncio | 异步测试支持 |
| httpx | 异步 HTTP 测试客户端 |
| Alembic | 数据库迁移 |
| ruff | 代码检查与格式化 |
```

### 审

审查技术栈时注意：

- **版本号是否合理？** AI 有时候会编造不存在的版本号。关键依赖的版本最好自己去 PyPI 确认一下。
- **依赖之间是否兼容？** 比如 SQLAlchemy 2.0 需要 asyncpg 而不是 psycopg2 来做异步。
- **有没有遗漏？** 常见的遗漏包括：环境变量管理（python-dotenv）、日志库、CORS 中间件等。
- **有没有多余？** 如果 AI 加了你不需要的东西（比如 Celery、Redis），先删掉。Constitution 里只放确定要用的。

## 4.4 开发方法论

### 讲

开发方法论回答的是：**写代码的流程是什么？**

你可能觉得"这有什么好定的，写就完了"。但如果你用 AI 写代码，方法论直接决定了 AI 的工作方式：

- 如果你定了 **TDD**（测试驱动开发），AI 就会先写测试、再写实现
- 如果你定了 **BDD**（行为驱动开发），AI 会从用户行为的角度设计测试用例
- 如果你什么都不定，AI 就直接写代码，没有测试——后面你自己补

**为什么在 Constitution 阶段就要确定开发方法论？** 因为它影响每一个 Feature 的实现方式。如果等到第一个 Feature 才决定"要不要写测试"，你会发现前面写的代码全都没有测试，补起来很痛苦。

对于我们的 Todo 应用，我们选择 **TDD + BDD 结合**：
- **BDD** 思维设计测试：测试用例从用户行为出发（"当用户创建一个 Todo 时，应该返回 201 并包含创建的 Todo"）
- **TDD** 流程执行：先写测试 → 再写实现 → 最后重构

### 做

#### 第一层：一句话启动

> **提示词**：
> "帮我确定这个项目的开发方法论。我想采用 TDD/BDD 结合的方式，先写测试再写实现。"

#### 第二层：对话补充

> **你**："具体描述一下每个任务的开发流程：先写什么测试、再实现什么、最后做什么检查。"

> **你**："BDD 部分要更具体——测试用例用 Given-When-Then 格式描述。给一个 Todo 创建的例子。"

#### 第三层：完整参考（可选）

> **不是必须的**，一句话 + 对话补充同样有效。

```
帮我定义项目的开发方法论，要求：

1. 采用 TDD + BDD 结合
2. 每个任务的开发流程：
   - 先用 BDD 风格设计测试用例（Given-When-Then）
   - 编写测试代码（pytest）
   - 实现功能代码使测试通过
   - 代码审查与重构
3. 给出一个具体示例（如 Todo 创建功能的测试设计）
4. 说明测试的分层：单元测试 vs 集成测试的划分标准
```

AI 产出示例（节选）：

```markdown
## 开发方法论

### 开发流程（每个任务）

1. **设计测试**：用 BDD 风格描述预期行为
   ```
   Given: 一个已认证的用户
   When: 用户发送 POST /todos 请求，body 包含 title 和 description
   Then: 返回 201，响应包含创建的 Todo 及其 ID
   ```

2. **编写测试代码**：将 BDD 场景转为 pytest 测试用例

3. **实现功能**：编写最少的代码使测试通过

4. **重构**：在测试保护下优化代码结构

### 测试分层

| 层级 | 覆盖范围 | 工具 |
|------|---------|------|
| 单元测试 | 领域层逻辑、工具函数 | pytest |
| 集成测试 | API 端到端、数据库交互 | pytest + httpx + 测试数据库 |
```

### 审

审查开发方法论时注意：

- **流程是否可执行？** 不能太抽象。"先写测试再写实现"不够——要说清楚写什么层级的测试。
- **BDD 示例是否具体？** Given-When-Then 不能太泛。"Given: 一个用户"太模糊，应该是"Given: 一个已认证的用户"。
- **测试分层是否合理？** 对于 API 项目，集成测试通常比单元测试更重要。如果 AI 把重心放在单元测试上，需要纠正。
- **有没有提到测试数据管理？** 测试数据库怎么管理、测试数据怎么准备，这些细节容易遗漏。

## 4.5 编码规范与质量标准

### 讲

编码规范是团队（包括 AI）都必须遵守的代码风格约定。没有它，AI 今天用 `snake_case`，明天用 `camelCase`，后天又变成 `PascalCase`。

你可能会说："Python 本身就有 PEP 8 啊。" 没错，但 PEP 8 只管基本的代码风格。你的项目还需要更多约定：

- **命名约定**：文件怎么命名？类怎么命名？API 路径用什么风格？
- **目录结构**：代码放在哪里？测试放在哪里？
- **代码风格**：用 ruff 还是 black？行宽限制多少？
- **质量标准**：测试覆盖率要求多少？是否强制类型注解？

这些东西如果不写在 Constitution 里，你就得在每次和 AI 对话时重复一遍。写一次 Constitution，AI 就会持续遵守。

### 做

#### 第一层：一句话启动

> **提示词**：
> "帮我制定这个 Python 项目的编码规范和质量标准，包括命名约定、目录结构、代码风格和测试要求。"

#### 第二层：对话补充

> **你**："命名约定要更具体：文件名用 snake_case，类名用 PascalCase，API 路径用 kebab-case，数据库表名用 snake_case 复数形式。"

> **你**："测试覆盖率要求 80% 以上。所有函数必须有类型注解。不允许使用 Any 类型，除非有注释说明原因。"

> **你**："目录结构要符合前面定的 DDD 四层和模块化原则。给出完整的项目目录树。"

#### 第三层：完整参考（可选）

> **不是必须的**。

```
为这个 Python/FastAPI 项目制定编码规范和质量标准：

1. 命名约定：
   - 文件/模块：snake_case
   - 类：PascalCase
   - 函数/变量：snake_case
   - 常量：UPPER_SNAKE_CASE
   - API 路径：kebab-case（/api/v1/todo-items）
   - 数据库表：snake_case 复数形式（users, todo_items）

2. 目录结构：基于 DDD 四层 + 模块化，给出完整目录树

3. 代码风格：
   - 格式化工具：ruff
   - 行宽：88 字符
   - 导入排序：isort 规则
   - 字符串：双引号

4. 质量标准：
   - 测试覆盖率 ≥ 80%
   - 所有函数必须有类型注解
   - 不允许使用 Any 类型（除非注释说明）
   - 所有 API 必须有 docstring

5. 给出目录结构示例
```

### 审

审查编码规范时注意：

- **命名约定是否完整？** 容易遗漏的：环境变量命名（UPPER_SNAKE_CASE + 前缀）、配置类命名、异常类命名。
- **目录结构是否符合前面定的架构原则？** 如果前面定了 DDD 四层 + 模块化，这里的目录结构必须体现出来。AI 有时候会"忘记"前面的约定。
- **质量标准是否可度量？** "代码要写好"不是质量标准。"测试覆盖率 ≥ 80%"才是。
- **有没有自相矛盾？** 比如说了"用 ruff"但又提了 black 和 isort 的配置——ruff 已经包含了这些功能。

## 4.6 安全策略

### 讲

安全策略是最容易被忽略的 Constitution 内容。很多人觉得"先把功能做了，安全以后再说"——但在 AI 编程中，**安全策略如果不在 Constitution 里明确，AI 根本不会主动考虑安全。**

你让 AI 写个登录功能，如果不提安全要求，AI 可能：
- 用明文存储密码
- JWT 不设过期时间
- API 不做权限校验
- 错误信息暴露数据库细节

这些都不是 AI 的错——你没提，它就不做。Constitution 里写清楚安全策略，AI 在后续每个 Feature 的实现中都会自觉遵守。

对于我们的 Todo 应用，安全策略需要覆盖三个方面：
1. **认证**：怎么确认"你是谁"
2. **数据保护**：怎么保护用户数据
3. **合规**：有没有必须满足的法规要求

### 做

#### 第一层：一句话启动

> **提示词**：
> "为这个项目制定安全策略，涵盖 JWT 认证方案、数据保护规则和基本的安全合规要求。"

#### 第二层：对话补充

> **你**："JWT 的具体要求：使用 HS256 算法，access token 过期时间 30 分钟，refresh token 7 天。token 中只放 user_id 和角色信息，不放敏感数据。"

> **你**："数据保护要更具体：密码用 bcrypt 哈希（cost factor 12），API 响应中永远不返回密码字段，日志中不记录敏感信息。"

> **你**："所有 API 错误响应统一格式，不暴露内部实现细节。比如登录失败只返回'用户名或密码错误'，不区分是用户不存在还是密码错误。"

#### 第三层：完整参考（可选）

> **不是必须的**。

```
为这个项目制定安全策略：

1. 认证方案：
   - JWT Bearer Token 认证
   - 算法：HS256
   - Access Token 过期：30 分钟
   - Refresh Token 过期：7 天
   - Token payload 只包含：user_id、role、exp
   - 不在 token 中存放敏感信息

2. 数据保护：
   - 密码：bcrypt 哈希，cost factor 12
   - API 响应永远不包含密码字段
   - 日志中屏蔽敏感信息（密码、token）
   - 数据库连接使用 SSL

3. API 安全：
   - 所有写操作需要认证
   - 错误响应统一格式，不暴露内部细节
   - 登录失败不区分"用户不存在"和"密码错误"
   - 实施请求频率限制

4. 合规：
   - 密码长度最少 8 位
   - 支持用户注销和数据删除
```

AI 产出示例（节选）：

```markdown
## 安全策略

### 认证

- 方式：JWT Bearer Token
- 算法：HS256
- Access Token 有效期：30 分钟
- Refresh Token 有效期：7 天
- Token Payload：仅包含 `sub`（user_id）、`role`、`exp`
- 认证头格式：`Authorization: Bearer <token>`

### 数据保护

- 密码存储：bcrypt 哈希，cost factor = 12
- 响应过滤：任何 API 响应不得包含密码、token 等敏感字段
- 日志脱敏：密码、token、个人身份信息在日志中以 `***` 替代
- 传输安全：生产环境强制 HTTPS

### API 安全规则

- 所有非 GET 端点（以及涉及用户数据的 GET 端点）必须认证

- 错误响应统一格式：`{"detail": "error message"}`，不暴露堆栈或数据库信息
- 登录失败统一返回："用户名或密码错误"
```

### 审

审查安全策略时注意：

- **JWT 配置是否完整？** 必须包含：算法、过期时间、payload 内容、刷新机制。
- **密码策略是否明确？** "哈希存储"不够——要指定算法（bcrypt）和参数（cost factor）。
- **错误处理是否安全？** 看 AI 有没有在错误响应中暴露内部信息。
- **有没有遗漏常见攻击面？** SQL 注入（ORM 已处理）、CORS 配置、请求频率限制、XSS（API 项目通常不需要）。
- **过度设计了吗？** 如果 AI 加了 OAuth2、多因素认证、IP 白名单——对 Todo 应用来说没必要。

## 4.7 部署架构

### 讲

部署架构定义的是：**代码怎么从你的电脑到线上运行？**

你可能觉得"部署是最后的事情，先把代码写了再说"。但 Constitution 里定好部署架构，有几个好处：

1. **开发环境一致性**：所有人（包括 AI）都知道项目怎么跑起来
2. **环境隔离**：开发、测试、生产环境的配置不混淆
3. **CI/CD 规范**：代码合并流程、自动化测试、部署流程提前定好

对于我们的 Todo 应用，部署架构保持简单：
- Docker 容器化
- 三个环境（开发 / 测试 / 生产）
- 基本的 CI/CD 流程

### 做

#### 第一层：一句话启动

> **提示词**：
> "为这个项目制定部署架构方案，要求 Docker 容器化，区分开发/测试/生产环境，包含基本的 CI/CD 流程。"

#### 第二层：对话补充

> **你**："开发环境用 docker-compose 一键启动，包含应用和 PostgreSQL。测试环境用独立的测试数据库。"

> **你**："CI/CD 用 GitHub Actions，PR 时自动跑测试和 lint，合并到 main 后自动部署。"

> **你**："环境变量管理：开发环境用 .env 文件，生产环境用环境变量注入。.env 文件不能进 git。"

#### 第三层：完整参考（可选）

> **不是必须的**。

```
为这个 FastAPI + PostgreSQL 项目制定部署架构：

1. 容器化：
   - Docker + docker-compose
   - 开发环境一键启动（应用 + 数据库）
   - 生产环境 Dockerfile 优化（多阶段构建）

   - 开发（development）：本地 docker-compose，热重载

   - 生产：环境变量注入
   - 提供 .env.example 作为模板
```

- **CI/CD 是否具体？** "自动化测试"太模糊，要说清楚跑什么（lint、test、coverage）、什么时候跑（PR、merge）。
- **有没有过度设计？** Kubernetes、多区域部署、蓝绿发布——Todo 应用不需要这些。

## 4.8 规则文件落地

到这里，我们已经有了一份完整的 Constitution 文档。但文档只是文档——你每次和 AI 对话时，还需要手动引用它。有没有更好的办法？

有。**把 Constitution 转化为规则文件。**

以 Cursor 为例，`.cursor/rules/` 目录下的文件会被 AI 自动读取和遵守。你不需要每次对话都说"按照 constitution.md 来"，AI 会自动按规则行事。

### Constitution 文档 vs 规则文件

| 维度 | Constitution 文档 | 规则文件 |
|------|------------------|---------|
| 位置 | `.spec/constitution.md` | `.cursor/rules/*.mdc` |
| 读者 | 人 + AI | AI |
| 内容 | 完整、有上下文和理由 | 精简、可执行的指令 |
| 用途 | 决策依据、团队共识 | AI 行为自动约束 |

简单说：**Constitution 文档是"为什么"，规则文件是"怎么做"。**

### 怎么转化？

不需要手动提取——让 AI 来做：

> **提示词**：
> "基于这份 Constitution 文档（@constitution.md），生成 Cursor 规则文件。按关注点拆分为多个文件，放在 .cursor/rules/ 目录下。每个文件聚焦一个方面，内容是 AI 可直接遵守的指令。"

AI 通常会生成这样的规则文件结构：

```
.cursor/rules/
├── architecture.mdc       # 架构原则规则
├── tech-stack.mdc         # 技术栈约束
├── coding-standards.mdc   # 编码规范
├── testing.mdc            # 测试要求
├── security.mdc           # 安全规则
└── deployment.mdc         # 部署规范
```

以 `architecture.mdc` 为例：

```markdown
---
description: 项目架构原则
globs: src/**
---

# 架构规则

## 分层架构（DDD 四层）

- API 层（`api/`）：只做请求解析、参数校验、响应封装，不包含业务逻辑
- 应用层（`application/`）：编排领域服务和基础设施，处理事务
- 领域层（`domain/`）：实体、值对象、业务规则，不依赖任何外部框架
- 基础设施层（`infrastructure/`）：数据库访问、外部服务、技术实现

## 依赖规则

- 只能上层依赖下层：api → application → domain ← infrastructure
- 领域层禁止导入 FastAPI、SQLAlchemy 等框架
- 基础设施层通过实现领域层接口与之交互

## 模块化

- 按业务域组织代码：src/auth/、src/todo/
- 每个模块包含完整的四层目录
- 模块间通过应用层协调
```

以 `coding-standards.mdc` 为例：

```markdown
---
description: 编码规范
globs: "**/*.py"
---

# 编码规范

## 命名

- 文件/模块：snake_case（如 todo_service.py）
- 类：PascalCase（如 TodoService）
- 函数/变量：snake_case（如 create_todo）
- 常量：UPPER_SNAKE_CASE（如 MAX_TITLE_LENGTH）
- API 路径：kebab-case（如 /api/v1/todo-items）
- 数据库表：snake_case 复数形式（如 todo_items）

## 代码质量

- 所有函数必须有类型注解
- 禁止使用 Any 类型（除非附注释说明）
- 使用 ruff 进行 lint 和格式化
- 行宽限制 88 字符
```

以 `testing.mdc` 为例：

```markdown
---
description: 测试规范
globs: tests/**
---

# 测试规范

## 方法论

- 开发流程：先写测试，再写实现（TDD）
- 测试设计：BDD 风格，Given-When-Then
- 测试覆盖率要求 ≥ 80%

## 测试分层

- 单元测试：领域层逻辑、工具函数
- 集成测试：API 端到端、数据库交互（使用测试数据库）

## 测试组织

- 测试文件镜像源码目录结构
- 文件命名：test_<module>.py
- 使用 pytest fixtures 管理测试数据
- 每个测试函数只测一个行为
```

### 关键原则

生成规则文件后，注意检查几点：

1. **规则文件要精简**。Constitution 里的"为什么"和"背景说明"不需要放进规则文件。规则文件只要告诉 AI"做什么"和"不做什么"。
2. **按关注点拆分**。不要把所有规则堆在一个文件里。拆开后，AI 可以根据当前工作的文件路径（通过 `globs` 匹配）加载相关规则。
3. **规则之间不矛盾**。拆分后检查一遍，确保各文件的规则不打架。
4. **Constitution 文档仍然保留**。规则文件是给 AI 的执行指令，Constitution 文档是给人看的决策依据。两者互补，不是替代。

## 4.10 本章小结

这一章我们完成了 SDD 的第一个阶段——Constitution。回顾一下我们做了什么：

1. **理解了 Constitution 的定位**：项目级、做一次、只放规矩不放设计
2. **逐个确定了 Constitution 的各个要素**：
   - 架构原则（DDD 四层、关注点分离、模块化）
   - 技术栈（FastAPI + PostgreSQL + JWT）
   - 开发方法论（TDD/BDD）
   - 编码规范与质量标准
   - 安全策略
   - 部署架构
3. **把 Constitution 转化为规则文件**：让 AI 自动遵守

每个要素的构建过程都遵循了渐进式的方法：

- **一句话启动**：不需要写复杂的提示词，一句话就能让 AI 开始
- **对话补充**：AI 的初版不完美，通过 2-3 轮追问补充细节
- **审查验证**：每个产出都要人来把关，AI 不负责决策

**几个关键提醒**：

- **Constitution 不是一成不变的**。项目初期定下来的规矩，后面发现不合适可以改。但改动应该是慎重的、低频的——就像修宪一样。
- **别追求完美**。第一版 Constitution 不可能覆盖所有场景。先把主要的规矩定下来，后面遇到新情况再补充。
- **规矩是给 AI 的约束，也是给自己的约束**。如果你自己都不遵守 Constitution，AI 的产出就会和你的手写代码风格不一致。
