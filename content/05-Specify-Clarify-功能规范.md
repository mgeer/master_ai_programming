# 第五章：Specify & Clarify — 功能规范

## 5.1 引言

**本章目标**：学会为一个 Feature 编写完整的功能规范，并通过 Clarify 查漏补缺。

上一章我们建好了 Constitution——项目的"宪法"。它规定了架构原则、技术栈、编码规范这些"规矩"。但规矩定好了，具体做什么功能，Constitution 一个字都没提。

这就是 Specify 的工作：**把"做什么"写清楚。**

回忆一下 SDD 的完整流程：

```
项目级（一次性）：Constitution           ← 上一章完成了
功能级（每个 Feature）：Specify → Clarify → Plan → Tasks → Implement
                        ↑ 本章 ↑
```

Specify 和 Clarify 是功能级的前两步，它们是一对搭档：

- **Specify**：写出功能规范的第一版——用户故事、功能需求、验收标准
- **Clarify**：审查第一版，找出盲区，补充完善

为什么要把它们放在一起讲？因为**规范的第一版一定有盲区**。你以为自己想清楚了，但 AI 一提问你就发现："哦，这个情况我没考虑到。" Specify 产出初稿，Clarify 打磨终稿——两步合在一起，才能产出一份靠谱的功能规范。

本章的贯穿案例：**Todo 应用的 Feature 1**——CRUD + 认证授权 + 筛选分页。我们会用这个案例完整地走一遍 Specify → Clarify 的全过程。

最终产出物：`.spec/features/001-todo-core/spec.md`

---

## 5.2 功能规范的定位

功能规范是每个 Feature 的起点。在 SDD 中，它的定位非常明确：

**只关注"做什么"和"为什么做"，不关注"怎么做"。**

这个区分至关重要。很多人写需求文档时忍不住就开始写"用 PostgreSQL 存储"、"API 返回 JSON 格式"——这些是"怎么做"，属于后面 Plan 阶段的事。Specify 阶段只需要回答：

- 用户能做什么？
- 系统应该表现出什么行为？
- 怎样算"做完了"？

打个比方：你去餐厅点菜，你会说"我要一份宫保鸡丁，微辣，不要花生"——这是 Specify。你不会说"鸡肉先用生抽腌 15 分钟，油温 180 度下锅"——那是 Plan（厨师的方案设计）。

再看 Specify 和 Constitution 的关系：

| 维度 | Constitution | Specify |
|------|-------------|---------|
| 层级 | 项目级 | 功能级 |
| 做几次 | 一次 | 每个 Feature 做一次 |
| 关注什么 | 规矩（架构、规范、安全…） | 需求（用户要什么） |
| 回答什么问题 | "代码怎么组织、质量怎么保证" | "这个功能做什么、不做什么" |
| 稳定性 | 高（很少改动） | 中（Clarify 阶段会修改完善） |

一句话总结：**Constitution 定规矩，Specify 定需求。规矩约束所有功能，需求只针对当前 Feature。**

## 5.3 规范的核心内容

一份功能规范应该包含哪些东西？五个核心部分：

### 1. 用户故事

用户故事从用户的视角描述需求，格式很简单：

> 作为 [角色]，我希望 [做什么]，以便 [达到什么目的]。

比如：

> 作为一个用户，我希望能创建待办事项，以便记录我需要完成的任务。

用户故事的价值在于**强制你从用户角度思考**。不是"系统提供 POST /todos 接口"，而是"用户能创建待办事项"。听起来差不多？差远了。前者是技术视角，后者是用户视角。技术视角容易遗漏用户真正关心的东西。

### 2. 功能需求

功能需求是对用户故事的展开——系统需要提供哪些具体能力。

比如，"创建待办事项"这个用户故事展开后：

- 用户可以设置标题（必填）
- 用户可以设置描述（选填）
- 创建后默认状态为"待完成"
- 系统自动记录创建时间

### 3. 非功能需求

非功能需求是功能之外的要求——性能、安全、可用性等。

比如：

- API 响应时间 < 200ms（性能）
- 用户只能看到自己的待办事项（安全）
- 列表接口支持分页，每页默认 20 条（可用性）

### 4. 验收标准

验收标准是**可验证的完成条件**。每一条功能需求都应该对应明确的验收标准。

好的验收标准长这样：

> 当用户发送创建请求时，如果标题为空，系统应返回 422 错误。

差的验收标准长这样：

> 系统应该能正常处理错误情况。

区别在于：前者可以直接变成测试用例，后者什么都测不了。

### 5. 边界场景与异常情况

边界场景是最容易被忽略、也最容易出 bug 的地方：

- 标题的最大长度是多少？超过了怎么办？
- 用户没有任何待办事项时，列表接口返回什么？
- 并发情况下两个请求同时修改同一条待办事项怎么处理？

**规范阶段把这些想清楚，比写完代码再发现问题要便宜得多。**

## 5.4 好规范 vs 差规范

在进入实战之前，我们先看看好规范和差规范的区别。这会帮你在审查 AI 产出时快速判断质量。

### 差规范

```markdown
## 功能需求

1. 用户可以管理待办事项
2. 系统要支持认证
3. 列表要能筛选和分页
4. 要处理各种错误情况
```

问题出在哪？

- "管理待办事项"——管理是什么意思？创建？删除？修改？分享？
- "支持认证"——什么认证方式？注册需要什么信息？
- "能筛选和分页"——按什么字段筛选？分页参数是什么？
- "处理各种错误情况"——各种是哪种？

这种规范给 AI，AI 只能自己"脑补"。脑补的结果大概率不是你想要的。

### 好规范

```markdown
## 功能需求

### 待办事项管理

1. 创建：用户可以创建待办事项，必须提供标题（1-200 字符），
   可选提供描述（最多 1000 字符），创建后状态默认为"待完成"
2. 查看：用户可以查看单个待办事项的详情，包括标题、描述、
   状态、创建时间、更新时间
3. 修改：用户可以修改待办事项的标题、描述和状态，
   状态可选值为"待完成"和"已完成"
4. 删除：用户可以删除自己的待办事项，删除为硬删除

### 验收标准

- 创建待办事项时，如果标题为空，返回 422 错误，
  提示"标题不能为空"
- 创建待办事项时，如果标题超过 200 字符，返回 422 错误，
  提示"标题不能超过 200 字符"
- 用户只能查看、修改、删除自己创建的待办事项，
  访问他人的待办事项返回 404
- 查看不存在的待办事项返回 404
```

差异一目了然：

| 维度 | 差规范 | 好规范 |
|------|--------|--------|
| 具体性 | "管理待办事项" | 明确列出 CRUD 四个操作及其细节 |
| 可验证性 | "处理错误" | 明确列出每种错误的触发条件和预期响应 |
| 无歧义 | "支持筛选" | 列出筛选字段、参数格式、默认值 |
| 边界清晰 | 无 | 标题长度限制、空列表处理、权限边界 |

记住三个关键标准：**具体、可验证、无歧义。**

## 5.5 Todo Feature 1 的 Specify 实战

好了，概念讲完了。现在我们来真刀真枪地为 Todo Feature 1 写功能规范。

### 讲

Todo Feature 1 是我们的核心功能，包含三大块：

1. **CRUD**：待办事项的创建、查看、修改、删除
2. **认证授权**：用户注册、登录、权限控制
3. **筛选分页**：按状态筛选、分页查看列表

这是一个典型的"中等复杂度"需求。说简单吧，认证授权和筛选分页有不少细节；说复杂吧，业务逻辑其实很直白。正适合用来演示 Specify 的完整过程。

### 做

#### 第一层：一句话启动

我们先用最简单的提示词开始：

```
我要做一个 Todo 应用的核心功能，包括待办事项的 CRUD、用户认证授权、筛选和分页。
帮我写一份功能规范。
```

就这么简单。不需要告诉 AI 格式怎么写、包含哪些部分——AI 知道功能规范是什么。

AI 会产出一份初版的功能规范。通常它会包含用户故事、功能需求、验收标准这些基本内容。但这个初版一定有问题——模糊的地方、遗漏的细节、过于笼统的描述。

这很正常。**Specify 的第一步不是追求完美，是快速拿到一个可以讨论的基础版本。**

AI 产出的初版通常长这样（节选）：

> ```markdown
> # Feature: Todo 核心功能
>
> ## 用户故事
>
> 1. 作为用户，我希望能注册和登录，以便安全地管理我的待办事项。
> 2. 作为用户，我希望能创建、查看、编辑和删除待办事项，以便管理我的任务。
> 3. 作为用户，我希望能按状态筛选和分页查看待办事项，以便快速找到我需要的任务。
>
> ## 功能需求
>
> ### 用户认证
> - 用户注册（邮箱 + 密码）
> - 用户登录（返回 JWT Token）
> - 认证保护（需要 Token 才能访问其他接口）
>
> ### 待办事项 CRUD
> - 创建待办事项（标题、描述、状态）
> - 查看待办事项列表
> - 查看待办事项详情
> - 更新待办事项
> - 删除待办事项
>
> ### 筛选与分页
> - 按状态筛选（全部、待完成、已完成）
> - 分页支持
>
> ## 验收标准
> - 用户注册后可以登录
> - 登录返回有效的 JWT Token
> - CRUD 操作需要认证
> - 用户只能操作自己的待办事项
> - 列表支持分页和筛选
> ```

看到了吧？初版的问题很多：

- **用户注册需要什么信息？** 只说了"邮箱 + 密码"，邮箱格式验证呢？密码强度要求呢？用户名要不要？
- **待办事项的字段细节呢？** 标题最大长度？描述是否必填？状态有几种？
- **验收标准太泛了**。"CRUD 操作需要认证"——这没法直接变成测试用例。
- **边界场景完全没有**。重复邮箱注册怎么办？删除不存在的 Todo 怎么办？

没关系，这正是我们接下来要通过对话补充来完善的。

#### 第二层：对话补充

看完初版后，我们通过几轮追问来补充细节：

**第一轮：补充认证细节**

```
认证部分需要更具体：
1. 注册需要邮箱和密码，不需要用户名
2. 邮箱必须唯一，格式合法
3. 密码最少 8 位
4. 注册成功直接返回 Token，不需要再登录一次
5. 登录失败不区分"邮箱不存在"和"密码错误"
```

**第二轮：补充 CRUD 细节**

```
待办事项部分需要更详细：
1. 标题必填，1-200 字符
2. 描述选填，最多 1000 字符
3. 状态只有两种：pending（待完成）和 completed（已完成）
4. 创建时默认 pending
5. 用户只能操作自己的待办事项，访问别人的返回 404（不是 403，避免信息泄露）
6. 删除是硬删除
```

**第三轮：补充筛选分页细节**

```
筛选和分页需要明确：
1. 按状态筛选：all / pending / completed，默认 all
2. 支持按创建时间范围筛选（可选的起止日期）
3. 分页参数：page（默认 1）、page_size（默认 20，最大 100）
4. 返回结果包含总数、当前页、总页数
5. 默认按创建时间倒序排列，支持自定义排序字段和方向
```

经过三轮补充，AI 会更新功能规范。更新后的版本会具体得多：

> ```markdown
> # Feature 1: Todo 核心功能
>
> ## 概述
>
> 实现 Todo 应用的核心功能，包括用户认证、待办事项的 CRUD
> 操作、以及列表的筛选与分页。
>
> ## 用户故事
>
> 1. 作为新用户，我希望用邮箱注册账号，以便开始使用 Todo 应用。
> 2. 作为已注册用户，我希望能登录系统，以便访问我的待办事项。
> 3. 作为已登录用户，我希望能创建待办事项，以便记录需要完成的任务。
> 4. 作为已登录用户，我希望能查看待办事项列表，以便了解所有任务的状态。
> 5. 作为已登录用户，我希望能修改待办事项的内容和状态，以便更新任务进展。
> 6. 作为已登录用户，我希望能删除不需要的待办事项，以便保持列表整洁。
> 7. 作为已登录用户，我希望能按状态筛选和分页查看待办事项，
>    以便快速找到特定任务。
>
> ## 功能需求
>
> ### FR-1: 用户注册
>
> - 用户通过邮箱和密码注册
> - 邮箱必须合法且唯一
> - 密码最少 8 个字符
> - 注册成功后直接返回 JWT Token（无需再次登录）
>
> ### FR-2: 用户登录
>
> - 用户通过邮箱和密码登录
> - 登录成功返回 JWT Token
> - 登录失败统一返回"邮箱或密码错误"，不区分具体原因
>
> ### FR-3: 创建待办事项
>
> - 标题：必填，1-200 个字符
> - 描述：选填，最多 1000 个字符
> - 创建后状态默认为 pending（待完成）
> - 系统自动记录创建时间和更新时间
>
> ### FR-4: 查看待办事项详情
>
> - 通过 ID 查看单个待办事项
> - 返回内容：标题、描述、状态、创建时间、更新时间
> - 只能查看自己创建的待办事项
>
> ### FR-5: 查看待办事项列表
>
> - 只返回当前用户的待办事项
> - 支持按状态筛选：all（默认）/ pending / completed
> - 支持按创建时间范围筛选（可选的起止日期参数）
> - 支持分页：page（默认 1）、page_size（默认 20，最大 100）
> - 支持自定义排序字段（created_at / updated_at）和排序方向（asc / desc）
> - 响应包含：数据列表、总数、当前页、总页数
> - 默认按创建时间倒序排列
>
> ### FR-6: 修改待办事项
>
> - 可修改：标题、描述、状态
> - 标题修改后仍需满足 1-200 字符限制
> - 描述修改后仍需满足最多 1000 字符限制
> - 状态可选值：pending / completed
> - 只能修改自己创建的待办事项
> - 修改后自动更新"更新时间"
>
> ### FR-7: 删除待办事项
>
> - 只能删除自己创建的待办事项
> - 硬删除（从数据库中移除）
>
> ## 非功能需求
>
> - NFR-1: API 响应时间 < 200ms（P95）
> - NFR-2: 支持至少 100 个并发用户
> - NFR-3: 数据持久化，服务重启后数据不丢失
>
> ## 验收标准
>
> ### 认证相关
>
> - AC-1: 使用合法邮箱和符合要求的密码注册，返回成功及 Token
> - AC-2: 使用已注册的邮箱重复注册，返回 409 错误
> - AC-3: 使用不合法邮箱注册，返回 422 错误
> - AC-4: 使用少于 8 位的密码注册，返回 422 错误
> - AC-5: 使用正确的邮箱和密码登录，返回 Token
> - AC-6: 登录时邮箱或密码错误，返回 401 并提示"邮箱或密码错误"
> - AC-7: 未携带 Token 访问受保护接口，返回 401
> - AC-8: 携带过期 Token 访问受保护接口，返回 401
>
> ### CRUD 相关
>
> - AC-9: 创建待办事项，标题合法，返回创建成功
> - AC-10: 创建待办事项，标题为空，返回 422
> - AC-11: 创建待办事项，标题超过 200 字符，返回 422
> - AC-12: 查看自己的待办事项详情，返回完整信息
> - AC-13: 查看不存在的待办事项，返回 404
> - AC-14: 查看别人的待办事项，返回 404（不是 403）
> - AC-15: 修改自己的待办事项，返回修改后的内容
> - AC-16: 修改别人的待办事项，返回 404
> - AC-17: 删除自己的待办事项，返回成功
> - AC-18: 删除别人的待办事项，返回 404
> - AC-19: 删除不存在的待办事项，返回 404
>
> ### 筛选分页相关
>
> - AC-20: 不带筛选参数查看列表，返回所有待办事项（分页）
> - AC-21: 按 pending 状态筛选，只返回待完成的项目
> - AC-22: 按 completed 状态筛选，只返回已完成的项目
> - AC-23: 分页参数 page_size 超过 100，返回 422
> - AC-24: 用户没有待办事项时，返回空列表（不报错）
> - AC-25: 列表按创建时间倒序排列
>
> ### 边界与补充
>
> - AC-26: 标题为纯空格（trim 后为空），返回 422
> - AC-27: page 参数为 0 或负数，默认视为 1
> - AC-28: page 超过总页数，返回空列表
> - AC-29: 重复删除同一待办事项，返回 404
> - AC-30: 支持按创建时间范围筛选（created_after / created_before）
> - AC-31: 支持自定义排序字段（created_at / updated_at）和排序方向（asc / desc）
> - AC-32: created_before 早于 created_after 时，返回 422
>
> ### Token 刷新
>
> - AC-33: 使用有效的 Refresh Token 换取新的 Access Token，返回成功
> - AC-34: 使用过期的 Refresh Token 刷新，返回 401
> - AC-35: 使用无效的 Refresh Token 刷新，返回 401
> ```

比起初版，这个版本好很多了。每条需求都有编号，验收标准可以直接变成测试用例。

#### 第三层：完整参考（可选）

> 下面这个完整版提示词**不是必须的**。上面的一句话启动 + 三轮对话补充完全能达到同样效果。放在这里只是给喜欢一次性把事情说清楚的读者参考。

```
为 Todo 应用编写 Feature 1（核心功能）的功能规范。

## 功能范围

1. 用户认证
   - 注册：邮箱 + 密码，邮箱唯一且格式合法，密码最少 8 位
   - 登录：邮箱 + 密码，失败不区分原因
   - 注册成功直接返回 Token

2. 待办事项 CRUD
   - 创建：标题必填（1-200 字符），描述选填（最多 1000 字符），
     默认状态 pending
   - 查看详情：通过 ID，只能看自己的
   - 修改：可改标题、描述、状态（pending/completed），只能改自己的
   - 删除：硬删除，只能删自己的
   - 权限控制：访问别人的资源返回 404（不是 403）

3. 筛选与分页
   - 状态筛选：all（默认）/ pending / completed
   - 分页：page 默认 1，page_size 默认 20（最大 100）
   - 响应含总数、当前页、总页数
   - 按创建时间倒序

## 输出要求

按以下结构输出：
1. 概述（一段话）
2. 用户故事（"作为…我希望…以便…"格式）
3. 功能需求（编号 FR-1, FR-2...，每条包含详细描述）
4. 非功能需求（编号 NFR-1, NFR-2...）
5. 验收标准（编号 AC-1, AC-2...，可直接变成测试用例）
6. 边界场景与异常（列表形式）
```

### 审

拿到 AI 产出的功能规范后，按以下几点审查：

**1. 用户故事是否完整？**

数一下用户故事，看有没有遗漏。Feature 1 至少应该覆盖：注册、登录、创建、查看列表、查看详情、修改、删除、筛选。如果少了某个，补上。

**2. 功能需求是否具体？**

每条需求检查三个标准：具体、可验证、无歧义。

- ❌ "用户可以创建待办事项" → 太模糊
- ✅ "用户可以创建待办事项，标题必填（1-200 字符），描述选填（最多 1000 字符），默认状态为 pending" → 具体

**3. 验收标准能不能直接变成测试用例？**

拿任意一条验收标准，问自己：我能不能根据这条直接写一个 pytest 测试？如果不能，说明它还不够具体。

- ❌ "CRUD 操作需要认证" → 怎么测？
- ✅ "未携带 Token 访问受保护接口，返回 401" → 直接写测试

**4. 边界场景有没有遗漏？**

常见遗漏：
- 空字符串 vs null 的区别
- 超长输入的处理
- 并发操作的行为
- 分页的边界（page = 0 怎么办？page 超过总页数怎么办？）

**5. 有没有混入技术实现？**

如果规范里出现了"用 SQLAlchemy 查询"、"返回 JSON 格式"、"使用 bcrypt 哈希"——这些是实现细节，不应该出现在功能规范里。它们属于 Constitution（规矩）或 Plan（设计方案）。

> **产出物保存路径**：`.spec/features/001-todo-core/spec.md`

## 5.6 为什么要 Clarify

你可能觉得："上面三轮对话补充已经很详细了，功能规范写完了吧？"

**没有。** 功能规范的第一版（即使经过几轮补充）一定有盲区。原因很简单：

1. **你写规范时有思维定式**。你脑子里有一个"理想流程"，沿着这个流程写下去，很容易忽略偏离主流程的情况。
2. **AI 补充时有讨好倾向**。你说什么 AI 就补什么，它不会主动挑战你的假设。你说"删除是硬删除"，AI 就照做——它不会问你"要不要考虑软删除？误删怎么恢复？"
3. **跨功能的影响容易忽略**。你在想"创建 Todo"的时候，不一定会想到这个操作和"认证过期"、"并发冲突"之间的关系。

**Clarify 的目标：在进入 Plan 之前消除歧义。**

Plan 阶段要做领域建模、数据库设计、API 设计——这些都依赖规范的准确性。如果规范有歧义或遗漏，Plan 做出来也是有问题的，最后写代码时就会发现"哎，这个情况规范没说怎么处理"。

Clarify 有三种做法，接下来我们逐一演示：

1. **结构化澄清**：让 AI 系统性地逐条提问
2. **自由补充**：你自己发现的遗漏，主动追加
3. **验收清单审查**：让 AI 逐条检查验收标准是否可执行

---

## 5.7 结构化澄清

### 讲

结构化澄清是让 AI 扮演"挑刺专家"的角色，系统性地审查规范，找出所有不够明确的地方。

关键词是**系统性**。你自己去找漏洞，容易东一个西一个、想到哪儿是哪儿。让 AI 来做，它会按类别逐一排查——认证、CRUD、权限、输入校验、错误处理、边界情况——确保不遗漏。

这其实就是第 2 章讲的"苏格拉底式提问"在 SDD 中的应用：不是 AI 给你答案，而是 AI 向你提问，帮你把没想清楚的地方想清楚。

### 做

#### 第一层：一句话启动

```
审查这份功能规范（@spec.md），找出不够明确的地方，逐条向我提问。
```

注意这里用了 `@spec.md`——这是引用前面 Specify 阶段产出的文件。在 Cursor 中，`@` 可以引用项目文件，让 AI 看到文件内容。

AI 通常会产出一份有组织的问题清单：

> **认证相关：**
>
> 1. 注册时邮箱格式验证的具体规则是什么？只检查 `@` 符号还是做完整的 RFC 校验？
> 2. 密码是否有额外要求？比如必须包含大写字母、数字、特殊字符？还是只要 ≥ 8 位就行？
> 3. 注册成功返回的 Token 是 Access Token 还是同时返回 Access + Refresh Token？
> 4. Token 过期后的刷新流程是什么？用户需要重新登录还是可以用 Refresh Token 换新的？
>
> **待办事项相关：**
>
> 5. 标题和描述是否允许纯空格字符串？比如 "   " 算有效标题吗？
> 6. 修改待办事项时，是否支持部分更新（只传要改的字段）？还是必须传完整对象？
> 7. 状态从 completed 改回 pending 是否允许？
> 8. 描述字段存不存在和描述为空字符串，是一回事吗？
>
> **筛选分页相关：**
>
> 9. page 参数传 0 或负数怎么处理？返回错误还是默认为 1？
> 10. page 超过实际总页数怎么处理？返回空列表还是返回最后一页？
> 11. 是否需要支持按标题关键字搜索？还是只按状态筛选？
>
> **其他：**
>
> 12. 对于同时在线的多个客户端，修改和删除是否需要考虑乐观锁/版本控制？
> 13. 是否有请求频率限制？比如防止暴力破解密码？
> 14. 用户是否可以注销（删除自己的账号）？如果注销，其待办事项如何处理？

看到了吧？这些问题你自己坐在那儿想，不一定能全想到。AI 帮你系统性地梳理了一遍，每个类别都挖了几个坑出来。

现在你需要逐条回答。注意：**不是所有问题都需要加到规范里。** 有些问题的答案是"不做"、"不考虑"——这也要明确说清楚。

```
回答你的问题，请根据我的回答更新功能规范：

认证相关：
1. 邮箱用简单的格式校验（包含 @ 和域名）就行，不需要 RFC 完整校验
2. 密码只要 ≥ 8 位就行，不要求复杂度
3. 注册和登录成功同时返回 Access Token 和 Refresh Token
4. Access Token 过期后可以用 Refresh Token 换取新的 Access Token

待办事项相关：
5. 纯空格不算有效标题，要 trim 后判断
6. 支持部分更新，只传要改的字段
7. 允许从 completed 改回 pending
8. 不传描述字段和传空字符串都行，效果一样

筛选分页相关：
9. page 传 0 或负数，默认当作 1
10. page 超过总页数，返回空列表
11. 本期不做关键字搜索，只按状态筛选

其他：
12. 不考虑并发冲突，不做乐观锁
13. 本期不做请求频率限制
14. 本期不做用户注销功能
```

AI 会根据你的回答更新规范，把这些细节补充进去。

> **操作提示**：如果你使用 Cursor Agent 模式，AI 可以直接修改 `spec.md` 文件。如果使用普通聊天模式，AI 会在对话中输出更新后的规范文本，你需要手动替换 `spec.md` 的内容。建议每次 Clarify 结束后，打开文件确认内容已正确更新。

#### 第二层：对话补充

如果 AI 的问题还不够深入，你可以追加：

```
还有没有遗漏的？特别关注错误处理和安全方面。
```

AI 可能会追加：

> **额外发现：**
>
> 15. 注册时如果邮箱大小写不同（user@test.com vs User@test.com），
>     是否视为同一邮箱？
> 16. 创建待办事项是否有数量上限？比如每个用户最多 1000 条？
> 17. Token 在响应中的返回格式？直接在 body 中还是在 header 中？

继续回答：

```
15. 邮箱不区分大小写，统一转小写存储
16. 本期不限制数量上限
17. Token 在 response body 中返回
```

### 审

结构化澄清结束后，检查这几点：

- **所有问题都有明确回答吗？** 不能留"待定"。要么做，要么明确说不做。
- **"不做"的决定有没有记录？** "本期不做关键字搜索"这样的决定要写进规范的"范围外"部分，避免后面有人问"怎么没有这个功能？"
- **回答是否和 Constitution 一致？** 比如 Constitution 里说了"JWT 支持 Refresh Token"，Specify 里也要保持一致——不能矛盾。
- **AI 有没有把你的回答准确地更新到规范里？** 别信 AI 说"已更新"，自己去看一眼。

## 5.8 自由补充

### 讲

结构化澄清是 AI 找漏洞，自由补充是**你自己找漏洞**。

有时候你突然想到一个点："哎，忘了说——如果用户修改 Todo 的时候只传了 status，标题和描述不变，我要不要返回完整的 Todo 对象？"

这种灵感式的补充不适合走结构化澄清的流程——直接告诉 AI 就行。

自由补充的场景通常有几种：

1. **你在想别的事情时突然意识到的遗漏**
2. **和同事讨论后发现的新需求**
3. **看了竞品后想加的细节**
4. **对之前某个决定的修改**

### 做

#### 第一层：直接追加

```
功能规范补充几点：

1. 所有修改和创建操作成功后，返回完整的 Todo 对象（不只返回成功状态）
2. 列表接口返回的每个 Todo 也要包含完整字段（不要精简版）
3. 增加一个"范围外"部分，明确说明以下内容本期不做：
   - 请求频率限制
   - 用户注销
   - 关键字搜索
   - Todo 数量上限
   - 并发冲突处理
```

#### 第二层：修正之前的决定

有时候你之前的某个决定想改一下：

```
之前说删除是硬删除，我改主意了。改成软删除——标记 deleted_at 时间戳，
但列表接口默认不返回已删除的项目。这样用户误删了还能找回来。

对应的验收标准也要更新：
- 删除后，该待办事项不出现在列表中
- 删除后，通过 ID 查看该待办事项返回 404
```

> 注意：这种需求变更在 Specify 阶段是正常的——**规范就是要在这个阶段反复打磨的**。如果等到写代码时才改需求，成本就高多了。

### 审

自由补充后注意检查：

- **新增内容有没有和已有规范冲突？** 比如上面把"硬删除"改成了"软删除"，所有提到删除的验收标准都要同步更新。
- **"范围外"部分有没有遗漏？** 结构化澄清中所有回答"不做"的项目都应该出现在这里。
- **AI 有没有做对？** 改一个地方可能需要联动改好几个地方。AI 有时候只改了你说的那一条，忘了更新相关的验收标准。

## 5.9 验收清单审查

### 讲

验收清单审查是 Clarify 的最后一步。它的目的很简单：**让 AI 逐条检查验收标准，确认每条都是可执行的。**

前面两步（结构化澄清 + 自由补充）关注的是"有没有遗漏"。这一步关注的是"已经写了的东西，质量行不行"。

具体来说，AI 会检查每条验收标准是否满足三个条件：

1. **可测试**：能不能直接变成一个 pytest 测试用例？
2. **无歧义**：两个不同的人读这条标准，理解是否一致？
3. **完整**：触发条件、操作、预期结果是否齐全？

### 做

#### 第一层：一句话启动

```
逐条审查功能规范（@spec.md）中的验收标准，检查每条是否可测试、无歧义、完整。
已满足的打 ✅，有问题的打 ❌ 并说明原因。
```

AI 的审查结果通常长这样：

> **认证相关：**
>
> - AC-1: 使用合法邮箱和符合要求的密码注册，返回成功及 Token ✅
> - AC-2: 使用已注册的邮箱重复注册，返回 409 错误 ✅
> - AC-3: 使用不合法邮箱注册，返回 422 错误 ❌
>   → 问题：什么算"不合法邮箱"？需要给出具体例子（缺少 @、缺少域名等）
> - AC-4: 使用少于 8 位的密码注册，返回 422 错误 ✅
> - AC-5: 使用正确的邮箱和密码登录，返回 Token ✅
> - AC-6: 登录时邮箱或密码错误，返回 401 ✅
> - AC-7: 未携带 Token 访问受保护接口，返回 401 ✅
> - AC-8: 携带过期 Token 访问受保护接口，返回 401 ✅
>
> **CRUD 相关：**
>
> - AC-9: 创建待办事项，标题合法，返回创建成功 ❌
>   → 问题："返回创建成功"不够具体，应说明返回的内容（完整 Todo 对象 + HTTP 201）
> - AC-10: 创建待办事项，标题为空，返回 422 ✅
> - AC-11: 创建待办事项，标题超过 200 字符，返回 422 ✅
> - AC-12: 查看自己的待办事项详情，返回完整信息 ❌
>   → 问题："完整信息"应列出具体字段列表
> - AC-13: 查看不存在的待办事项，返回 404 ✅
> - AC-14: 查看别人的待办事项，返回 404 ✅
> - AC-15: 修改自己的待办事项，返回修改后的内容 ✅
> - AC-16: 修改别人的待办事项，返回 404 ✅
> - AC-17: 删除自己的待办事项，返回成功 ✅
> - AC-18: 删除别人的待办事项，返回 404 ✅
> - AC-19: 删除不存在的待办事项，返回 404 ✅
>
> **筛选分页相关：**
>
> - AC-20 ~ AC-25: ✅
>
> **缺失的验收标准：**
>
> - 缺少：标题为纯空格时的处理（应返回 422）
> - 缺少：描述超过 1000 字符时的处理
> - 缺少：邮箱大小写统一的验证（User@Test.com 和 user@test.com 注册同一账号）
> - 缺少：修改时只传部分字段的验证
> - 缺少：软删除后通过 ID 查看返回 404 的验证

价值一目了然——AI 帮你找到了 3 条有问题的验收标准和 5 条缺失的验收标准。

#### 第二层：修复问题

```
根据你的审查结果修改规范：

1. AC-3 补充不合法邮箱的具体场景：缺少 @、缺少域名、格式明显错误
2. AC-9 改为：创建待办事项，标题合法，返回 HTTP 201 和完整的 Todo 对象
   （包含 id、title、description、status、created_at、updated_at）
3. AC-12 改为：查看自己的待办事项详情，返回 id、title、description、
   status、created_at、updated_at
4. 补充缺失的验收标准（全部加上）
```

### 审

验收清单审查后做最终确认：

- **所有 ❌ 都修复了吗？** 不要只修一部分就结束了。
- **新增的验收标准质量如何？** 新加的也要满足"可测试、无歧义、完整"三个标准。
- **验收标准的编号是否连续？** 中间有增有删，编号可能乱了。重新编号一下，方便后续引用。
- **总数是否合理？** Feature 1 大概需要 25-30 条验收标准。如果只有 10 条，可能遗漏了很多；如果有 50 条，可能写得太细了。

## 5.10 Clarify 前后对比

走完了结构化澄清、自由补充、验收清单审查，功能规范有了质的提升。我们来直观对比 Clarify 前后的变化。

### 用户注册部分对比

**Clarify 前：**

```markdown
### FR-1: 用户注册

- 用户通过邮箱和密码注册
- 邮箱必须合法且唯一
- 密码最少 8 个字符
- 注册成功后直接返回 JWT Token
```

**Clarify 后：**

```markdown
### FR-1: 用户注册

- 用户通过邮箱和密码注册
- 邮箱格式验证：包含 @ 和有效域名（简单校验，非 RFC 完整校验）
- 邮箱不区分大小写，存储时统一转小写
- 邮箱必须唯一，已注册的邮箱返回 409
- 密码长度 ≥ 8 个字符，无复杂度要求
- 注册成功返回 HTTP 201、Access Token 和 Refresh Token
```

变化：

- 邮箱校验规则从"合法"变成了可执行的具体规则
- 大小写处理明确了
- Token 类型明确了（Access Token + Refresh Token）
- HTTP 状态码明确了

### 验收标准部分对比

**Clarify 前（节选）：**

```markdown
- AC-3: 使用不合法邮箱注册，返回 422 错误
- AC-9: 创建待办事项，标题合法，返回创建成功
```

**Clarify 后：**

```markdown
- AC-3a: 邮箱缺少 @ 符号，注册返回 422
- AC-3b: 邮箱缺少域名（如 user@），注册返回 422
- AC-3c: 邮箱格式明显错误（如 @test.com），注册返回 422
- AC-9: 创建待办事项，标题合法，返回 HTTP 201 和完整的 Todo 对象
  （包含 id、title、description、status、created_at、updated_at）
```

变化：

- 一条模糊的验收标准拆成了三条可测试的具体场景
- "返回创建成功"变成了可验证的具体响应内容

### 新增的内容

Clarify 后，规范多了几个重要部分：

**1. 范围外声明**

```markdown
## 范围外（Out of Scope）

以下功能本期明确不做：
- 请求频率限制
- 用户注销 / 账号删除
- 按标题关键字搜索
- Todo 数量上限
- 并发冲突处理（乐观锁）
- 密码复杂度要求（只要求长度）
```

**2. 边界场景补充**

```markdown
## 边界场景

- 标题为纯空格（trim 后为空），视为无效标题，返回 422
- page 参数为 0 或负数，默认视为 1
- page 超过总页数，返回空列表
- 描述字段不传和传空字符串，效果相同
- 修改时只传部分字段（如只传 status），未传的字段保持不变
- 软删除后，列表中不显示，通过 ID 查看返回 404
```

这些内容在 Clarify 之前完全不存在。**这就是 Clarify 的价值——把"你以为你想清楚了"变成"你真的想清楚了"。**

### Specify 完整提示词

```
为 Todo 应用编写 Feature 1（核心功能）的功能规范文档。

## 功能范围

本 Feature 包含三大块：
1. 用户认证（注册、登录）
2. 待办事项 CRUD（创建、查看、修改、删除）
3. 列表筛选与分页

## 详细需求

### 认证
- 注册：邮箱（唯一、简单格式校验、不区分大小写）+ 密码（≥ 8 位，无复杂度要求）
- 注册和登录成功同时返回 Access Token + Refresh Token
- 登录：邮箱 + 密码，失败统一返回"邮箱或密码错误"
- Access Token 过期后通过 Refresh Token 换取新 Token

### CRUD
- 创建：标题必填（1-200 字符，trim 后不能为空），描述选填（≤ 1000 字符），默认状态 pending
- 查看详情：通过 ID，只能看自己的
- 修改：支持部分更新（只传要改的字段），状态可选 pending/completed，可双向切换
- 删除：软删除（标记 deleted_at），列表不显示，通过 ID 查看返回 404
- 权限：访问别人的资源统一返回 404

### 筛选分页
- 状态筛选：all（默认）/ pending / completed
- 日期范围筛选：可选的 created_after / created_before 参数
- 排序：支持按 created_at / updated_at 排序，支持 asc / desc，默认 created_at desc
- 分页：page（默认 1，≤ 0 当作 1）、page_size（默认 20，最大 100）
- 返回：数据列表、总数、当前页、总页数
- page 超过总页数返回空列表

### 操作响应
- 创建/修改成功：返回完整 Todo 对象（id, title, description, status, created_at, updated_at）
- 列表中每个 Todo 包含完整字段

## 输出格式

按以下结构输出 Markdown 文档：
1. 概述
2. 用户故事（"作为…我希望…以便…"）
3. 功能需求（编号 FR-1, FR-2...）
4. 非功能需求（编号 NFR-1, NFR-2...）
5. 验收标准（编号 AC-1, AC-2...，每条可直接变成 pytest 测试用例）
6. 边界场景与异常
7. 范围外（Out of Scope）
```

### Clarify 结构化澄清提示词

```
你是一位资深产品经理，擅长审查功能规范文档。

请审查这份功能规范（@spec.md），从以下维度逐一排查盲区：

1. 认证与安全：注册/登录流程、Token 管理、错误处理
2. 数据校验：每个字段的类型、长度、格式、必填/选填
3. 业务规则：状态流转、权限控制、删除策略
4. 边界场景：空值、极端输入、分页边界、并发
5. 错误处理：每种错误的 HTTP 状态码和错误信息

对于每个发现的问题，请：

- 说明为什么这是问题
- 提供 2-3 个选项供我选择（如果适用）

## 5.12 本章小结

这一章我们完成了 SDD 功能级的前两步——Specify & Clarify。回顾一下完整流程：

### Specify 阶段

1. **理解了功能规范的定位**：只关注"做什么"，不关注"怎么做"
2. **掌握了规范的五个核心部分**：用户故事、功能需求、非功能需求、验收标准、边界场景
3. **学会了区分好规范和差规范**：关键标准是"具体、可验证、无歧义"
4. **完成了 Todo Feature 1 的 Specify 实战**：通过一句话启动 + 多轮对话补充，产出功能规范初版

### Clarify 阶段

5. **理解了为什么要 Clarify**：第一版规范一定有盲区，在进入 Plan 之前必须消除
6. **三种 Clarify 方式**：
   - **结构化澄清**：让 AI 系统性提问，覆盖各维度的盲区
   - **自由补充**：主动追加你发现的遗漏或变更
   - **验收清单审查**：逐条检查验收标准的可测试性
7. **看到了 Clarify 前后的具体差异**：从模糊到具体，从遗漏到完整

### 渐进式方法回顾

和上一章一样，整个过程不需要复杂的提示词：

| 步骤 | 一句话启动 |
|------|-----------|
| Specify | "我要做一个 Todo 应用的核心功能，帮我写功能规范。" |
| 结构化澄清 | "审查这份规范，找出不够明确的地方，逐条向我提问。" |
| 验收清单审查 | "逐条审查验收标准，检查是否可测试、无歧义、完整。" |

一句话启动，然后在对话中逐步完善——这就是 SDD 的节奏。

### 几个关键提醒

- **别追求完美的第一版**。Specify 阶段快速出初稿，Clarify 阶段精雕细琢。想在第一版就写出完美规范，反而会卡住。
- **"不做"也是规范的一部分**。"范围外"部分非常重要——它防止后面有人（包括未来的你）问"为什么没有这个功能"。
- **规范是活文档**。即使 Clarify 做完了，后面在 Plan 和 Implement 阶段发现新问题，也可以回来更新规范。但频繁大改说明 Specify 和 Clarify 没做到位。
- **验收标准是最有价值的部分**。它们直接变成测试用例——这是 SDD 中规范驱动代码的关键链路。
