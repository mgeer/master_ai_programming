# 第六章：SDD 方法与工具介绍

## 6.1 引言

**本章目标**：理解 SDD 的核心理念，建立"规范先行"的开发直觉，并用工具走完一遍完整流程。

接到一个新需求：为内部系统添加评论功能。小明想着 AI 这么强，直接说需求就行了：

> 帮我做一个评论功能

AI 很快给出了实现：数据库表、API 接口、前端组件，洋洋洒洒两百行。小明合并进主分支。

第二天产品来问：评论支持嵌套吗（回复某条评论）？

小明去问 AI：给现有评论功能加嵌套支持。

AI 改了一版，但架构需要大调整——原来的表结构没有预留父评论字段，现在要加字段、迁移数据、改接口。改完后，产品又问：评论能 @人 吗？

再次大改。三轮下来，评论模块的代码改了又改，没有一致的设计逻辑，测试也断断续续。

小明后来复盘：问题不在于 AI 写的代码质量——问题在于他从来没有想清楚"评论功能到底要做什么"就让 AI 开始写了。需求没想清楚，AI 只能猜。每次 AI 猜错，就是一次大返工。

这个模式很多人都遇到过：

- **对话记忆丢失**：关掉窗口重新开对话，AI 完全不记得上次的设计决策——为什么用软删除、为什么不支持嵌套，它不知道
- **跨会话历史缺失**：过了一周开新对话加功能，要重新解释整个背景，AI 容易做出和之前不一致的设计
- **范围失控**：没有明确"不做什么"，AI 自作主张加了不需要的功能，或漏掉应该有的边界处理
- **决策无据可查**：三个月后回来维护，为什么 API 这样设计、为什么用这个数据结构——没人知道，也找不到记录
- **多人协作失控**：团队每人各自和 AI 对话，设计假设都在各自的对话里，没有书面记录，改动容易互相冲突

根本原因有两个：AI 没有持久记忆，每次对话都是全新开始；同时没有规范文档记录决策，上下文全靠对话承载，对话结束，上下文消失。

---

## 6.2 SDD 是什么

**SDD（Specification-Driven Development，规范驱动开发）**：先写清楚规范，再让 AI 按规范执行。

核心理念只有一句话：**人决策，AI 执行。**

架构怎么设计、边界在哪里、这期不做什么——这些决策由人来做，写进规范文档。AI 负责的是执行：按规范生成代码。

规范文档解决的正是上面那些问题：它是跨会话的持久记录，每次开新对话只需引用文档，AI 就能获得完整上下文；它也是团队的共识载体，让所有人和 AI 在同一份"合同"上工作。

Vibe Coding 的问题不在于"用 AI"，而在于把决策权交给了 AI，同时没有任何持久化记录——AI 只能猜，猜错就返工，每次返工都从零开始。SDD 把决策显式化、文档化，把执行交给 AI。

---

## 6.3 最小化实践：PDCA 循环

SDD 是理念，不绑定工具。用文本编辑器手写规范文档就能落地：

```
Plan  → 写需求规范（做什么、不做什么）；和 AI 澄清边界
Do    → 技术设计 + 拆分任务 + AI 执行
Check → 对照规范检查代码
Act   → 修复偏差，归档，进入下一轮
```

关键是在 **Plan 阶段**写清楚「不做什么」——范围不清是翻车最常见的原因。先写规范的过程本身会暴露需求漏洞，比如「游客能否查看评论」这类遗漏，在动手前澄清比实现后返工代价小得多。

上面这套流程可以纯手动执行。下一节用 OpenSpec 工具自动化它。OpenSpec 的 explore 命令专门服务于 Plan 阶段——帮你在动手前把漏洞逼出来。

## 6.4 OpenSpec 工具实战

### 安装与配置

OpenSpec 是一个 CLI 工具，核心是一套 Skill 文件。

```bash
# 全局安装
npm install -g @fission-ai/openspec

# 配置扩展工作流（交互式，选择包含 new/continue 等命令的配置）
openspec config profile

# 在项目根目录初始化，将 Skill 文件安装到 .claude/skills/
openspec init --tools claude

# 如果项目已初始化过，更新 Skill 文件
openspec update
```

重启 Claude Code 后斜杠命令生效。Skill 文件是斜杠命令的底层机制，详见 Ch7。

### Explore：先和 AI 对齐，再出发

大多数 AI 工具是执行者——你说什么，它做什么。Explore 不一样，它是教练。

```
执行者模式（直接开写）
────────────────────────────────────────
你 ──需求──▶ AI ──代码──▶ 你
      单向传递，AI 只能猜你的意图

教练模式（先 explore）
────────────────────────────────────────
你 ◀──问题── AI
你 ──回答──▶ AI ──"你有没有考虑过…"──▶ 你
你 ◀──图表── AI
你 ──"哦！"─▶（自己想清楚了）
      双向对齐，你和 AI 同时理解清楚
```

好的教练不替你决策，但会问出那个你没问过自己的问题。Explore 的价值正是如此：**帮你发现盲区，帮 AI 理解你**——两件事同时发生。

以「给博客加评论功能」为例：

| 你以为想清楚的 | 实际遗漏的盲区 |
|---|---|
| 登录用户可以发评论 | 游客能看到评论吗？ |
| 作者可以删评论 | 评论可以编辑吗？改了有记录吗？ |
| 评论列表公开可见 | 文章删除后，评论怎么处理？ |
| （未提及） | 账号注销后，评论显示什么名字？ |
| （未提及） | 评论有长度限制吗？ |

每一个遗漏，在需求阶段是一句话，在实现阶段是一次返工。Explore 在动手之前把它们逼出来。

**一段典型的 Explore 对话：**

小明：`/opsx:explore 我想给博客加评论功能，登录用户可以发评论，作者可以删评论，列表公开可见。`

AI 没有立刻说"好的，我来帮你实现"，而是先把问题的形状画出来：

```
  谁能做什么？
  ┌─────────┬────────┬────────┬────────┐
  │  动作   │  游客  │登录用户│  作者  │
  ├─────────┼────────┼────────┼────────┤
  │ 看评论  │   ?    │   ✓    │   ✓   │
  │ 发评论  │   ✗    │   ✓    │   ✓   │
  │ 删评论  │   ✗    │  自己  │  任意  │
  └─────────┴────────┴────────┴────────┘
```

> AI：你说「列表公开可见」，但没提游客——游客能看评论吗？是疏漏还是确实不让看？

小明：啊，游客应该能看，我没想到要说这个。

> AI：既然列表公开，如果一个注销账号的用户发过评论，评论里的名字显示什么？

小明：……我完全没想过这个。

> AI：我看了你的数据库结构，articles 表用了 `deleted_at` 做软删除——comments 要保持一致吗？

小明：对，软删除，和文章保持一致。

一次 explore，发现了 1 个权限盲区、1 个边缘情况、1 个架构一致性问题。这些问题在对话里解决只需几分钟，留到实现阶段每个都是一次返工。

**如何使用 explore：可以带任何东西进来**

| 输入类型 | 示例 |
|---|---|
| 模糊想法 | `/opsx:explore 想给系统加个消息通知` |
| 具体问题 | `/opsx:explore 现在的权限系统越来越难维护` |
| 技术选型 | `/opsx:explore 用 Redis 还是数据库存 session` |
| 实现卡住了 | `/opsx:explore add-comment-feature`（带变更名，AI 会读已有工件继续探索） |
| 什么都没有 | `/opsx:explore`（AI 会先问你想聊什么） |

不需要想清楚了再进来。正因为没想清楚，才更需要 explore。

Explore 没有副作用——不写代码、不强制产出文档、不催你做决定，随时可进、随时可退。它是一种思维模式，不是流程里的一个步骤，不只是开始阶段才能用，实现到一半发现问题时也可以随时回来。

> 每次进 explore，都像是有个经验丰富的工程师坐在你旁边，帮你把问题想透再动手。

### 扩展工作流

OpenSpec 的扩展工作流把 PDCA 拆成一组命令。先理解三个核心工件的关系——顺序是 **proposal → design → spec**：

| 工件 | 回答什么问题 | 性质 |
|------|-------------|------|
| **Proposal（提案）** | 为什么做？做什么？影响范围？ | 问题定义 + 范围界定 |
| **Design（设计）** | 怎么做？架构决策是什么？ | 技术方案 + 关键决策 |
| **Spec（规格）** | 做到什么程度算「做完了」？ | 可验证的验收标准 |

类比理解：Proposal ≈ PRD，Design ≈ 架构设计文档，Spec ≈ 验收标准。

**命令与工件依赖：**

| 命令 | 作用 |
|------|------|
| `/opsx:explore` | 先和 AI 双向对齐：发现盲区、厘清思路，不写代码、不强制产出 |
| `/opsx:new` | 创建变更目录，初始化工件结构 |
| `/opsx:continue` | 生成下一个工件（依次：proposal → design → spec → tasks） |
| `/opsx:apply` | 按任务清单逐条实现代码，完成一条打勾一条 |
| `/opsx:archive` | 归档完成的变更，清理工作目录 |

```
proposal → design → spec → tasks → apply → archive
```

工件驱动的关键：每个阶段产出明确的文档，下一步以上一步的文档为输入——不依赖对话记忆。

> **Spec 依赖 Design**：Spec 不是收集用户原始需求的地方，而是把 Design 的决策转化为可验证的规格。例如 Design 决定了「软删除」，Spec 才写「SHALL 包含 deleted_at 字段」。先有设计决策，才有验收标准。

---

### 案例：为博客系统添加评论功能

以小明的案例为例，用扩展工作流重来一遍。

**Step 1：探索需求**

```
/opsx:explore 想给博客加评论功能
```

几分钟对话，厘清了游客权限、账号注销处理、软删除一致性等边界。带着这份共识进入下一步，后续返工大幅减少。

**Step 2：创建变更**

```
/opsx:new add-comment-feature
```

在 `openspec/changes/add-comment-feature/` 创建变更目录，等待生成工件。

**Step 3：逐步生成工件（continue × 4）**

```
/opsx:continue   # 生成 proposal.md（变更意图与范围）
/opsx:continue   # 生成 design.md（技术设计）
/opsx:continue   # 生成 spec（可验证的验收规格，基于 design 决策）
/opsx:continue   # 生成 tasks.md（任务清单）
```

`proposal.md` 示例片段（问题与范围）：

```markdown
## 为什么做
为博客增加评论能力，提升用户互动。

## 做什么 / 不做什么
- 本期：登录用户发评论、评论者可删自己的、作者可删任意、列表公开可见
- 不做：嵌套回复、审核机制、匿名评论
```

`design.md` 示例片段（技术决策）：

```markdown
## 数据模型
comments 表：id, article_id, user_id, content, created_at, deleted_at

## 技术决策
- 软删除（deleted_at 字段）：保留审计追踪
- API：POST /articles/:id/comments、DELETE /comments/:id（含权限校验）
```

`spec` 示例片段（可验证验收标准，由 design 转化而来）：

```markdown
### Requirement: 评论发表
系统 SHALL 允许已登录用户对文章发表评论。

#### Scenario: 发表成功
- WHEN 用户已登录且提交有效评论内容
- THEN 系统创建评论记录并返回 201
```

**Step 4（关键）：人工审查 design 与 spec**

小明读 design 和 spec，确认技术决策和验收条款一致、没有遗漏。发现问题直接编辑文档——决策在文档里做，不让 AI 猜。

**Step 5：实现**

```
/opsx:apply
```

AI 按任务清单逐条实现，完成一条打勾一条：

```
- [x] 建 comments 数据库迁移文件
- [x] 实现 Comment 数据模型
- [x] 实现 POST /articles/:id/comments 接口
- [x] 实现 DELETE /comments/:id 接口（含权限校验）
- [x] 在文章详情页展示评论列表
- [x] 编写接口测试
```

**Step 6：归档**

```
/opsx:archive
```

归档变更，清理工作目录。下一期要加嵌套回复时，重新从 `/opsx:explore` 开始。

---

## 6.5 要点

- **先 explore 再动手**：不管需求是否清晰，先和 AI 双向对齐——盲区在对话里解决比实现后返工代价小得多
- **规范的最低标准**：写了「不做什么」就算合格——大多数翻车源于范围不清
- **人工审查不能跳过**：design 和 spec 生成后，必须人工确认技术决策与验收条款一致，再进入实现
- **何时用 SDD**：需要长期维护的功能、多人协作、需求可能扩展的场景。一次性脚本不必

---

## 6.6 本章小结

- SDD = 先写规范，人决策，AI 执行
- 最简实践：Plan（需求规范 + 澄清边界）→ Do（技术设计 + 拆任务 + AI 执行）→ Check（对照规范）→ Act
- OpenSpec 把上述流程工具化：先 explore（双向对齐）→ new → continue（proposal → design → spec → tasks）→ apply → archive
- 核心不变：决策显式化，不依赖对话记忆，不让 AI 猜

**练习**：用 OpenSpec 为你当前项目的一个真实小需求走一遍流程：`/opsx:explore` 探索需求，`/opsx:new` 创建变更，`/opsx:continue` 依次生成 proposal、design、spec、tasks，完成 design 与 spec 的人工审查。
