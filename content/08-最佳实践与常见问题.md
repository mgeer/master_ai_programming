# 第八章：最佳实践与常见问题

## 8.1 引言

前面七章讲了完整的方法论：CRC → 多轮对话 → CODE（BASER + STIR）。

这些方法论是**脚手架**，不是标准答案。它给你一个起点和框架，但**真正的最佳实践要你自己在实践中摸索出来**。

每个人的技术背景不同、项目场景不同、思维习惯不同——别人总结的经验可以参考，但只有你自己踩过的坑、总结过的规律，才是真正属于你的最佳实践。

这一章分享一些起步阶段的经验，供你参考和验证。**更重要的是：鼓励你在使用过程中，不断总结、迭代、形成自己的方法。**

## 8.2 一些起步建议

### 1. 不要盲目信任 AI 的输出

AI 的代码可能：
- 看起来对，但有隐藏的逻辑错误
- 使用了过时的 API 或废弃的库
- 在特定边界条件下崩溃

**原则：AI 写的每一行代码，都要当作"新同事提交的 PR"来对待——Review 后再合并，不是直接用。**

测试先行（STIR 的 T）就是最好的防线。

### 2. 小步迭代，而不是一次性生成

```
❌ "帮我实现整个用户管理模块"
✅ "帮我实现用户注册接口"
```

每次让 AI 做一个小任务，完成后验证，再做下一个。原因：
- 小任务的上下文更集中，AI 输出质量更高
- 出了问题容易定位
- 你始终掌握对代码的理解

### 3. 保持对代码的理解

AI 生成的代码，如果你看不懂，就不要用。

看不懂有两种可能：
- **AI 用了你不熟悉的技巧**：让 AI 解释清楚，学会了再用
- **AI 写得太复杂了**：让 AI 简化，用你能理解的方式重写

**你不理解的代码，你就无法维护。**

### 4. 善用规则文件积累团队经验

规则文件是团队知识的沉淀——每次遇到"AI 总犯的错误"或"团队的特殊要求"，都加进去。规则越具体，AI 输出越符合预期。具体的积累方式见 8.5 节。

### 5. 把 AI 的输出作为起点，不是终点

AI 生成的代码是"初稿"，不是"定稿"。最好的工作方式是：

1. 让 AI 快速生成初版
2. 你在初版基础上调整、优化
3. 让 AI 审查你的修改

这样既利用了 AI 的速度，又保留了你的判断力。

### 6. 管理对话上下文

AI 的上下文窗口是有限的。对话太长，AI 会"忘记"早期的讨论内容。

**实操建议**：
- 一个 STIR 任务一个对话——完成后开新对话做下一个任务
- 每次新对话开头，通过文件引用提供关键上下文（如 `@docs/requirements.md`、`@docs/tech-architecture.md`）
- 如果在同一个对话中工作超过 15-20 轮，让 AI 先总结当前进展并保存到文件，然后开新对话通过 `@` 引用该文件
- 把重要的设计决策保存到文档中（而不是只留在对话里），这样即使对话丢失也不影响后续工作

**文档就是 AI 的长期记忆。** 你在 CODE 各阶段产出的文档（需求、架构、任务清单），本质上就是在帮 AI "记住"项目的上下文。

## 8.3 常见问题

### Q1：AI 生成的代码跑不起来怎么办？

**先自己看错误信息**，判断是什么类型的问题：
- **语法错误**：直接把错误信息发给 AI，让它修复
- **依赖缺失**：检查是否安装了所需的库
- **环境问题**：检查 Python 版本、数据库连接等
- **逻辑错误**：把错误现象和预期行为一起发给 AI
- **API 不存在或参数不对**：AI 可能使用了不存在的函数或过时的 API（见 Q6）

**关键：不要只说"跑不起来"，要把具体的错误信息给 AI。**

### Q2：AI 总是不按我的要求输出怎么办？

检查三个方面：
1. **Context 够不够？** 技术栈、已有代码、项目结构是否说清楚了
2. **Requirement 够不够具体？** "写一个函数"太模糊，"写一个接收 X 返回 Y 的函数"才具体
3. **Constraint 够不够明确？** 有没有告诉 AI 不要做什么、必须遵循什么

大多数情况下，回到 CRC 三要素重新审视你的提示词，就能解决问题。

### Q3：什么时候该用 AI，什么时候该自己写？

| 适合用 AI | 适合自己写 |
|-----------|-----------|
| 标准的 CRUD 接口 | 核心业务算法 |
| 测试用例生成 | 涉及敏感数据的逻辑 |
| 样板代码（配置、模型定义） | 你需要深入理解的代码 |
| 文档编写 | 性能关键路径 |
| 代码审查和 bug 查找 | 涉及复杂状态管理 |
| 重构和代码优化 | 你无法验证正确性的专业领域（如密码学实现、金融精度计算） |

**经验法则：如果你能清晰描述"要做什么"和"怎么验证做对了"，就适合用 AI；如果你自己都说不清楚要什么，先想清楚再用 AI。**

### Q4：AI 编程会让我的技术退步吗？

**不会，前提是你用对方法。**

- 如果你把 AI 当作"黑盒代码生成器"，不看不想直接用——会退步
- 如果你把 AI 当作"协作伙伴"，Review 每段代码、理解每个设计——不仅不会退步，还能从 AI 的输出中学到新东西

CODE 方法论的设计就确保了这一点：**你始终在做决策（C 和 O），AI 在做执行（D），你在做验收（E）**。思考的责任始终在你手上。

### Q5：团队如何协作使用 AI 编程？

1. **统一开发规范**：规则文件纳入版本控制，所有人的 AI 输出风格一致
2. **共享提示词模板**：把有效的提示词存为团队资源
3. **Code Review 不变**：AI 生成的代码也要走团队的 Review 流程，特别注意边界条件和错误处理
4. **分享经验**：定期交流 AI 使用技巧和踩过的坑
5. **善用版本控制**：每完成一个 STIR 的 T→I→R 循环后 commit；commit 前做 git diff 审查 AI 的改动；不要让 AI 一次改太多文件

### Q6：AI 使用了不存在的函数或过时的 API 怎么办？

这叫"AI 幻觉"——AI 编造了看起来合理但实际不存在的代码。这是 AI 编程中最常见的问题之一。

**识别方法**：
- 函数调用报 `AttributeError` 或 `ImportError`
- 参数签名和官方文档不一致
- 库版本和 AI 使用的 API 对不上

**应对策略**：
1. **在规则文件中锁定版本**：写明 `使用 Pydantic v2（不是 v1）`、`使用 SQLAlchemy 2.0 语法`，减少 AI 混淆新旧版本
2. **要求 AI 解释依据**：问"你使用的这个函数来自哪个库的哪个版本？"，AI 解释不出来时通常就是编造的
3. **把错误信息和正确的 API 文档一起给 AI**：比如"这个函数不存在，正确的用法见官方文档 [粘贴]，请修正"
4. **测试先行是最好的防线**：先写测试再实现，AI 编造的 API 在跑测试时会立刻暴露

### Q7：已有项目怎么用这套方法论？

不需要对已有项目走完整的 CODE 流程。可以根据需求灵活切入：

- **新增功能**：从 STIR 切入——拆解任务、写测试、让 AI 实现、审查
- **重构优化**：先用 CRC 描述清楚重构目标和约束，再让 AI 辅助
- **建立规范**：先建立规则文件（R），把现有项目的编码规范写进去，后续 AI 输出就会遵循
- **提供上下文**：用文件引用让 AI 了解已有代码结构，比从零开始更需要充分的 Context

**核心原则不变**：人做决策，AI 做执行，测试做保障。

## 8.4 练习

回顾你在前面章节的练习过程，完成以下反思练习：

1. **记录 3 个你踩过的坑**：AI 输出不符合预期的情况，你是怎么发现的、怎么解决的？
2. **记录 3 个有效的做法**：哪些提示词写法或对话策略让你觉得效果特别好？
3. **整理成你自己的"AI 编程备忘录"**：可以是一个文档、一个笔记，也可以直接写进规则文件

这份备忘录就是你的个人最佳实践的起点。

## 8.5 如何形成自己的最佳实践

以上只是起步建议，不是标准答案。**真正有价值的最佳实践，是你自己总结出来的。**

### 建议的积累方式

1. **记录有效的提示词**：遇到好用的提示词，保存下来。时间长了你会积累出一套适合自己和团队的"提示词库"
2. **记录踩过的坑**：AI 犯过的错、你发现的规律、有效的纠正方法——这些经验比任何教程都有价值
3. **持续完善规则文件**：每次发现"AI 总犯的错误"或"团队的特殊要求"，加进去。例如：
   - `所有查询必须通过 ORM，禁止拼接原生 SQL`
   - `新增表必须包含 created_at 和 updated_at 字段`
   - `所有列表查询默认按 created_at 倒序`
4. **团队分享**：定期交流各自的 AI 使用技巧和经验，别人的实践可以启发你

### CRC / CODE / BASER / STIR 也不是一成不变的

随着你的经验积累，你可能会发现：
- CRC 的某些场景可以更简化
- CODE 的某些环节在你的项目中可以合并
- BASER 的某个要素在你的领域需要扩展
- STIR 的某个步骤你有更好的替代方式

**这是正常的，也是我们鼓励的。方法论是起点，不是终点。** 当你能根据自己的实践改进方法论的时候，说明你已经真正掌握了它。

## 8.6 本章小结

**核心心法：**

- AI 是工具，你是工程师。工具再好，决策权在你手上
- 方法论是脚手架，最佳实践要自己长出来
- 持续记录、总结、迭代——这本身就是工程师最重要的能力
