# 第九章：SDD 工具实战

## 9.1 引言

**本章目标**：用工具走完一遍 SDD 流程，把前八章的知识整合为完整的开发工作流。

Ch6 讲了 SDD 方法论，你用文本编辑器手写了三层文档。现在用工具自动化这个过程——工具不改变方法，只是把重复劳动交给 AI。

---

## 9.2 SDD 工具生态

| 工具 | 出品方 | 方式 | 特点 |
|------|--------|------|------|
| GitHub Spec Kit | GitHub 官方 | 斜杠命令（`/speckit.specify` 等） | 轻量，搭配现有 AI 助手使用 |
| OpenSpec | 开源社区 | 斜杠命令（`/opsx-propose` 等） | 工件驱动，结构清晰，基于 SKILL 实现 |
| Kiro | AWS | 图形界面 | 可视化工作流，IDE 集成；2025 年发布 |

本章以 **OpenSpec** 为主：它是基于 SKILL（Ch7）实现的——你在 Ch7 学会创建 `/code-review`，OpenSpec 的三个命令是完全相同的机制。

---

## 9.3 OpenSpec 是什么

OpenSpec 本质是三个 Skill 文件：

- `/opsx-propose`：输入变更意图，AI 生成需求文档（为什么）+ 设计文档（如何）+ 任务清单（步骤）。工具将需求、设计、任务拆分一次性完成，但人工审查设计文档的决策点不能跳过
- `/opsx-apply`：按任务清单逐条实现代码，完成一条打勾一条
- `/opsx-archive`：归档完成的变更，清理工作目录

工件驱动：每个阶段有明确的文档产出，不依赖对话记忆——这是与 Vibe Coding 的根本区别。

---

## 9.4 案例：完整走一遍 SDD 流程

以"为博客系统添加评论功能"为例：

**Step 1**：`/opsx-propose 为博客文章添加评论功能`

AI 生成三份文档：需求文档、设计文档、任务清单。

**Step 2（关键）**：人工审查设计文档

> 评论是否支持嵌套回复？是否需要审核机制？作者能否删除他人评论？

这一步是 SDD 与 Vibe Coding 的核心区别——你在这里做决策，AI 在后面执行。修改设计文档，确认后再进入下一步。

**Step 3**：`/opsx-apply`

AI 逐条实现任务清单，完成一条打勾一条。

**Step 4（检查）**：对照规范文档 review 代码

> 根据以下规范文档，检查实现代码：1）任务清单每条是否都已实现？2）设计决策是否正确落地？3）有没有超出规范范围的额外实现？
> [粘贴规范文档 + 关键代码]

发现问题则修改，符合规范后进入下一步。

**Step 5**：`/opsx-archive`

归档，清理工作目录，准备下一个功能迭代。

---

## 9.5 要点

- **工具选择**：小团队/个人用 OpenSpec 或 Spec Kit；偏好可视化用 Kiro
- **关键认知**：`/opsx-propose` 等命令与 Ch7 的 `/code-review` 是同一种机制——都是 `.md` 文件驱动的 Skill
- **迭代**：archive 之后再次 propose，就是下一轮迭代——这就是完整的 AI 辅助开发循环
- **延伸**：参考 OpenSpec 的结构，可以为自己的项目创建定制化的 SDD 工作流 Skill

---

## 9.6 本章小结

- SDD 工具 = 自动化三层文档生成 + 任务驱动实现
- 工具不改变方法论，只是把重复劳动交给 AI
- "人工审查设计文档"和"对照规范检查代码"，是流程中最不该跳过的两步

**练习**：安装 OpenSpec（参考附录"工具与项目"一节获取链接，或直接在附录链接的 GitHub 仓库查找安装说明），用 `/opsx-propose` 为你当前项目的一个真实小需求生成三份文档，完成人工审查设计文档这一步。

**讲师备注**：建议培训前预先验证 OpenSpec 安装流程，确认所用 Claude Code 版本支持相应 Skill 触发方式。

**结语**：你已经掌握了从提示词到 Agent、从规范到工具的完整 AI 编程工作流。工具会持续迭代，但"让 AI 按你的规矩干活"的核心方法不会变。
