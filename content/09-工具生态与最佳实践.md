# 第九章：工具生态与最佳实践

## 9.1 引言

**本章目标**：了解 SDD 工具生态，掌握实践中的常见问题和应对策略。

前面八章，我们从零走完了 SDD 的全流程：Constitution → Specify → Clarify → Plan → Tasks → Implement，还用 Feature 2 跑了一遍迭代循环。

到这里，你已经具备了独立使用 SDD 的能力。

这一章换个节奏——探讨 SDD 周边的"软知识"：有哪些工具可以帮你更高效地实践 SDD？实战中有哪些坑？什么场景该用 SDD，什么场景不用？

> **提示**：工具信息以 2025 年中为准，具体用法请参阅官方文档。

## 9.2 工具生态

### 9.2.1 GitHub Spec Kit

**Spec Kit 是什么？**

Spec Kit 是 GitHub 官方出品的 SDD 工具，定位是"规范驱动开发的标准化工具链"。它将前面提到的手动创建 `.spec/` 目录、生成规范文档、管理 Feature 生命周期等流程自动化封装。

**怎么用？**

在兼容的 AI 编程助手（如 Cursor）中，使用 `/speckit.constitution`、`/speckit.specify` 这样的斜杠命令即可触发对应阶段，生成标准化的目录结构和文档模板：

````markdown
.speckit/
├── constitution.md     # 项目宪章
└── features/           # 功能规范目录
    └── todo-core/
        ├── spec.md     # 功能规范
        ├── plan.md     # 技术方案
        └── tasks.md    # 任务清单
````

> **注意**：请以 [GitHub Spec Kit 官方仓库](https://github.com/github/spec-kit) 为准了解最新用法。

**说明**

- Spec Kit 工具无关，能与任何 AI 助手配合（如 Cursor、Claude Code、GitHub Copilot、Windsurf）。
- 它能够将项目宪章转换为各个工具所需的规则文件格式（如 `.cursor/rules/`、`CLAUDE.md`）。

---

### 9.2.2 其他 SDD 工具

除了 Spec Kit，还有一些工具在相似理念下提供了不同的侧重点：

- **Kiro**：AWS 推出的 AI IDE（基于 VS Code），内置 Requirements → Design → Tasks → Implementation 工作流，完全图形化操作。
- **Qoder**：侧重规范的版本控制和变更追踪，当修改规范时，自动识别需同步更新的代码。

**怎么选？**

| 工具 | 优势 | 适合场景 |
|------|------|---------|
| Spec Kit | GitHub 官方、轻量 | 通用项目，搭配已有 AI 助手 |
| Kiro | IDE 集成、可视化流程 | 偏好图形界面、AWS 生态 |
| Qoder | 规范变更追踪 | 规范频繁迭代的项目 |

工具的核心都是：**先写规范，再写代码。** 即使纯手工管理 `.spec/` 目录，只要遵循流程也能达到预期效果。

---

### 9.2.3 AI 编程助手的选择

SDD 能够与不同的助手良好结合，但体验略有差异：

- **Cursor**：基于 VS Code，对 SDD 极其友好。`.cursor/rules/` 文件系统能自动加载 Constitution 规则，上下文管理（如 `@spec.md`）快捷高效。
- **Claude Code**：命令行工具，支持 `CLAUDE.md`，拥有大上下文窗口，适合需要处理复杂领域模型的场景。
- **GitHub Copilot**：IDE 插件，支持 `.github/copilot-instructions.md`，与 GitHub 生态深度绑定。
- **Windsurf**：基于 VS Code，支持 `.windsurfrules`，Cascade 模式便于多步执行。

**实用建议**：选择助手时，确保其支持"规则文件"或"项目级指令"。这是 SDD 落地并让 AI 持续读取 Constitution 的关键保障。

## 9.3 最佳实践

### 9.3.1 SDD 适用场景 vs 不适用场景

SDD 绝非银弹。在特定场景下它无可替代，在其他场景则可能导致过度工程。

**适合场景**：生产级项目、团队协作、复杂业务逻辑、长期维护项目、多 Feature 迭代。

**不适合场景**：快速原型 (PoC)、一次性脚本、实验探索、极小的局部修改。

**混合使用策略**：
- **大 Feature**：完整走 SDD（Specify → Clarify → Plan → Tasks → Implement）。
- **中 Feature**：简化流程（简短 spec，简单 plan）。
- **小改动**：CRC 对话直接完成。

只有风险高的部分才值得用完整的重流程应对。

---

### 9.3.2 常见误区与踩坑经验

- **误区 1：规范写得太细**
  不要将规范当成"像素级设计稿"。规范负责"做什么"，把"怎么做"留给后续阶段。
- **误区 2：规范写得太粗**
  至少必须包含用户故事、功能需求及验收标准。
- **误区 3：不审查 AI 产出**
  AI 可能过度设计、编造版本号或自相矛盾。必须由人来决策并审查其生成内容。
- **误区 4：Constitution 塞入领域模型**
  Constitution 只存放全局规矩，具体的业务模型应放入 Plan，以免规章臃肿混淆。
- **误区 5：代码改了规范没跟上**
  需求变更时必须先更新规范文档，确保它是唯一的"真相源"。
- **误区 6：每次对话从头交代**
  利用好工具的规则文件加载机制，避免每次重复粘贴内容。

### 9.3.3 Constitution 的演进

Constitution 会随项目成长而迭代：

**什么时候需要修改？**
引入新技术（如 WebSocket）、架构升级（单体转微服务）、原有规范失效或安全要求变更。

**"修宪"四步法**：
1. **评估影响**：梳理改动涉及的已有模块和代码。
2. **记录原因**：在文档的变更记录中解释修改动因。
3. **同步更新**：重写由其生成的规则文件。
4. **通知团队**：在团队项目中，修改需走 PR 审查。

---

### 9.3.4 在已有项目中引入 SDD

不可停工重构，建议采用**渐进式引入**：

1. **只写 Constitution（1-2 小时）**：快速梳理现有技术栈、架构、编码规范。
2. **新 Feature 按 SDD 走**：基于现有项目基础，新功能按流程拆解开发。
3. **补写关键 Feature 规范**：遇到重构时再通过 AI 反向生成已有模块的规范。
4. **团队推广**：以示范性 Feature 证明价值，逐步形成共识。

---

### 9.3.5 从个人到团队的扩展

**个人项目简化版**：
个人开发可精简流程，但 **Specify 和 Plan 不能省**。确保需求有落点，设计有依据。

**团队协作中的 SDD**：
规范文档成为团队的沟通载体。
- **起草与审查**：技术负责人起草 Constitution，全员参与 Review。
- **审查前移**：在 Plan 阶段通过 PR 发现架构冲突，远比写完代码再发现要高效得多。
- **新成员 Onboarding**：读一遍 `.spec/` 目录便能迅速了解项目整体轮廓和规范历史。
- **多 AI 协作**：统一的 Constitution 确保无论多少人或 Agent 并行，代码风格和设计都能保持高度一致。

---

## 9.4 本章小结

**工具生态**：
- GitHub Spec Kit 提供标准的 SDD 工具链支持。
- AI 助手的选择应兼顾个人习惯并支持配置规则文件。

**最佳实践**：
- 按需调整 SDD 流程的深度。
- 规避太细或太粗的规范编写，坚守"人决策、AI 执行"的审查防线。
- 采用"修宪四步法"有序推进 Constitution 变更。
- 在旧项目中采取渐进式的引入策略。
- 团队应用中，以规范文档前置审查取代事后的代码救火。
