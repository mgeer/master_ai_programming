# 第九章：工具生态与最佳实践

## 9.1 引言

**本章目标**：了解 SDD 工具生态，掌握实践中的常见问题和应对策略。

前面八章，我们从零走完了 SDD 的全流程：Constitution → Specify → Clarify → Plan → Tasks → Implement，还用 Feature 2 跑了一遍迭代循环。

到这里，你已经具备了独立使用 SDD 的能力。

这一章换个节奏——不做项目、不写提示词，而是聊聊 SDD 周边的"软知识"：有哪些工具可以帮你更高效地实践 SDD？实战中有哪些坑？什么场景该用 SDD，什么场景不用？

> **提醒**：工具会更新换代，本章介绍的工具信息以写作时（2025 年中）为准。具体命令和用法请以官方文档为准。

## 9.2 工具生态

### 9.2.1 GitHub Spec Kit

**Spec Kit 是什么？**

Spec Kit 是 GitHub 官方出品的 SDD 工具，定位是"规范驱动开发的标准化工具链"。它把我们在前面章节中手动做的事情——创建目录结构、生成规范文档、管理 Feature 生命周期——封装成了命令行工具。

简单说：我们前面手动创建 `.spec/` 目录、手动组织 `spec.md`、`plan.md`、`tasks.md`——Spec Kit 帮你用一条命令搞定。

**怎么用？**

Spec Kit 主要通过 AI 编程助手内的**斜杠命令**（Slash Commands）来工作，而不是独立的 CLI 工具。例如在 Cursor 中，你可以使用类似 `/speckit.constitution`、`/speckit.specify` 这样的命令来触发对应的 SDD 阶段。

Spec Kit 会在项目中创建 `.speckit/` 目录来管理规范文档：

```
.speckit/
├── constitution.md     # 项目宪章
└── features/           # 功能规范目录
    └── todo-core/
        ├── spec.md     # 功能规范
        ├── plan.md     # 技术方案
        └── tasks.md    # 任务清单
```

> **注意**：Spec Kit 仍在快速迭代中，具体的命令名称、目录结构和用法可能会发生变化。以上信息以写作时为准，请以 [Spec Kit 官方文档](https://github.com/nicholaschuayunzhi/speckit) 为准。

**几点说明**

- Spec Kit 的目录名和本书使用的 `.spec/` 可能不同，但理念完全一致。如果你已经按本书前面的方式组织了规范文档，切换到 Spec Kit 的迁移成本很低。
- Spec Kit 生成的模板文件预设了标准的章节结构，你可以直接在模板基础上用 AI 填充内容。
- Spec Kit 支持与多种 AI 编程助手配合使用——它不绑定特定的 AI 工具。

**支持的 AI 助手**

Spec Kit 设计为工具无关，它生成的规范文档可以被任何 AI 助手读取。官方文档列出的支持列表包括：

- Cursor（通过 `.cursor/rules/` 加载规则）
- Claude Code（通过 `CLAUDE.md` 加载规则）
- GitHub Copilot（通过 `.github/copilot-instructions.md` 加载规则）
- Windsurf（通过 `.windsurfrules` 加载规则）

不管你用哪个 AI 助手，Spec Kit 都能把项目宪章转化为对应的规则文件格式。

### 9.2.2 其他 SDD 工具

SDD 不只有 Spec Kit。市面上还有几个值得关注的工具，它们的理念相似，但切入角度不同。

**Kiro**

Kiro 是 AWS 推出的 AI IDE（基于 VS Code），内置了规范驱动的工作流。它的核心流程是：

```
Requirements → Design → Tasks → Implementation
```

和 SDD 的 Specify → Plan → Tasks → Implement 几乎一一对应。不同的是，Kiro 把这个流程直接做进了 IDE 的 UI——你不需要手动管理 Markdown 文件，而是在 IDE 界面里点击按钮推进各个阶段。

适合什么人？如果你更喜欢图形化界面、不想手动管理文件，Kiro 是个不错的选择。

**Qoder**

Qoder 的定位是"规范即代码"——它把规范文档当作一等公民，和源代码一样管理。Qoder 的特点是强调规范文档的版本控制和变更追踪：当你修改了规范，Qoder 会自动识别哪些代码需要同步更新。

适合什么人？如果你的项目规范变动频繁，需要严格追踪规范和代码的对应关系，Qoder 值得一试。

**怎么选？**

| 工具 | 优势 | 适合场景 |
|------|------|---------|
| Spec Kit | GitHub 官方、工具无关、轻量 | 通用项目，搭配已有 AI 助手 |
| Kiro | IDE 集成、可视化流程 | 偏好图形界面、AWS 生态 |
| Qoder | 规范变更追踪 | 规范频繁迭代的项目 |

说实话，这些工具的核心思想都一样：**先写规范，再写代码。** 工具只是让这个过程更顺畅。即使不用任何工具，只要你按照本书前面讲的方法手动管理 `.spec/` 目录，效果是一样的。

### 9.2.3 AI 编程助手的选择

SDD 是方法论，不绑定任何特定的 AI 编程助手。但不同的助手在实践 SDD 时体验差异很大。这里简要列出主流选项：

**Cursor**

- 类型：AI IDE（基于 VS Code）
- SDD 友好度：⭐⭐⭐⭐⭐
- 规则文件：`.cursor/rules/*.mdc`，支持按文件路径匹配自动加载
- 上下文管理：`@` 引用文件（如 `@spec.md`、`@constitution.md`），很方便
- 特点：Agent 模式能自动读写文件、运行命令，适合 Implement 阶段

Cursor 是本书案例使用的工具。它对 SDD 最友好的地方在于规则文件系统——你在 Constitution 阶段生成的规则会被自动加载，不需要每次手动引用。

**Claude Code**

- 类型：命令行 AI 编程助手
- SDD 友好度：⭐⭐⭐⭐⭐
- 规则文件：`CLAUDE.md`（项目根目录）
- 上下文管理：直接读取项目文件
- 特点：在终端中工作，适合喜欢命令行的开发者；上下文窗口大

Claude Code 的优势是上下文窗口非常大，可以同时"看到"更多的规范文档内容。在 Plan 阶段处理复杂的领域模型时，这个优势很明显。

**GitHub Copilot**

- 类型：IDE 插件（VS Code、JetBrains 等）
- SDD 友好度：⭐⭐⭐⭐
- 规则文件：`.github/copilot-instructions.md`
- 上下文管理：通过 `#file` 引用
- 特点：与 GitHub 生态深度集成，Copilot Chat + Agent 模式

Copilot 的优势是 GitHub 生态集成——如果你的项目已经在用 GitHub Actions、GitHub Issues，Copilot 的工作流会更自然。

**Windsurf**

- 类型：AI IDE（基于 VS Code）
- SDD 友好度：⭐⭐⭐⭐
- 规则文件：`.windsurfrules`
- 上下文管理：`@` 引用文件
- 特点：Cascade 模式支持多步骤自动执行

**怎么选？**

老实说，主流 AI 助手在 SDD 实践中的差异越来越小。选择的关键因素往往不是"哪个更支持 SDD"，而是：

1. **你习惯用什么 IDE？** 如果你离不开 JetBrains，Copilot 可能是唯一选择。
2. **你的团队用什么？** 统一工具比选最好的更重要。
3. **你的预算是多少？** 各工具的价格和额度差异不小。

**一个实用建议**：不管用哪个助手，确保它支持某种形式的"规则文件"或"项目级指令"。这是 SDD 落地的关键——Constitution 必须能被 AI 持续读取，而不是每次对话手动粘贴。

## 9.3 最佳实践

### 9.3.1 SDD 适用场景 vs 不适用场景

SDD 不是银弹。它在某些场景下价值巨大，在另一些场景下则是过度工程。

**适合用 SDD 的场景**

| 场景 | 为什么适合 |
|------|-----------|
| 生产级项目 | 需要可维护、可扩展的代码，规范是长期资产 |
| 团队协作 | 规范是团队的共同语言，减少沟通成本 |
| 复杂业务逻辑 | 领域模型、业务规则需要提前想清楚 |
| 需要长期维护的项目 | 三个月后回来看，规范比代码更容易理解 |
| 多 Feature 迭代 | Constitution 做一次，后续 Feature 高效复用 |

**不适合用 SDD 的场景**

| 场景 | 为什么不适合 |
|------|-------------|
| 快速原型 / PoC | 规范写完了，原型可能方向都变了 |
| 一次性脚本 | 数据迁移脚本、临时工具，写完就扔 |
| 实验探索 | "我先试试看这个库能不能用"——不需要规范 |
| 极小的改动 | 改个按钮颜色、修个 typo，CRC 就够了 |

**关键判断标准**：这个项目/功能，三个月后还会有人维护吗？如果会，用 SDD；如果不会，CRC + 直接编码就行。

**混合使用的现实**

即使在 SDD 项目中，也不是所有事情都要走完整流程。真实的工作节奏是这样的：

- **大 Feature**（用户认证、订单系统）：完整走 SDD → Specify → Clarify → Plan → Tasks → Implement
- **中 Feature**（新增一个筛选条件）：简化走 → 写个简短的 spec，Plan 里加几行，直接实现
- **小改动**（修 Bug、调样式）：CRC 直接搞定，不碰规范文档

不要为了方法论而方法论。SDD 的每个阶段都是为了降低风险——如果风险本身很小，就不需要那么多步骤。

### 9.3.2 常见误区与踩坑经验

在实践 SDD 的过程中，这些是最常见的坑。提前知道，可以少走弯路。

**误区 1：规范写得太细**

> "我在 spec.md 里把每个按钮的像素大小都写了……"

规范是给 AI 的"指导"，不是"像素级设计稿"。写太细的问题：

- 写规范的时间超过了直接写代码的时间
- AI 被过度约束，生成的代码反而不灵活
- 需求一旦变化，改规范的成本很高

**正确做法**：规范关注"做什么"和"为什么"，不关注"怎么做的细节"。具体实现留给 Plan 和 Implement 阶段。

**误区 2：规范写得太粗**

> "spec.md 就一句话：做一个用户管理功能。"

太粗的问题和不写规范一样——AI 会自由发挥，产出物可能和你想的完全不同。

**正确做法**：规范至少要包含用户故事、功能需求列表、验收标准。这三样是底线。

**误区 3：不审查 AI 的产出**

> "AI 写的 Constitution 看起来挺好的，直接用了。"

AI 生成的规范文档有几个常见问题：

- **过度设计**：Todo 应用不需要 CQRS、事件溯源、微服务
- **版本号编造**：AI 可能给出不存在的库版本
- **内部矛盾**：前面说用 SQLAlchemy，后面的示例代码用了 Tortoise ORM
- **遗漏关键项**：安全策略经常缺少错误处理规范

每个阶段的产出都要人来审查。SDD 的"人决策、AI 执行"原则，在审查环节最为关键。

**误区 4：Constitution 塞了太多东西**

> "我把领域模型、API 设计、数据库表结构全写进 Constitution 了。"

回顾第四章的原则：**Constitution 只放规矩，不放设计。** 领域模型和 API 设计属于 Plan 阶段。把它们放进 Constitution，会导致：

- Constitution 频繁修改（每加一个 Feature 都要改）
- Constitution 文档臃肿，AI 读取效率下降
- 职责混乱，分不清哪些是长期规矩、哪些是当前设计

**误区 5：规范写完就不管了**

> "spec.md 写完就开始写代码了，后来需求变了也没更新规范。"

规范和代码脱节是 SDD 最大的隐患。规范不更新，后续的 AI 对话会基于过时的信息产出代码。

**正确做法**：需求变更时，先更新规范文档，再改代码。保持规范是"单一真相源"。

**误区 6：每次对话都从头开始**

> "我每次开新对话都要把 Constitution、spec、plan 全部粘贴一遍……"

这是没有用好规则文件。回顾 4.8 节——把 Constitution 转化为规则文件后，AI 会自动加载。每次对话只需要 `@` 引用当前 Feature 的 spec 和 plan 即可。

### 9.3.3 Constitution 的演进

第 4 章讲 Constitution 时说过"Constitution 不是一成不变的"。但那句话太轻描淡写了。实际项目中，Constitution 的修改是一个高频问题，而且操作不当会影响整个项目。

这里给出具体的操作建议。

**什么时候需要修改 Constitution？**

| 场景 | 例子 | 影响范围 |
|------|------|---------|
| 新技术引入 | 项目需要实时通知，引入 WebSocket | 技术栈、安全策略可能需要更新 |
| 规范被证明不合理 | 强制要求所有函数不超过 20 行，但某些复杂逻辑做不到 | 编码规范需要调整 |
| 架构升级 | 从单体拆微服务 | 架构原则、部署架构大改 |
| 安全要求变化 | 从 JWT 切换为 OAuth2 | 安全策略需要重写 |

**怎么修改？"修宪"四步法**

**第一步：评估影响。** 在修改 Constitution 之前，先问自己：

```
这个修改会影响哪些已有的 Feature？
已经实现的代码需要改吗？
正在进行中的 Feature 的 spec/plan 要更新吗？
```

比如你要把命名规范从 camelCase 改成 snake_case——所有已有代码都要改，这是大工程。但如果你只是增加一条"所有 API 必须返回 request_id"——已有代码需要改，但改动是机械的，可以接受。

**第二步：记录修改原因。** 在 Constitution 文件的变更记录中说明为什么改：

```markdown
## 变更记录

| 日期 | 修改内容 | 原因 |
|------|---------|------|
| 2025-03-15 | 新增 WebSocket 安全策略 | Feature 3 需要实时通知功能 |
| 2025-04-02 | 函数行数限制从 20 行放宽到 50 行 | 实践中发现某些业务逻辑无法在 20 行内合理实现 |
```

**第三步：同步更新规则文件。** Constitution 改了，从它生成的规则文件（如 `.cursor/rules/`）也要同步更新。否则 AI 读到的还是旧规矩。

**第四步：通知相关方。** 如果是团队项目，Constitution 的修改应该通过 PR 提交，让团队成员审查和讨论。不要一个人悄悄改——Constitution 是团队共识。

**Constitution 的修改频率预期**

一个健康的 Constitution 应该是这样的演进节奏：

- **项目前期（前 1-3 个 Feature）**：修改较频繁，因为很多规矩是写第一个 Feature 时才意识到需要的
- **项目中期（3-10 个 Feature）**：偶尔修改，主要是引入新技术或优化不合理的规范
- **项目后期**：很少修改，Constitution 已经稳定

如果你的 Constitution 每做一个 Feature 都在大改——说明初始版本太草率了，回去花点时间把它做扎实。如果 Constitution 一直不改——要么项目太小，要么你没在实践中反思。

### 9.3.4 在已有项目中引入 SDD

本书用从零开始的 Todo 应用做案例，但现实中大多数人面对的是**已有项目想引入 SDD**。直接照搬全流程不现实——你不可能停下来给所有已有代码补写规范。

推荐**渐进式引入**策略：

**第一阶段：只写 Constitution（1-2 小时）**

不管项目多大，先花 1-2 小时把 Constitution 写出来。不需要完美，把以下内容记录下来就行：

- 项目用什么技术栈（已经定了，照实填）
- 已有的架构风格（是不是分层？模块怎么划分的？）
- 团队约定的编码规范（有就写，没有就趁机定）
- 安全相关的基本策略

这一步的价值是：**让 AI 了解你的项目。** 从此每次和 AI 对话，它都基于正确的上下文工作。

**第二阶段：新 Feature 按 SDD 流程走**

从下一个新 Feature 开始，完整走 SDD 流程：Specify → Clarify → Plan → Tasks → Implement。

```
.spec/
├── constitution.md              # 第一阶段产出
└── features/
    └── 005-new-feature/         # 从最新的 Feature 开始
        ├── spec.md
        ├── plan.md
        └── tasks.md
```

已有的 Feature 1-4 没有规范文档？没关系，不需要回头补。**往前走比回头补更重要。**

**第三阶段：按需补写关键 Feature 的规范**

当你需要重构或大改某个已有功能时，趁这个机会给它补写 spec 和 plan：

```
现有代码已经实现了用户认证功能，请根据现有代码反向生成一份功能规范文档。
包含：功能需求列表、非功能需求、验收标准。
```

让 AI 根据已有代码生成规范，你来审查和修正。这比从头写快得多。

**第四阶段：团队推广**

个人实践顺畅后，再推广到团队：

1. 把 Constitution 提交到仓库
2. 选一个新 Feature 做示范，让团队看到 SDD 的效果
3. 逐步形成团队规范

**千万别做的事**：

- ❌ 停下所有开发，花两周给已有代码补规范
- ❌ 要求团队一夜之间全面切换到 SDD
- ❌ 给已经稳定运行的老代码强行套 SDD

SDD 是渐进式的——它的价值在于**从现在开始让事情变好**，而不是回头清理历史。

### 9.3.5 从个人到团队的扩展

前面的内容主要面向个人开发者。当团队使用 SDD 时，有一些额外的考量。

**个人项目的 SDD 简化版**

如果你是一个人做项目，SDD 可以适当简化：

| 阶段 | 完整版 | 个人简化版 |
|------|--------|-----------|
| Constitution | 完整的六大要素 | 技术栈 + 架构原则 + 编码规范（够用就行） |
| Specify | 详细的用户故事和验收标准 | 需求列表 + 关键验收条件 |
| Clarify | 结构化澄清 + 自由补充 | 快速过一遍，没疑问就跳过 |
| Plan | 领域模型 + 数据模型 + API 设计 | 重点部分做详细设计，简单部分略写 |
| Tasks | 完整的任务列表 + 依赖关系 | 列个清单就行 |
| Implement | Test → Implement → Review | 重要逻辑写测试，简单 CRUD 直接实现 |

原则是：**核心步骤不跳过，每个步骤的深度按需调整。** Specify 和 Plan 是最不能省的——即使简化，这两步也要走。

**团队协作中的 SDD**

团队使用 SDD 时，规范文档有了新的角色——**它是团队的沟通载体。**

**谁写 Constitution？怎么 Review？**

Constitution 是团队共识，不是某个人拍脑袋定的。推荐的做法：

1. **由技术负责人起草初版**：他最了解项目的技术选型和架构方向
2. **全员 Review**：通过 PR 提交，每个团队成员都有义务审查和提意见
3. **达成共识后合并**：有分歧的地方讨论清楚再合并，不要"先合并再说"
4. **定期回顾**：每个季度或者每 3-5 个 Feature 之后，团队一起回顾 Constitution 是否需要更新

关键原则：**Constitution 的修改权不属于某个人，而属于整个团队。** 任何修改都要走 PR + Review 流程。

**Spec 和 Plan 的 Review 流程**

```
1. 产品经理描述需求
2. 开发者用 AI 生成 spec.md → 提交 PR
   - 产品经理审查：需求是否准确？有没有遗漏？
   - 其他开发者审查：可行性如何？边界场景全吗？
3. spec.md 合并后，开发者用 AI 生成 plan.md → 提交 PR
   - 技术负责人审查：架构方案是否合理？和 Constitution 一致吗？
   - 相关模块的开发者审查：会不会和我正在做的 Feature 冲突？
4. plan.md 合并后，拆解 tasks.md → 开始实现
5. 实现完成后，代码 PR + 更新后的规范文档一起提交
```

这个流程的好处是：**审查前移。** 传统的 Code Review 是在代码写完之后才发现问题——改起来成本高。SDD 的 Spec Review 和 Plan Review 在代码之前就进行，发现问题的成本极低。

一个真实的对比：

| 场景 | 传统流程 | SDD 流程 |
|------|---------|---------|
| 发现 API 设计不合理 | 代码写完了，要改 API + 改前端 + 改测试 | Plan Review 阶段就发现了，改一下 plan.md |
| 发现需求有歧义 | 代码写了一半，停下来找产品确认，可能要推翻重来 | Spec Review 阶段就澄清了，还没写一行代码 |
| 发现和其他 Feature 冲突 | 两个人的代码都写完了，合并时冲突一大堆 | Plan Review 时就发现了，提前协调设计 |

**多人并行开发时的 Spec 冲突处理**

团队多人并行开发不同 Feature 时，最常见的问题是：Feature A 和 Feature B 的设计互相影响。

处理原则：

1. **Plan 阶段暴露冲突**：每个 Feature 的 plan.md 提交 PR 时，其他 Feature 的负责人必须审查。如果 Feature A 的 API 设计和 Feature B 冲突——在 Plan 阶段解决，而不是等代码合并时才发现。

2. **共享模块优先讨论**：如果两个 Feature 都需要修改同一个领域模型（比如给 User 加字段），先在 Plan 层面协调：谁先改？加的字段会不会影响对方？

3. **Constitution 变更冻结**：当多个 Feature 并行时，不要同时修改 Constitution。如果某个 Feature 确实需要改 Constitution（比如引入新技术），要先和所有并行 Feature 的负责人确认影响。

**新成员 Onboarding**

SDD 对新成员最友好的一点：**读完 `.spec/` 目录就能了解整个项目。**

```
新成员 onboarding 路径：
1. 读 constitution.md → 了解项目的技术栈、架构、规范
2. 浏览 features/ 目录 → 了解项目有哪些功能
3. 读最近一个 Feature 的 spec.md + plan.md → 了解需求和设计是怎么写的
4. 领一个新 Feature → 按 SDD 流程走一遍
```

比传统的"看代码理解项目"高效得多——代码告诉你"怎么做的"，规范文档告诉你"为什么这么做"。

**多 AI Agent 协作**

当团队规模更大时，可能会出现多个 AI Agent（或者多个开发者各自的 AI 助手）同时工作的情况。这时候 Constitution 的价值更加凸显：

- **一致性保障**：不管谁的 AI 助手在写代码，都遵守同一份 Constitution 的规则
- **冲突减少**：架构原则和编码规范统一，不同人产出的代码风格一致
- **并行开发**：不同 Feature 可以并行推进，只要各自的 spec 和 plan 不冲突
- **可审计性**：每个 Feature 的规范文档都有 Git 记录，谁在什么时候做了什么决策，一目了然

## 9.4 本章小结

这一章我们聊了三个方面的内容：

**工具生态**：
- GitHub Spec Kit 是目前最标准化的 SDD 工具，值得关注
- Kiro、Qoder 等工具各有特色，但核心理念相同
- AI 编程助手的选择取决于个人习惯和团队统一，不必纠结"哪个最好"
- 关键是选一个支持规则文件的助手，让 Constitution 能被自动加载

**最佳实践**：
- SDD 适合生产级、需要长期维护的项目；不适合原型、脚本、实验
- 即使在 SDD 项目中，也要按任务大小灵活调整流程深度
- 常见误区集中在"规范粒度"和"审查习惯"上
- Constitution 会演进——通过"评估影响 → 记录原因 → 同步规则 → 通知团队"四步法管理变更
- 已有项目渐进式引入 SDD：先写 Constitution，新 Feature 走 SDD，按需补写旧 Feature 规范

**团队扩展**：
- 个人项目可以简化 SDD 流程，但 Specify 和 Plan 不能省
- 团队协作的核心价值是"审查前移"——在代码之前审查规范
- Constitution 由团队共同拥有，修改走 PR + Review 流程
- 多人并行开发时，通过 Plan Review 提前暴露 Feature 间的冲突
- 新成员读完 `.spec/` 目录即可快速了解项目
